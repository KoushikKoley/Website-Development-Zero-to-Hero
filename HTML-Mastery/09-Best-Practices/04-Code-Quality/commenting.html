HTML Comments

Comments are the only way to write human-readable notes inside HTML. Used well, they make large files navigable. Used poorly, they leak secrets, bloat downloads, and confuse future maintainers. Here's how to comment like a professional.

1 Comment Syntax

HTML comments start with <!-- and end with -->. They can span multiple lines. The browser does not render them visually, but they appear in the source and in the DOM as Comment nodes.

<!-- A single-line comment -->

<!--
  A multi-line comment.
  Often used to describe a section
  or temporarily disable code.
-->

<p>This renders.</p>
<!-- <p>This does not render.</p> -->

What you CAN'T put in a comment

Comments cannot contain the sequence -- (two hyphens) anywhere inside them — this is the closing delimiter and confuses the parser. The sequence --> ends the comment immediately.

<!-- INVALID: nested --> inside comment ends it early -->

<!-- INVALID: -- inside the comment -->
                 ^^^ parser may misinterpret

<!-- VALID but weird: - is fine, only -- is special -->
Common Mistake Trying to nest comments. <!-- outer <!-- inner --> more outer --> doesn't work — the first --> ends the outer comment, and "more outer -->" renders as visible text. To "comment out" code that contains comments, use a build step or temporarily rename the inner -->.

2 What to Comment

Comments should answer why, not what. The HTML itself already shows what the code does. Comments add the context the code can't show: intent, history, gotchas, and section structure.

Section starts/ends

In large files, mark the beginning and end of major sections so a reader can scroll-jump and orient quickly.

Complex markup intent

When a chunk of HTML exists for a non-obvious reason — browser workaround, A/B test variant, legacy support — say so.

TODOs and FIXMEs

Mark incomplete or known-buggy code with a discoverable prefix.

External references

Link to design docs, ticket numbers, specs, or pull requests that explain the markup.

Browser-specific hacks

Code that exists to work around a specific browser bug deserves a comment explaining what bug, what browser, and when it can be removed.

Templating placeholders

In server-rendered templates, mark where dynamic content goes.

3 What NOT to Comment

Comments have a cost — they're downloaded by every visitor, they get stale, and they can leak information. Don't comment:

✗ Never comment these

  • Obvious things: <!-- close div -->
  • Secrets: API keys, database passwords, internal URLs
  • Sensitive info: customer names, internal employee names, unreleased dates
  • Rants: complaints about coworkers, management, or the codebase
  • Changelogs: use git for history, not HTML
  • Removed code: delete it, rely on git history

✓ Comment these instead

  • Why this hack exists: "Safari 15 box-shadow bug"
  • What a complex template outputs: "Renders the user's first 5 orders"
  • Removal conditions: "Remove when IE11 support dropped (Q3 2025)"
  • Cross-references: "See /docs/api/auth.md §3.2"
  • Warnings: "Editing this breaks the build pipeline"
Common Mistake Committing comments like <!-- TODO: ask marketing for the real price --> or <!-- HACK: this is wrong but management wanted it --> into production. These end up in your public HTML, visible to anyone who clicks "View Source". Customers, competitors, and security researchers all see them.

4 Section Markers

In long HTML files (landing pages, email templates, complex layouts), comment markers help maintainers find sections quickly. A common pattern:

<!-- ============================= -->
<!-- HERO SECTION                  -->
<!-- ============================= -->
<section class="hero">
  ...
</section>
<!-- /HERO SECTION -->


<!-- ============================= -->
<!-- FEATURES GRID                 -->
<!-- ============================= -->
<section class="features">
  ...
</section>
<!-- /FEATURES GRID -->

Notice the matching end marker <!-- /HERO SECTION --> — closing the section with a slash makes it easy to find both the open and close with editor search.

Pro Tip If you find yourself needing dozens of section markers, consider splitting the file into partials/includes. Comments are a workaround for files that are too big.

5 TODOs and FIXMEs

Use standardized prefixes so tools can find them. Most IDEs highlight TODO, FIXME, and XXX in comment scanning.

<!-- TODO: replace placeholder copy with marketing's final text -->
<h1>Lorem ipsum dolor sit amet</h1>

<!-- FIXME: this layout breaks on iOS Safari 14, see ticket #4521 -->
<div class="grid">...</div>

<!-- HACK: extra wrapper div needed for IE11 flexbox bug.
     Remove when IE11 support drops (planned Q4 2024). -->
<div class="ie11-wrapper">
  <div class="grid">...</div>
</div>

<!-- XXX: this ARIA pattern is suspect. Re-check against
     WAI-ARIA Authoring Practices 1.2 -->
<div role="combobox" ...>...</div>

Standard prefixes

PrefixMeaning
TODOWork that needs to be done
FIXMEKnown broken code that needs fixing
HACKWorking but ugly workaround — should be refactored
XXXWarning — this code is suspect
NOTEInformational note for future readers
OPTIMIZEPerformance improvement opportunity
REVIEWNeeds code review or design review

6 Browser-Specific Hacks

When you must include markup that exists only for a specific browser, comment what bug you're working around and when it can be removed.

<!-- Safari 15 box-shadow render bug.
     See https://bugs.webkit.org/show_bug.cgi?id=234567
     Remove when Safari 17 adoption > 95% (estimate: Jan 2025) -->
<div class="safari-shadow-fix">...</div>

Three critical pieces:

  1. What browser/bug
  2. Reference link (bug tracker, MDN, caniuse)
  3. Removal condition (date, version, metric)

Without all three, the hack lives forever because no one knows it's safe to remove.

7 IE Conditional Comments

Internet Explorer (5 through 9) supported a special comment syntax that only IE parsed as content:

<!--[if IE]>
  <link rel="stylesheet" href="ie-only.css">
<![endif]-->

<!--[if lt IE 9]>
  <script src="html5shiv.js"></script>
<![endif]-->

<!--[if !IE]><!-->
  <p>Shown in all non-IE browsers.</p>
<!--<![endif]-->

These are deprecated and removed in IE 10+. Modern browsers see them as ordinary comments and ignore the contents. Conditional comments are a relic of the past — don't use them.

Modern alternatives

  • Feature detection via JavaScript (@supports in CSS, Modernizr or native checks in JS)
  • Progressive enhancement — serve a baseline that works everywhere, enhance for modern browsers
  • Polyfills loaded conditionally based on user agent or feature detection
Common Mistake Using IE conditional comments in 2024 code. They're no-ops in every modern browser (IE itself is unsupported by Microsoft). If you see them in a codebase, they can be safely deleted along with the IE-specific code they loaded.

8 Performance Impact

Comments are still downloaded by every visitor. They're part of the HTML response, even though they're not rendered. A 200-line comment block on every page is 8 KB of bandwidth per page view.

Performance implications:

  • Bandwidth: comments are bytes shipped to every client
  • Parse time: minimal — the HTML tokenizer skips comments in microseconds
  • DOM size: comments become Comment nodes in the DOM, slightly increasing memory
  • HTTP compression: gzip and brotli compress comments aggressively — usually by 80%+

Removing comments in production

Most build tools strip comments in production builds:

// vite.config.js
import { defineConfig } from 'vite';
import htmlMinifier from 'vite-plugin-html-minifier';

export default defineConfig({
  plugins: [
    htmlMinifier({
      collapseWhitespace: true,
      removeComments: true,        // strip all comments
      removeCommentsFromCDATA: true,
      // To preserve specific comments (like IE conditional or license):
      // ignoreCustomComments: [/^license:/i]
    })
  ]
});
Pro Tip Configure your minifier to preserve license comments. Many open-source libraries require their license notice to be included. Use a pattern like /*! license: ... */ (with the leading exclamation mark in some tools) to keep these in production.

9 Common Mistakes

Leaking secrets in comments

<!-- API_KEY=sk_abc123 --> ships to every visitor. Strip comments or use env vars.

Nesting comments

HTML doesn't support it. The first --> ends the comment, the rest renders as text.

Comment-out instead of delete

"Just in case I need it later" — that's what git history is for. Dead code in comments accumulates.

Commenting the obvious

<!-- this is a button --> before <button> adds zero value.

Stale comments

Code changes, comment doesn't. Now the comment contradicts the code. Worse than no comment.

Internal jargon in production

Comments that reference internal team names, ticket systems, or trade secrets are visible to all visitors.

10 Exercise

Exercise: Audit a Page's Comments

Below is a section of HTML with problematic comments. Identify each issue and rewrite the comments appropriately.

<!-- begin hero section -->
<section class="hero">
  <!-- TODO: replace this with the real headline -->
  <h1>Lorem ipsum dolor</h1>
  <!-- API_KEY=sk_live_abc123, used for /v1/checkout -->
  <!-- HACK: this div has display:none because the
       old design had an image here that marketing
       didn't want to remove yet -->
  <div style="display:none"><img src="old-hero.png"></div>
</section>
<!-- end hero section -->

<!--[if IE]>
  <link rel="stylesheet" href="ie.css">
<![endif]-->

<!-- TODO: ask @mike from billing for the correct price -->
<span class="price">$99</span>

Issues to find:

  • begin hero section / end hero section — redundant; the section tag is obvious
  • API_KEY=... — secret leaked in production HTML
  • HACK comment is fine but should specify removal condition
  • display:none image is dead code — should be deleted, not commented or hidden
  • IE conditional comment is deprecated — remove it
  • "ask @mike from billing" — internal reference visible to all visitors

Deliverable: Rewrite the markup with minimal, professional comments that don't leak information.

11 Browser Support

HTML comments: supported in every browser ever Multi-line comments: all browsers IE conditional comments: IE 5–9 only, removed in IE 10+ Comment stripping (minification): supported by all major build tools

Comments are universally supported. The only deprecated feature is the IE conditional comment syntax, which is silently ignored by all modern browsers (including modern IE 10/11).

Real-World Use Case A startup's production HTML leaked <!-- TODO: replace dummy price $99 with the real $149 --> for three months. A customer noticed it in "View Source", took a screenshot, and posted it on social media. The CEO had to issue a public apology. After the incident, the company added html-minifier-terser with removeComments: true to their build pipeline. Production comments are now stripped automatically — developers can comment freely without worrying about leaks.

Tools for stripping comments

  • html-minifier-terser — the most popular HTML minifier, used by Webpack, Vite plugins
  • Vite plugin: vite-plugin-html-minifier
  • Webpack: html-webpack-plugin with minify option
  • Server-side rendering — most frameworks (Next.js, Nuxt, Astro) strip comments in production builds by default
