Code Formatting

Consistency beats correctness. Pick indentation, attribute order, line length, and quote style — then automate enforcement with Prettier and ESLint. Stop debating style in code review; let machines handle it.

1 Why Formatting Matters

Developers spend more time reading code than writing it. Consistent formatting reduces cognitive load — your brain doesn't have to context-switch between different styles. Inconsistent formatting creates "noise" that hides real bugs and triggers unproductive debates in code review.

The professional approach: pick a style once, automate it, never argue about it again.

Pro Tip The best formatting rule is the one your team can agree to enforce automatically. Prettier, ESLint, and editor configs make style debates obsolete — the formatter just runs on save.

2 Indentation

Two choices: 2 spaces or 4 spaces. Tabs vs spaces. The actual choice matters less than consistency — but each has practical tradeoffs.

StyleProsCons
2 spacesMost popular in modern JS/HTML ecosystems; allows deeper nesting without running off screen; matches Prettier defaultLess visually distinct at shallow depths
4 spacesMore visually distinct; traditional in Python/JavaDeep nesting overflows narrow viewports
TabsAccessible — screen reader users can configure tab width; one character per indent level; smaller file sizeSome tools render tabs inconsistently; mix with spaces = chaos
Spaces (any)Always renders identically across editorsLarger files; can't be customized per viewer

✗ Mixed

<div>
    <p>Indented 4 spaces</p>
  <p>Indented 2 spaces</p>
</div>

✓ Consistent (2 spaces)

<div>
  <p>First paragraph</p>
  <p>Second paragraph</p>
</div>
Real-World Use Case The Prettier project surveyed thousands of OSS repos and found 2-space indentation dominates modern HTML/JS (~85%). Prettier defaults to 2 spaces — most teams just go with the default and stop thinking about it.

3 Line Length

Long lines force horizontal scrolling and obscure structure. The convention in modern HTML is 80 characters soft limit, 120 hard limit. Prettier defaults to 80.

<!-- Good: under 80 chars -->
<a href="/blog/seo-meta-tags" class="card-link">Read more</a>

<!-- Borderline: ~80 chars -->
<button type="button" class="btn btn-primary" data-action="submit">Save</button>

<!-- Too long: split across lines -->
<button
  type="button"
  class="btn btn-primary btn-large"
  data-action="submit"
  data-track="form-submit"
  aria-label="Save and submit the form"
>
  Save
</button>
Pro Tip Prettier automatically breaks long attribute lists across multiple lines when they exceed the print width. You don't have to think about it — just write your HTML normally and let Prettier decide when to wrap.

4 Attribute Order

There's no official HTML spec for attribute order, but a strong convention has emerged from the Vue.js, React, and HTML communities:

  1. id — unique identifier (most important for selectors)
  2. class — styling hooks
  3. data-* — custom data attributes
  4. src, href, type — primary resource/behavior
  5. name, value, placeholder — form-related
  6. role, aria-* — accessibility
  7. style, title, tabindex — presentation & misc
  8. Everything else, alphabetical

✗ Random order

<button
  data-action="submit"
  class="btn"
  id="save-button"
  aria-label="Save"
  type="button"
>Save</button>

✓ Convention

<button
  id="save-button"
  class="btn"
  data-action="submit"
  type="button"
  aria-label="Save"
>Save</button>

Within each group, order alphabetically for predictability. The order isn't about correctness — it's about making attributes easy to find when scanning unfamiliar markup.

5 Multiline Attributes

When an element has many attributes or a single attribute (like srcset) is very long, break across lines. Prettier's default behavior:

<!-- Single line if short -->
<img src="hero.webp" alt="Sunrise" width="1600" height="900">

<!-- Multiline when over print width -->
<img
  src="hero.webp"
  alt="Sunrise over the mountains, casting long shadows across the valley"
  width="1600"
  height="900"
  loading="lazy"
  decoding="async"
  fetchpriority="low"
>

<!-- Long srcset broken into one source per line -->
<img
  srcset="
    /img/small.webp   480w,
    /img/medium.webp  960w,
    /img/large.webp  1600w
  "
  sizes="(max-width: 600px) 100vw, 50vw"
  src="/img/large.webp"
  alt="..."
>
Pro Tip Notice the closing > on its own line in the multiline case. This is Prettier's default — it makes diffs cleaner when adding attributes (the closing bracket line doesn't change). Some teams prefer the > on the last attribute line; either is fine, just be consistent.

6 Single vs Double Quotes

HTML allows both single (') and double (") quotes for attribute values. The WHATWG spec treats them identically. The choice is purely stylistic.

ConventionUsed byNotes
Double quotesHTML spec examples, most legacy HTML, Prettier default for HTMLMatches what most developers expect; safer when value contains apostrophes
Single quotesJSX (React), some Vue style guidesAllows apostrophes in values without escaping
No quotesAllowed for unambiguous attribute values per specNever do this — fragile and confusing
 
<!-- Don't mix styles -->
<a href='/' class="nav-link">Home</a>

<!-- Pick one (Prettier default: double) -->
<a href="/" class="nav-link">Home</a>

<!-- When value contains a quote, switch or escape -->
<a href="/" title="User's profile">Profile</a>
<a href="/" title='User "jane" profile'>Profile</a>
<a href="/" title="User \"jane\" profile">Profile</a>  <!-- invalid HTML! -->
Common Mistake Trying to escape double quotes inside double-quoted attributes with \". That's JavaScript syntax — HTML uses &quot; for escaped double quotes. Or just switch to single quotes for that attribute.

7 Semantic Line Breaks

The Semantic Line Breaks convention suggests breaking lines at natural semantic boundaries — between clauses, sentences, list items — even when there's no technical need to wrap. This makes diffs cleaner and code easier to read in plain text.

<p>
  This is a long paragraph
  that has been broken into lines
  at natural semantic boundaries.
  Each line is a complete thought
  that can be reviewed independently.
</p>

Pros:

  • Git diffs are line-based — semantic breaks mean a single word change only affects one line
  • Easier to scan in narrow terminals or side-by-side diffs
  • Plain-text editors show structure naturally

Cons:

  • Source has more lines than the rendered output (visual mismatch)
  • Some tools (linters, minifiers) may complain or reflow
  • Not always intuitive to new contributors

Most teams don't enforce semantic breaks for HTML — they're more common in Markdown. Use them in HTML when content is hand-written prose, skip them when content is short or templated.

8 Prettier Configuration

Prettier is the de facto HTML formatter. Install and configure once; never think about formatting again.

# Install
npm install --save-dev prettier

# Run on save (VS Code)
# Install "Prettier - Code formatter" extension, then:
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "[html]": { "editor.defaultFormatter": "esbenp.prettier-vscode" }
}
// .prettierrc — the standard config most teams use
{
  "printWidth": 80,
  "tabWidth": 2,
  "useTabs": false,
  "semi": true,
  "singleQuote": true,
  "htmlWhitespaceSensitivity": "css",
  "bracketSameLine": false,
  "overrides": [
    {
      "files": "*.html",
      "options": {
        "parser": "html",
        "singleQuote": false,
        "printWidth": 120
      }
    }
  ]
}

Key HTML-specific options

OptionDefaultEffect
printWidth80Max chars before wrapping
tabWidth2Spaces per indent level
useTabsfalseUse tab characters instead of spaces
singleQuotefalseUse single quotes (most teams set true for JS, false for HTML)
htmlWhitespaceSensitivity"css"How to handle inline vs block whitespace — "css" (default), "strict", or "ignore"
bracketSameLinefalseWhether to put > on the same line as the last attribute
Pro Tip Use the .prettierignore file to skip generated HTML, vendor files, and template partials that don't fit Prettier's expectations. Example: dist/**, vendor/**, *.hbs.

9 ESLint for HTML

ESLint is primarily a JavaScript linter, but with the eslint-plugin-html plugin, it lints JavaScript inside <script> tags. For pure HTML structural linting, use htmlhint or html-validate (covered in the validation file).

# Install
npm install --save-dev eslint eslint-plugin-html

# .eslintrc.json
{
  "env": { "browser": true, "es2024": true },
  "parserOptions": { "ecmaVersion": "latest" },
  "plugins": ["html"],
  "rules": {
    "no-undef": "error",
    "no-unused-vars": "warn",
    "no-console": "warn"
  },
  "settings": {
    "html/indent": "+2"
  }
}

htmlhint for structural rules

# .htmlhintrc
{
  "tag-pair": true,
  "tagname-lowercase": true,
  "attr-lowercase": true,
  "attr-value-double-quotes": true,
  "attr-value-not-empty": true,
  "attr-no-duplication": true,
  "doctype-first": true,
  "id-unique": true,
  "src-not-empty": true,
  "title-tag-required": true,
  "alt-require": true,
  "inline-style-disabled": false,
  "inline-script-disabled": false,
  "space-tab-mixed-disabled": "space",
  "id-class-value": "dash",
  "style-disabled": false,
  "img-alt-require": true
}

Run with npx htmlhint "**/*.html" or via a pre-commit hook.

10 Common Mistakes

Mixing tabs and spaces

Causes "phantom" indentation bugs. Configure editor to insert spaces for tabs; Prettier normalizes on save.

Manually aligning attributes

Looks tidy but breaks the moment you add a longer attribute. Let Prettier handle it.

Unquoted attribute values

class=btn works in HTML but is fragile. Always quote.

No formatter on save

Manual formatting wastes time. Set editor.formatOnSave and forget about it.

Long lines (300+ chars)

Force horizontal scrolling, hide structure. Cap at 80–120 chars.

Style debates in code review

If Prettier produced it, it's by definition correct. Don't review formatting — review logic.

11 Exercise

Exercise: Format and Standardize

Take this inconsistent HTML and (1) manually reformat it according to the conventions in this page, then (2) run Prettier on it and compare your result.

<div class='container' id='main'>
        <header>
<h1>Welcome</h1>
   <nav class='main-nav'>
<a href='/'>Home</a><a href='/blog'>Blog</a><a href='/about'>About</a>
            </nav>
</header>
    <main>
<article class="post" id="post-1" data-author="jane">
<h2>First Post</h2>
<p>This is a paragraph that goes on for a very long time without any obvious reason to break it across multiple lines, which makes it hard to read in narrow editors and terminals.</p>
<img src='/img/cover.webp' alt='Cover image' width=1600 height=900>
</article>
</main>
</div>

Tasks:

  1. Standardize on 2-space indentation.
  2. Use double quotes for all attribute values.
  3. Reorder attributes: id, class, data-*, then the rest.
  4. Break long lines and put each link in the nav on its own line.
  5. Add quotes to the width and height attributes.
  6. Install Prettier and run it on the result. Diff your manual formatting against Prettier's output.

12 Tooling Support

Prettier: VS Code, JetBrains, Sublime, Vim, Emacs — all major editors ESLint + eslint-plugin-html: all editors via CLI HTMLHint: CLI + VS Code extension html-validate: CLI + VS Code extension EditorConfig: universal — all editors respect .editorconfig

The .editorconfig safety net

Even without Prettier, a .editorconfig file enforces basic indentation across every editor that supports it (which is all of them, via built-in or plugin).

# .editorconfig
root = true

[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true
trim_trailing_whitespace = true

[*.{html,htm}]
indent_style = space
indent_size = 2
max_line_length = 80

[*.md]
trim_trailing_whitespace = false  # preserve Markdown line breaks
Real-World Use Case A 40-developer team standardized on Prettier with 2-space indentation, double quotes for HTML, single for JS. Code review comments about formatting dropped 92% (measured over 6 months). Reviewers focused on logic, not style. New hires stopped asking "what style should I use" — they just ran the formatter and shipped.
