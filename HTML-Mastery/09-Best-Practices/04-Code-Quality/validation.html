HTML Validation

The W3C Markup Validator catches mistakes browsers silently forgive — unclosed tags, duplicate IDs, invalid nesting, deprecated attributes. Validation isn't pedantry; it prevents quirks mode, parsing inconsistencies, and accessibility failures.

1 Why Validate?

Browsers are incredibly forgiving. They'll render HTML with unclosed tags, misspelled attributes, and duplicate IDs without showing an error. This forgiveness is a feature for resilience — but it hides bugs from developers. The same invalid markup may parse differently in different browsers, or break accessibility tools, or trigger quirks mode.

Validation checks your HTML against the official WHATWG HTML spec (or W3C's HTML5 spec — essentially the same). It catches:

  • Structural errors (unclosed tags, invalid nesting)
  • Missing required attributes (e.g. alt on <img>, label on form controls)
  • Deprecated elements and attributes (<center>, bgcolor)
  • Invalid attribute values (e.g. tabindex="banana")
  • Duplicate id attributes (which break getElementById, <label for>, ARIA relationships)
Pro Tip Validation is a baseline, not a quality bar. A page can pass validation and still be inaccessible, slow, and ugly. But a page that fails validation almost certainly has bugs you don't know about. Validate early, validate often.

3 The W3C Validator

The official service at validator.w3.org. Three input methods:

  • Validate by URL — paste a public URL, validator fetches and checks
  • Validate by File Upload — upload an HTML file from disk
  • Validate by Direct Input — paste HTML text

The validator reports three severities:

  • Error — Spec violation that browsers may interpret unpredictably
  • Warning — Likely mistake but not strictly spec-violating
  • Info — Suggestions and best-practice notes
Pro Tip The W3C validator is built on the nu Html Checker — the same engine Google uses internally. You can run it locally via Java: java -jar vnu.jar your-file.html. Ideal for batch validation of thousands of pages in CI.

4 Browser DevTools

Modern browsers surface HTML problems directly in DevTools — no external service needed.

Chrome DevTools → Issues tab

Open DevTools (F12), find the "Issues" tab. Chrome lists:

  • Cross-origin resource issues (CORS, mixed content)
  • Deprecated features (document.write, <marquee>)
  • Accessibility issues (missing alt, low-contrast)
  • Quirks mode triggers

Viewing the parsed (not source) DOM

The Elements panel shows what the browser actually parsed, which may differ from your source HTML. If your source has unclosed tags, the Elements panel shows where the browser inserted implicit closing tags — invaluable for diagnosing layout bugs.

Source HTML:                    Parsed DOM (Elements panel):
─────────────                    ────────────────────────────
<div>                           <div>
  <p>Hello                        <p>Hello</p>       ← auto-closed
  <div>World</div>              <div>World</div>
</div>                            </div>
                                </div>                  ← extra close!

5 VS Code Extensions

VS Code ships with built-in HTML Language Features (Microsoft) that flag many issues as you type. For deeper validation:

HTMLHint

Configurable linter. Catches tag-pair mismatches, duplicate IDs, missing alt. Configurable via .htmlhintrc.

HTML-validate

Wraps the nu Html Checker engine. Strictest, most accurate. Integrates with VS Code and CI.

Prettier

Formatter, not validator — but catches structural problems by refusing to format broken HTML.

6 Common Validation Errors

6.1 Unclosed tags

✗ Unclosed <p>

<p>First paragraph
<p>Second paragraph

Browser auto-closes <p> at the next <p>, but other nesting may break.

✓ Explicit close

<p>First paragraph</p>
<p>Second paragraph</p>

6.2 Duplicate IDs

<!-- ERROR: ID "email" defined more than once -->
<input id="email" type="email">
<input id="email" type="text">

<!-- Consequence -->
document.getElementById('email')  // returns first only
label[for="email"]                // only labels the first

6.3 Invalid nesting

✗ Block inside inline

<a href="/">
  <h2>Title</h2>
  <p>Body</p>
</a>

Heading and paragraph inside an anchor was allowed in HTML5, but nesting <a> inside <a> or <button> inside <button> is not.

✓ Use the right element

<a href="/" class="card-link">
  <span class="card-title">Title</span>
  <span class="card-body">Body</span>
</a>

Or restructure to put the link inside the heading.

6.4 Deprecated attributes

<!-- DEPRECATED -->
<body bgcolor="#ffffff" text="#000000">
<table border="1" cellpadding="5" cellspacing="0">
<img src="x.png" align="right">
<font face="Arial" size="3">Text</font>
<center>Centered</center>

<!-- MODERN EQUIVALENT -->
<body style="background:#fff; color:#000">
<table style="border:1px solid; padding:5px; border-collapse:collapse">
<img src="x.png" style="float:right">
<span style="font-family:Arial; font-size:1rem">Text</span>
<div style="text-align:center">Centered</div>

6.5 Missing required attributes

ElementRequired attributeWhy
<img>alt (even if empty)Accessibility — screen reader needs text or empty alt to skip
<input type="image">alt + srcImage button needs accessible name
<map>nameRequired for image map reference
<form>None strictly required, but action strongly recommendedWhere the form submits
<label>Either wraps a control or has for matching an input's idAccessibility — associates label with input
<iframe>titleAccessibility — announces iframe purpose
<video> / <audio>src or <source> childMedia to play

6.6 Stray end tags

<!-- ERROR: Stray end tag "div" -->
<p>Hello</p>
</div>        ← no matching <div>

<!-- ERROR: end tag for element "p" which is not open -->
<div>Content</p></div>

7 Quirks vs Standards Mode

The browser chooses between three rendering modes based on the doctype:

  • No-quirks (standards) mode — modern, predictable rendering. Triggered by <!DOCTYPE html>.
  • Limited-quirks mode — close to standards, but uses legacy table layout for backward compat. Triggered by HTML 4.01 Transitional / XHTML 1.0 Transitional doctypes.
  • Quirks mode — replicates pre-2000 browser behavior. Box model is wrong (border/padding inside declared width). Triggered by missing or malformed doctype.
Common Mistake Forgetting <!DOCTYPE html>. Without it, the browser enters quirks mode — CSS layouts behave unpredictably, table layouts come back, and modern features may be disabled. Always start your document with the doctype. 
// Check current mode in DevTools console:
document.compatMode
// "CSS1Compat" = standards mode
// "BackCompat" = quirks mode

8 Parsing Inconsistencies

When HTML is malformed, each browser follows the HTML5 spec for "error recovery" — but spec-recovery isn't always predictable, and edge cases differ across browsers. Common issues:

  • Table layout — broken <tr>/<td> nesting may auto-insert extra rows
  • Form control adoption — misplaced form controls can be silently reassigned to a different form
  • Script execution order — misnested <script> tags may execute in unexpected order
  • Cascade layer confusion — broken DOM structure means selectors match unintended elements
Real-World Use Case A team spent two days debugging why a "Submit" button didn't submit. They had a typo: <button type="submti"> — invalid value, browser defaulted to type="submit" in Chrome but type="button" in older Safari. Validation would have caught this in seconds.

9 Common Mistakes

Skipping the doctype

Triggers quirks mode. Always include <!DOCTYPE html> as the first line.

Block elements inside inline

Putting <div> inside <span> is invalid and renders unpredictably.

Duplicate IDs

Breaks getElementById, label for, ARIA relationships. IDs must be unique.

Missing alt on images

Always include — empty alt="" for decorative, descriptive text otherwise.

Inline style for layout

Valid HTML, but unmaintainable. Use external stylesheets.

Validating only at the end

By the time you ship, you've accumulated dozens of errors. Validate continuously with IDE plugins.

10 Exercise

Exercise: Validate and Fix a Buggy Page

Below is HTML with at least 8 validation errors. Copy it to the W3C Validator (or run locally), identify each error, and fix it.

<!DOCTYPE html>
<html>
<head>
  <meta charset="UTF-8">
  <title>Buggy Page</title>
</head>
<body bgcolor="#ffffff">
  <header>
    <img src="logo.png">
    <h1 id="title">Welcome</h1>
  </header>
  <main>
    <h2 id="title">About Us</h2>
    <p>We are a company.
    <p>Located in Portland.
    <div>
      <span>
        <div>Block inside inline</div>
      </span>
    </div>
    <form>
      <input id="email" type="email">
      <input id="email" type="text">
      <button type="submti">Submit</button>
    </form>
    <iframe src="map.html"></iframe>
  </main>
</body>
</html>

Errors to find:

  • Missing lang attribute on <html>
  • Missing viewport meta tag
  • bgcolor on <body> — deprecated
  • Missing alt on <img>
  • Duplicate id="title"
  • Unclosed <p> tags (auto-closed but warn)
  • <div> inside <span> — invalid nesting
  • Duplicate id="email"
  • Typo type="submti" — invalid value
  • Missing title on <iframe>

Deliverable: A clean version that passes the W3C validator with zero errors and zero warnings.

11 Support & CI Integration

W3C Validator: web service, free, no limit for personal use nu Html Checker (v.Nu): Java binary, runs anywhere html-validate: npm package, integrates with Jest/CI Lighthouse: Chrome built-in, includes HTML audit All modern browsers: render per HTML5 spec, error recovery is consistent

CI integration with html-validate

# .github/workflows/validate.yml
name: HTML Validation
on: [push, pull_request]
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: npm install -g html-validate
      - run: html-validate "src/**/*.html"
// .htmlvalidate.json — config
{
  "extends": ["html-validate:recommended"],
  "rules": {
    "void-style": ["error", { "style": "omit" }],
    "attr-quotes": ["error", { "style": "double" }],
    "no-trailing-whitespace": "error"
  }
}
Pro Tip Add html-validate to a pre-commit hook. Every commit gets validated automatically — invalid HTML never reaches your repo. This catches ~80% of validation errors before they hit code review.
