Lazy Loading

Defer off-screen images and iframes until the user scrolls to them. Native loading="lazy", decoding="async", fetchpriority="high" for LCP, aspect-ratio to prevent layout shift, and Intersection Observer for custom lazy behavior.

1 Why Lazy Load?

By default, the browser downloads every <img> and <iframe> on the page as soon as it parses the HTML — even ones the user has to scroll three screens down to see. On a typical blog post with 20 images, that's 8 MB of bandwidth spent on content the user may never reach.

Lazy loading defers the fetch until the element is about to enter the viewport. The result:

  • Faster initial page load (fewer simultaneous downloads compete for bandwidth)
  • Lower data usage for users on metered connections
  • Reduced server load (fewer requests for content that's never viewed)
  • Longer battery life on mobile devices

2 Native loading="lazy"

The browser handles everything — no JavaScript required. Add loading="lazy" to any <img> or <iframe> element. The browser fetches the resource only when it's about to enter the viewport.

<!-- Lazy-load an image -->
<img src="hero.webp"
     alt="Mountain landscape at sunrise"
     width="1600" height="900"
     loading="lazy"
     decoding="async">

<!-- Lazy-load an iframe -->
<iframe src="https://www.youtube.com/embed/abc123"
        title="How to bake sourdough"
        width="560" height="315"
        loading="lazy">
</iframe>

When to NOT use lazy loading

  • The LCP image — it's the largest content element, lazy-loading it would delay LCP
  • Images above the fold (the first viewport's worth)
  • Images inside a print stylesheet that should always be available
  • Critical UI icons (favicons, logo, brand mark)
Pro Tip Pair loading="lazy" with explicit width and height attributes. The browser uses them to reserve space before the image loads, preventing layout shift. Without dimensions, the page reflows every time an image loads — a major Cumulative Layout Shift problem.

3 decoding="async"

Image decoding (turning compressed bytes into pixels) happens on the main thread by default. Large images can jank the UI for tens of milliseconds. decoding="async" tells the browser to decode the image off the main thread, freeing it for other work.

<img src="large-photo.webp"
     alt="..."
     loading="lazy"
     decoding="async">

Three values are accepted:

  • async — decode off the main thread (recommended for most images)
  • sync — decode synchronously when the image is displayed (rarely needed)
  • auto — browser picks (default, equivalent to no attribute)

This attribute is independent of loading="lazy" — you can have one without the other.

4 fetchpriority for LCP

The Largest Contentful Paint (LCP) element is the largest visible block when the page first renders. Often it's a hero image. By default, browsers can't easily tell which image will be LCP — they fetch images in document order. fetchpriority="high" tells the browser "this is critical, fetch it first".

<!-- Hero image: high priority, eager loading -->
<img src="hero.webp"
     alt="Sunrise over the mountain range"
     width="1600" height="900"
     fetchpriority="high"
     decoding="async">

<!-- Background image: low priority -->
<img src="footer-decor.webp"
     alt=""
     aria-hidden="true"
     loading="lazy"
     fetchpriority="low"
     decoding="async">

fetchpriority values

ValueUse case
highLCP image, hero video poster, critical above-the-fold image
lowBelow-the-fold images, decorative backgrounds
autoDefault — browser picks based on heuristics
Common Mistake Setting loading="lazy" on the LCP image. This tells the browser to defer it — the opposite of what you want. The LCP image should be eagerly loaded with fetchpriority="high".

5 aspect-ratio & CLS

When an image loads without explicit dimensions, the browser doesn't know how much space to reserve. The image starts at 0×0, content flows beneath it, then the image loads and shoves everything down. This is Cumulative Layout Shift (CLS) — a Core Web Vital.

Three solutions

<!-- 1. Explicit width and height attributes (best) -->
<img src="hero.webp" width="1600" height="900" alt="...">

<!-- 2. CSS aspect-ratio (modern) -->
<style>
  .card-image { aspect-ratio: 16 / 9; width: 100%; height: auto; }
</style>
<img class="card-image" src="card.webp" alt="...">

<!-- 3. Combined: explicit dims + CSS (fallback-safe) -->
<img src="hero.webp"
     width="1600" height="900"
     style="aspect-ratio: 16/9; width:100%; height:auto;"
     alt="...">

The aspect ratio of the image's intrinsic dimensions should match the displayed aspect ratio. If they differ, the browser stretches or squishes — but at least layout is stable.

Pro Tip For responsive images served at different resolutions by the same <img>, set explicit width/height matching the largest displayed size. CSS can scale down responsively while preserving the ratio.

6 <picture> Art Direction

The <picture> element lets you serve different images based on viewport size, density, or format. Combined with lazy loading, you ship a tiny mobile image on phones and a high-res one on desktops.

<picture>
  <!-- Modern format first -->
  <source type="image/avif"
          srcset="hero-sm.avif 480w, hero-md.avif 960w, hero-lg.avif 1600w"
          sizes="(max-width: 600px) 100vw, (max-width: 1200px) 50vw, 33vw">
  <source type="image/webp"
          srcset="hero-sm.webp 480w, hero-md.webp 960w, hero-lg.webp 1600w"
          sizes="(max-width: 600px) 100vw, (max-width: 1200px) 50vw, 33vw">
  <!-- Fallback for older browsers -->
  <img src="hero-lg.jpg"
       alt="Mountain landscape at sunrise"
       width="1600" height="900"
       loading="lazy"
       decoding="async">
</picture>

Art direction: different images for different screens

<picture>
  <!-- Cropped close-up on mobile -->
  <source media="(max-width: 600px)"
          srcset="portrait-crop.webp"
          width="600" height="900">
  <!-- Wide landscape on desktop -->
  <source media="(min-width: 601px)"
          srcset="wide-hero.webp"
          width="1600" height="600">
  <img src="wide-hero.jpg" alt="..." loading="lazy" decoding="async">
</picture>

Art direction (different crops) is different from resolution switching (same image, different sizes). Use media for art direction, srcset for resolution.

7 Lazy iframes

Third-party embeds (YouTube, Twitter, maps) are heavy: they pull in JS, CSS, fonts, and often third-party tracking. Lazy-loading iframes is one of the highest-impact performance wins on a content page.

<iframe src="https://www.youtube.com/embed/abc123"
        title="Sourdough tutorial"
        width="560" height="315"
        loading="lazy"
        allow="accelerometer; encrypted-media; picture-in-picture"
        allowfullscreen>
</iframe>

<iframe src="https://www.google.com/maps/embed?..."
        title="Map to the venue"
        width="600" height="450"
        loading="lazy"
        referrerpolicy="no-referrer-when-downgrade">
</iframe>
Real-World Use Case A blog with 5 YouTube embeds per post switched to loading="lazy" on the iframes. Initial page weight dropped from 4.2 MB to 0.8 MB (the embeds were loading 3.4 MB of YouTube JS/CSS even though the user hadn't watched anything). First Contentful Paint improved 1.6 seconds on mobile.

Facades for ultimate control

For even faster load, replace embeds with a static thumbnail that becomes the iframe on click. This is called a "facade" — libraries like lite-youtube-embed implement it.

8 Intersection Observer

For custom lazy behavior beyond images and iframes (e.g. lazy-loading a complex widget, infinite scroll, triggering analytics), the Intersection Observer API is the modern tool. It replaces scroll-event listeners that thrash the main thread.

<!-- HTML -->
<div class="lazy-widget" data-src="/api/summary" role="region"
     aria-label="Summary widget">
  Loading summary...
</div>
// JavaScript
const observer = new IntersectionObserver((entries, obs) => {
  entries.forEach(entry => {
    if (!entry.isIntersecting) return;

    const widget = entry.target;
    const src = widget.dataset.src;

    fetch(src)
      .then(r => r.text())
      .then(html => { widget.innerHTML = html; })
      .finally(() => obs.unobserve(widget));
  });
}, {
  root: null,
  rootMargin: '200px',  // start loading 200px before visible
  threshold: 0
});

document.querySelectorAll('.lazy-widget').forEach(el => observer.observe(el));

Why rootMargin?

Without rootMargin, the resource starts fetching only when the element is fully on screen — too late, the user sees empty space. rootMargin: '200px' extends the observer's bounding box 200px outward, so loading starts before the element is visible.

Pro Tip For backward compatibility with very old browsers, the IntersectionObserver polyfill is 3 KB. But all modern browsers (Chrome 51+, Firefox 55+, Safari 12.1+) support it natively. In 2024, you can ship without the polyfill.

9 Common Mistakes

Lazy-loading the LCP image

Delays your largest visible element. Use fetchpriority="high" and no lazy on the hero.

No dimensions on images

Causes Cumulative Layout Shift. Always set width + height or use aspect-ratio.

Lazy-loading first-screen content

Anything visible on initial load should be eagerly fetched.

Missing alt text on lazy images

Accessibility is independent of loading strategy. Always include alt.

JS-based lazy when native works

Native loading="lazy" is faster, simpler, and works without JS. Use libraries only when you need art direction or analytics triggers.

Not respecting Save-Data

Users with Save-Data: on want fewer images, not just lazy ones. Consider serving smaller images to these users.

10 Exercise

Exercise: Optimize a News Article

Below is the markup of a typical news article. Identify the performance problems and rewrite the markup.

<article>
  <h1>Record Heat Wave Sweeps the Pacific Northwest</h1>
  <img src="/img/hero-weather.jpg" alt="Sun over a city">

  <p>Temperatures reached 112°F in Portland on Tuesday...</p>

  <img src="/img/chart-1.png" alt="Temperature graph">
  <p>The chart shows the 7-day forecast...</p>

  <img src="/img/photo-portland.jpg" alt="Downtown Portland">
  <p>Downtown Portland saw temperatures peak at 4pm...</p>

  <iframe src="https://www.youtube.com/embed/heatwave"
          width="560" height="315"></iframe>
</article>

Tasks:

  1. Decide which images should be eagerly loaded with fetchpriority="high" vs lazy-loaded.
  2. Add explicit width and height attributes (you can assume standard sizes).
  3. Add decoding="async" to all images.
  4. Convert one of the inline images to a <picture> with AVIF, WebP, and JPG sources.
  5. Lazy-load the YouTube iframe.
  6. Add title to the iframe for accessibility.

11 Browser Support

loading="lazy" (img): Chrome 76+, Firefox 75+, Safari 15.4+ loading="lazy" (iframe): Chrome 77+, Firefox 121+, Safari 15.4+ decoding="async": Chrome 65+, Firefox 63+, Safari 14+ fetchpriority: Chrome 101+, Edge 101+, Safari 17+ fetchpriority: Firefox — in development as of 2024 aspect-ratio CSS: all modern browsers Intersection Observer: Chrome 51+, Firefox 55+, Safari 12.1+ <picture> element: all modern browsers

For browsers that don't support loading="lazy", the attribute is ignored and images load normally — graceful degradation, no broken behavior.

Testing tools

  • Chrome DevTools → Network — verify that lazy images don't appear in network log until scrolled
  • Lighthouse — flags images without dimensions, off-screen images that aren't lazy
  • WebPageTest — filmstrip view shows when each image loads over time
  • Chrome DevTools → Rendering → "Disable JavaScript" — confirms native lazy-loading still works without JS
