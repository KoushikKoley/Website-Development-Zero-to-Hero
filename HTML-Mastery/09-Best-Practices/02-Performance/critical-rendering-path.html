Critical Rendering Path

The browser turns HTML bytes into pixels through a precise pipeline. Understanding it tells you exactly why <script defer>, async, and CSS placement matter — and how to make your pages feel instant.

1 Pipeline Overview

When the browser receives an HTML response, it runs the following pipeline. Each stage must complete (or be unblocked) before the next can produce visible pixels:

HTML bytes → DOM + CSS bytes → CSSOM → Render Tree → Layout → Paint → Composite

The two parallel trees (DOM and CSSOM) must both finish before the render tree is built. This is why CSS in the <head> blocks rendering — the browser won't paint half-styled content.

Pro Tip Measure with Chrome DevTools → Performance tab. Record a page load and you'll see the DOM, CSSOM, recalc-style, layout, and paint events. This is the only way to know which stage is your actual bottleneck.

2 DOM Construction

The browser reads the HTML byte stream, decodes characters, tokenizes into start/end tags, and builds a tree of node objects. The DOM is built incrementally — the browser doesn't wait for the full HTML to start creating nodes.

But two things pause DOM construction:

  • Synchronous scripts — the parser hits a <script src> without defer or async, blocks, downloads, and executes the script before continuing.
  • Document.write — document.write() injects HTML synchronously, blocking parsing until the inserted content is loaded. Deprecated and forbidden in modern contexts.
<!-- This blocks parsing -->
<script src="analytics.js"></script>

<!-- This doesn't -->
<script src="analytics.js" defer></script>
<script src="analytics.js" async></script>

3 CSSOM Construction

As the parser encounters <link rel="stylesheet"> or <style> blocks, the browser requests and parses CSS into a parallel tree called the CSS Object Model (CSSOM). Unlike the DOM, CSSOM construction is not incremental — the entire stylesheet must be downloaded and parsed before any of it can be used.

CSS is render-blocking by default. This is usually what you want: rendering unstyled content then flashing to styled would be worse (the "FOUC" — Flash of Unstyled Content).

Common Mistake Loading a 200 KB CSS bundle that styles the entire site on every page. The browser must download and parse all of it before painting. Split CSS by route, and inline the critical above-the-fold CSS.

4 Render Tree

The render tree is a merge of DOM and CSSOM — it contains only visible nodes. Elements with display: none are excluded. visibility: hidden elements stay (they take space). Text nodes with content are included; empty ones aren't.

DOM                CSSOM              Render Tree
─────              ──────             ────────────
html               html               html
└ body             └ body             └ body
  ├ div.header     ├ div.header       ├ div.header
  │ └ h1           │ └ h1             │ └ h1  (visible)
  ├ div.hidden     ├ div.hidden       │   ← excluded (display:none)
  │ └ p            │ └ p              │
  └ div.main       └ div.main         └ div.main
    └ p              └ p                └ p

Once the render tree is built, the browser can compute layout — the geometry of every node on screen.

5 Layout & Paint

Layout (also called "reflow") computes the position and size of every render-tree node based on viewport, fonts, and CSS rules. Paint fills pixels into layers. Composite combines layers into the final image the GPU sends to the screen.

StageWhat it doesWhat triggers it
LayoutComputes x/y/width/height of every nodeAdding/removing elements, changing size, font load
PaintRasterizes each layer to pixelsColor, background, shadow, border changes
CompositeCombines layers via GPUTransform, opacity — these skip layout & paint
Pro Tip Animating transform and opacity skips layout and paint — they go straight to the compositor. Animating top, left, width, or height forces layout on every frame and drops you to 30 fps or worse.

6 Script Loading: defer, async, module

Where and how you load JavaScript has the biggest single impact on initial render. Three attributes control the behavior:

AttributeDownloadExecutionBest for
(none)Blocks parsingImmediately on download, blocks parsingAvoid for anything non-critical
asyncIn parallel with parsingAs soon as downloaded, pauses parserIndependent scripts: analytics, ads
deferIn parallel with parsingAfter parsing, before DOMContentLoaded, in orderApp bundles, scripts that touch the DOM
type="module"Defaults to deferredAfter parsing, in orderES modules — adds CORS by default

Execution timeline

HTML parsing:   ─────────────────────────────────────►
                │                                  │
sync script:    ██ download ██ exec ████ (blocks parser)
                │                                  │
async script:   ── download ── ██ exec (briefly pauses) ──►
                │                                  │
defer script:   ── download ──────────────────► ██ exec (after parse)
                │                                  │
                parser done    DOMContentLoaded fires ──►

✗ Slow: blocking scripts in head

<head>
  <script src="jquery.js"></script>
  <script src="app.js"></script>
  <script src="analytics.js"></script>
</head>

Three blocking scripts. Page won't render until all three download and execute.

✓ Fast: defer & async in head

<head>
  <script src="app.js" defer></script>
  <script src="analytics.js" async></script>
</head>

Browser continues parsing HTML. App runs after DOM is ready, in order.

Pro Tip Modern best practice: put all scripts in <head> with defer. This downloads them as early as possible (in parallel with HTML) but executes them only after the DOM is parsed. The old advice "scripts at the bottom of body" is obsolete.

type="module" specifics

<!-- Module scripts are deferred by default, executed in order -->
<script type="module">
  import { init } from './app.js';
  init();
</script>

<!-- Classic scripts inline are NOT deferred -->
<script>
  // runs immediately during parsing
</script>

7 Render-Blocking CSS Strategies

CSS blocks first render. This is correct for above-the-fold styles but wasteful for CSS that styles content the user won't see for seconds. Strategies:

Inline critical CSS

Embed the minimal CSS needed for above-the-fold content in a <style> block in the head. Eliminates a network request for first paint.

Async-load the rest

Load non-critical CSS with <link rel="preload" as="style" onload="this.rel='stylesheet'">. The browser fetches early but applies without blocking.

Per-route CSS

On multi-page apps, ship only the CSS for the current route. Code-split with bundlers like Vite or Webpack.

Avoid @import

@import in CSS is serial — the browser can't start downloading the imported file until it parses the parent. Use <link> tags instead.

<!-- Critical CSS inlined, full sheet loaded async -->
<head>
  <style>
    /* Above-the-fold rules only — hero, nav, H1 */
    body { margin: 0; font-family: system-ui; }
    .hero { padding: 48px; background: #0f172a; color: #fff; }
  </style>
  <link rel="preload" href="/css/main.css" as="style"
        onload="this.onload=null;this.rel='stylesheet'">
  <noscript><link rel="stylesheet" href="/css/main.css"></noscript>
</head>

8 How HTML Structure Affects Render

Choices in your HTML directly affect CRP performance:

  • Place CSS in <head> — so the browser can start CSSOM construction in parallel with DOM parsing.
  • Preconnect to third-party origins — saves DNS+TLS handshake time before CSS/JS requests fire.
  • Avoid @import in CSS — use <link> tags so downloads parallelize.
  • Use defer for non-critical scripts — never block the parser.
  • Set explicit dimensions on images and embeds — prevents layout shift when they load.
  • Minimize DOM size — large DOMs slow style recalculation, layout, and querySelector performance.
Real-World Use Case A news site moved a 380 KB JavaScript bundle from <script src> to <script defer> in the head, and inlined 4 KB of critical CSS. First Contentful Paint dropped from 3.4s to 1.1s on mobile 4G. The site's Core Web Vitals went from "Poor" to "Good" and search rankings rose accordingly.

9 Common Mistakes

Synchronous scripts in head

Blocks HTML parsing during download and execution. Almost always a mistake.

CSS @import chains

@import url('a.css') inside b.css forces serial download. Use parallel <link> tags.

Large CSS bundles

A 500 KB site-wide stylesheet blocks first render on every page. Split by route.

Inline styles on body elements

Forces style recalculation per element. Use class names and external sheets.

document.write() in modern code

Forces synchronous reflow. Browsers show warnings; some block it entirely in cross-origin iframes.

Missing width/height on images

Causes Cumulative Layout Shift (CLS) as images load. Always set explicit dimensions or use aspect-ratio.

10 Exercise

Exercise: Optimize a Slow Page

Below is the head of a slow page. Identify every CRP problem and rewrite it.

<head>
  <meta charset="UTF-8">
  <title>Slow Page</title>
  <style>
    @import url('/css/reset.css');
    @import url('/css/base.css');
    @import url('/css/components.css');
    @import url('/css/pages/home.css');
  </style>
  <script src="https://cdn.example.com/jquery.js"></script>
  <script src="https://cdn.example.com/analytics.js"></script>
  <script src="/js/app.js"></script>
</head>

Tasks:

  1. Convert the @import chain to parallel <link> tags.
  2. Identify which scripts should be defer vs async.
  3. Add a preconnect hint for cdn.example.com.
  4. Inline a 1 KB critical CSS block for above-the-fold styles.
  5. Load the full CSS asynchronously without breaking the no-JS fallback.

11 Browser Support

defer: all browsers since IE 4 async: all modern browsers type="module": Chrome 61+, Firefox 60+, Safari 11+ preload + onload trick: all modern browsers preconnect: all modern browsers

The critical rendering path itself is browser-internal and consistent across all modern engines. The optimization techniques (defer, async, preload, preconnect) are universally supported in modern Chrome, Firefox, Safari, and Edge.
