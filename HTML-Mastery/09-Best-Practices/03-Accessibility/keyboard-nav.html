Keyboard Navigation

For 8% of users, the keyboard is the only way to navigate. Tab order, tabindex, :focus-visible, skip links, focus traps, and roving tabindex are the techniques that make your site usable without a mouse.

1 Why Keyboard Matters

Keyboard-only users include people with motor disabilities, screen reader users (who rarely use a mouse), power users, and anyone with a broken trackpad. WCAG 2.1.1 (Level A) requires all functionality to be operable from the keyboard — not as a nice-to-have, as a legal baseline.

Native HTML elements (<button>, <a>, <input>, <select>, <textarea>) get keyboard behavior for free: they're in the tab order, they respond to Enter/Space, and they emit focus events. Most keyboard accessibility failures come from custom widgets that rebuild what the browser already does.

Pro Tip If your custom <div>-based widget needs tabindex, role, aria-*, keyboard handlers, and focus management to be accessible — you probably should have used a native element. The browser does all of this for free.

2 Tab Order

The default tab order follows the DOM order. Pressing Tab moves focus from one focusable element to the next, top to bottom, left to right. This is almost always the correct order.

Problems arise when:

  • CSS reorders elements visually (flex-direction: row-reverse, order: 5) — visual order doesn't match tab order, disorienting keyboard users
  • Positive tabindex values — force a different order (almost always wrong; see below)
  • Hidden content becomes visible via JS but isn't focusable
  • Newly inserted elements aren't reached because they were added after the initial tab sequence
<!-- DOM order = visual order = tab order (correct) -->
<header>
  <a href="/">Home</a>
  <a href="/blog">Blog</a>
  <a href="/about">About</a>
</header>

<!-- Problematic: CSS order changes visual order but tab order
     follows DOM, so Tab jumps "backwards" -->
<div style="display:flex; flex-direction: row-reverse;">
  <a href="/a">First in DOM, last visually</a>
  <a href="/b">Second in DOM, first visually</a>
</div>

3 tabindex Values

The tabindex attribute controls whether an element participates in keyboard focus. Three cases:

ValueBehaviorUse case
(no attribute)Default — focusable only if it's a native interactive elementButtons, links, inputs — never add tabindex to these
tabindex="0"Element is focusable in its natural DOM orderCustom widgets that should be in tab order (e.g. a custom <div> acting as a button)
tabindex="-1"Element is NOT in tab order, but can be focused programmatically via JS .focus()Modals, off-screen menus, dynamically inserted content
tabindex="1+"Element is focusable and is visited in numerical order, before tabindex="0"Anti-pattern — avoid
Common Mistake Using positive tabindex values like tabindex="1", tabindex="2". This creates a parallel tab order that breaks when content is added or removed. Always use tabindex="0" for natural-order focus, and re-order the DOM if you need a different sequence. 
<!-- DON'T: positive tabindex -->
<a href="/search" tabindex="1">Search</a>
<a href="/home"  tabindex="2">Home</a>
<a href="/blog"  tabindex="3">Blog</a>

<!-- DO: let DOM order handle it -->
<a href="/home">Home</a>
<a href="/blog">Blog</a>
<a href="/search">Search</a>

<!-- Focusable programmatically only -->
<div id="modal" role="dialog" tabindex="-1" aria-modal="true">
  ...
</div>

4 :focus-visible Styling

For decades, web developers removed focus outlines with outline: none — making keyboard navigation invisible. WCAG 2.4.7 (Level AA) requires a visible focus indicator. The modern solution is :focus-visible, which shows focus rings only for keyboard users, not mouse clickers.

/* Bad: removes focus for everyone, including keyboard users */
button { outline: none; }

/* Better: removes for mouse, keeps for keyboard */
button:focus { outline: none; }
button:focus-visible {
  outline: 3px solid var(--brand);
  outline-offset: 2px;
}

/* Best: pair with :hover and :active for full state styling */
button { outline: none; }
button:focus-visible {
  outline: 3px solid #2563eb;
  outline-offset: 2px;
  box-shadow: 0 0 0 4px rgba(37, 99, 235, 0.25);
}

↑ Try clicking the first button — no ring. Try Tabbing to the second — visible ring.

Pro Tip Never use :focus to show the ring — it shows for mouse clickers too, which looks noisy. Use :focus-visible: the browser intelligently shows it for keyboard users and skips it for mouse users.

5 Skip Links

A skip link is the first focusable element on the page. It's visually hidden until focused, then jumps the user past repetitive navigation to the main content.

<body>
  <a href="#main" class="skip-link">Skip to main content</a>
  <header>...site nav...</header>
  <main id="main" tabindex="-1">
    <h1>Main content starts here</h1>
    ...
  </main>
</body>
.skip-link {
  position: absolute;
  top: -100px;       /* off-screen by default */
  left: 0;
  background: #fbbf24;
  color: #000;
  padding: 12px 18px;
  z-index: 1000;
  border-radius: 0 0 8px 0;
  text-decoration: none;
  font-weight: bold;
}
.skip-link:focus {
  top: 0;            /* slides in when focused */
}
main:focus { outline: none; }
Common Mistake Adding a skip link but no tabindex="-1" on the target. When the user clicks the link, focus doesn't actually move — the browser only scrolls. Adding tabindex="-1" to <main> makes it programmatically focusable, so the next Tab goes to the first interactive element inside main, not back to the header.

6 Focus Traps for Modals

When a modal opens, focus must move into the modal, stay inside it while the user Tabs, and return to the triggering element when the modal closes. Without this, keyboard users Tab out of the modal into hidden page content.

function openModal(trigger) {
  const modal = document.getElementById('modal');
  modal.classList.add('open');

  // Find all focusable elements inside the modal
  const focusables = modal.querySelectorAll(
    'button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])'
  );
  const first = focusables[0];
  const last = focusables[focusables.length - 1];

  // Move focus into the modal
  first.focus();

  // Trap Tab inside the modal
  modal.addEventListener('keydown', e => {
    if (e.key !== 'Tab') return;
    if (e.shiftKey) {
      if (document.activeElement === first) {
        e.preventDefault();
        last.focus();
      }
    } else {
      if (document.activeElement === last) {
        e.preventDefault();
        first.focus();
      }
    }
  });

  // Close handler: restore focus to trigger
  modal.addEventListener('close', () => trigger.focus());
}
Pro Tip Use the native <dialog> element with showModal() — it handles focus trapping, restoration, and ESC-to-close automatically. Only build custom traps if you can't use <dialog>.

7 Roving Tabindex for Widgets

For composite widgets like toolbars, tab lists, menus, and grids, you don't want every child in the tab order — that would require 10+ Tabs to traverse a menu. Instead, only one child is tabindex="0"; the rest are tabindex="-1". Arrow keys move the "roving" tabindex between them.

<!-- Toolbar: only "Save" is in the tab order initially -->
<div role="toolbar" aria-label="Text formatting">
  <button tabindex="0">Bold</button>
  <button tabindex="-1">Italic</button>
  <button tabindex="-1">Underline</button>
  <button tabindex="-1">Save</button>
</div>
const toolbar = document.querySelector('[role="toolbar"]');
const buttons = Array.from(toolbar.querySelectorAll('button'));

toolbar.addEventListener('keydown', e => {
  const current = document.activeElement;
  const i = buttons.indexOf(current);
  if (i === -1) return;

  let next = i;
  if (e.key === 'ArrowRight') next = (i + 1) % buttons.length;
  if (e.key === 'ArrowLeft')  next = (i - 1 + buttons.length) % buttons.length;
  if (next === i) return;

  e.preventDefault();
  buttons.forEach((b, idx) => b.tabIndex = idx === next ? 0 : -1);
  buttons[next].focus();
});

The W3C ARIA Authoring Practices Guide (APG) has fully-worked examples for tabs, menus, comboboxes, and grids. Don't reinvent these — copy the patterns.

8 accesskey (Avoid)

The accesskey attribute assigns a keyboard shortcut to an element. Sounds helpful — in practice, it's almost always harmful:

<!-- Avoid this -->
<a href="/home" accesskey="h">Home</a>

Problems

  • Conflicts with browser/OS shortcuts — Alt+H might be "History" menu in one browser, "Help" in another
  • Hidden from users — sighted users can't see the shortcut without inspecting source or using an extension
  • Inconsistent modifiers — Alt on Windows, Ctrl+Option on Mac, varies by browser
  • Conflicts with screen reader shortcuts — JAWS and NVDA use Alt+letter combos heavily
Common Mistake Using accesskey on every nav item. Power users who know the shortcut use it; everyone else doesn't know it exists; some users have it silently break their browser shortcuts. Skip accesskey entirely unless you have a very specific use case (e.g. an internal tool with documented shortcuts).

9 Keyboard Testing Workflow

A simple, thorough manual test takes 5 minutes. Do this on every page before shipping:

StepActionWhat to verify
1Unplug your mouse. Put it in a drawer.You can't accidentally use it
2Press Tab from page load.First focus should be the skip link
3Tab through every focusable element.Focus moves in visual order; nothing is skipped; nothing is unreachable
4Press Enter on links and buttons.Actions fire
5Press Space on buttons.Actions fire (different from Enter on links)
6Use arrow keys in form selects, dropdowns.Options cycle without a mouse
7Open any modal/dialog.Focus jumps into the modal; Tab cycles inside; Escape closes; focus returns to trigger
8Tab through any custom widget (tabs, accordion, menu).Arrow keys move within the widget; Tab exits cleanly
9Verify the visible focus indicator.Every focused element has a clearly visible ring
10Use Shift+Tab to go backward through the page.Same elements focus in reverse; nothing is unreachable backward
Pro Tip Pair this with screen reader testing (next file). Many keyboard failures are also screen reader failures — but some (like focus traps) are keyboard-only. Test both.

10 Common Mistakes

Removing outlines globally

* { outline: none } at the top of every CSS file. Replace with :focus-visible styling.

Positive tabindex

Always use 0 or -1. Positive values create brittle, parallel tab orders.

Modals without focus traps

Tab escapes to background content that's invisible. Use native <dialog> or implement a trap.

No skip link

Keyboard users Tab through 30 nav links on every page before reaching content. Add a skip link as the first focusable element.

Hidden focusable elements

Elements with display: none are removed from tab order (good), but visibility: hidden children of visibility: visible parents are still focusable. Verify with Tab.

Mismatched DOM/visual order

CSS order, flex-direction: row-reverse, and absolute positioning can make Tab jump backwards through visible content.

11 Exercise

Exercise: Fix a Modal Dialog

Below is a modal implementation with several keyboard accessibility problems. Identify each and rewrite the code.

<div class="backdrop" onclick="close()">
  <div class="modal">
    <h2>Confirm Delete</h2>
    <p>Are you sure you want to delete this item?</p>
    <div class="actions">
      <div class="btn" onclick="cancel()">Cancel</div>
      <div class="btn danger" onclick="confirm()">Delete</div>
    </div>
  </div>
</div>

Problems to find:

  • No role="dialog" or aria-modal
  • No focus trap — Tab escapes to the background
  • No focus on open — focus stays on the trigger button behind the modal
  • No focus restoration on close
  • Divs-as-buttons — no keyboard activation
  • Backdrop click closes the modal without warning (unexpected)
  • No Escape key handler

Deliverable: Rewrite using <dialog> where possible, or with all accessibility attributes and handlers if not.

12 Browser Support

tabindex: all browsers :focus-visible: Chrome 86+, Firefox 85+, Safari 15.4+ <dialog>: Chrome 37+, Firefox 98+, Safari 15.4+ Arrow key navigation: native to select, details, dialog Element.focus(): all browsers
Real-World Use Case A SaaS dashboard rebuilt their custom dropdown component with native <select> and added :focus-visible rings everywhere. Keyboard-only user testing showed task completion time dropped from 4.2 minutes to 1.8 minutes — a 2.3× speedup that benefited power users (who increasingly use keyboard shortcuts) as much as users with disabilities.
