WCAG Basics

The Web Content Accessibility Guidelines (WCAG) 2.1 and 2.2 are the global standard for accessible web content. Built on four POUR principles, three conformance levels, and dozens of testable success criteria — here are the ones every HTML author must know.

1 What is WCAG?

The Web Content Accessibility Guidelines are published by the W3C's Web Accessibility Initiative (WAI). They are referenced by accessibility laws worldwide, including the Americans with Disabilities Act (US), the European Accessibility Act (EU), and equivalents in Canada, Australia, Japan, and Israel.

  • WCAG 2.0 (2008) — the original, still the legal baseline in many jurisdictions
  • WCAG 2.1 (2018) — added 17 new success criteria, mostly mobile and cognitive
  • WCAG 2.2 (2023) — added 9 more, including focus appearance and target size
  • WCAG 3.0 — in draft; introduces a new scoring model. Not yet ready for production.
Pro Tip Most laws and policies today require WCAG 2.1 Level AA. That's the practical target. Level A is the bare minimum (and not enough). Level AAA is ideal but not required, and some AAA criteria conflict with each other so a page can't be fully AAA.

2 The POUR Principles

Every WCAG success criterion falls under one of four principles. An accessible site must be:

Perceivable

Users must be able to perceive the content — through sight, hearing, or touch. Alt text, captions, sufficient contrast.

Operable

Users must be able to operate the interface — by keyboard, voice, switch, or any device. No mouse-only interactions.

Understandable

Content and operation must be understandable. Plain language, predictable navigation, error prevention.

Robust

Content must work across browsers and assistive tech. Valid HTML, proper ARIA, compatibility with screen readers.

3 Conformance Levels A / AA / AAA

Each success criterion is assigned a level indicating its priority and impact.

LevelMeaningLegal requirement
AMinimum — without this, assistive tech often can't use the page at allRequired by all laws referencing WCAG
AAStandard — removes major barriers for users with disabilitiesMost laws require Level AA conformance
AAAExceptional — not required, and not all criteria can be met simultaneouslyOnly for sites serving specialized audiences

Conformance is per-page. A site can claim "WCAG 2.1 AA" only if every page meets every Level A and AA criterion.

4 A 1.1.1 Non-text Content

All non-text content (images, icons, charts, CAPTCHAs) must have a text alternative that serves the equivalent purpose.

✗ Fails 1.1.1

<img src="logo.png">
<img src="chart.png" alt="image">
<img src="spacer.gif" alt="a transparent pixel
     that is one by one in size and used for
     spacing">
<button><img src="x.png" alt=""></button>

✓ Passes 1.1.1

<img src="logo.png" alt="Acme — home">
<img src="chart.png"
     alt="Bar chart: revenue grew 40%
     from $2M in 2022 to $2.8M in 2024">
<img src="spacer.gif" alt="">
<button aria-label="Close">
  <img src="x.png" alt="">
</button>

Rules for alt text

  • Informative images: concise description of what the image conveys
  • Decorative images: alt="" (empty alt — screen readers skip them)
  • Functional images (buttons, links): describe the action — "Search", "Close"
  • Charts/diagrams: brief summary, link to a full data table for detail
  • CAPTCHAs: provide an audio alternative

5 A 1.3.1 Info and Relationships

Information and relationships conveyed visually (headings, lists, tables, form labels) must be programmatically determinable — that means using the right HTML elements, not <div> with styling.

✗ Visual only

<div class="form-row">
  <span class="label">Email</span>
  <input type="text">
</div>
<div class="heading-1">Welcome</div>
<div class="list-item">Apples</div>
<div class="list-item">Oranges</div>

Screen reader sees nothing meaningful.

✓ Programmatic

<div>
  <label for="email">Email</label>
  <input type="email" id="email">
</div>
<h1>Welcome</h1>
<ul>
  <li>Apples</li>
  <li>Oranges</li>
</ul>

Screen reader announces all relationships.

Pro Tip The single biggest win for 1.3.1: use real HTML form controls, real <label> elements, real <fieldset>/<legend> groups, real <th scope> in tables, real <ul>/<ol> for lists. Rebuilding these with divs + ARIA almost always misses something.

6 AA 1.4.3 Contrast (Minimum)

Text must have a contrast ratio of at least 4.5:1 against its background (3:1 for large text ≥ 18pt or 14pt bold, and for UI components like icons and form borders under 1.4.11).

Text sizeLevel AALevel AAA
Normal text (< 18pt)4.5:17:1
Large text (≥ 18pt or 14pt bold)3:14.5:1
UI components & graphics3:1 (1.4.11)Not specified

Test with the WebAIM Contrast Checker or the built-in contrast checker in browser DevTools. Common failures:

  • Light gray text on white (often "#888 on #fff" = 4.48:1 — barely fails)
  • Placeholder text with insufficient contrast
  • Disabled inputs — exempt from 1.4.3, but must meet 1.4.11 if they're still important
  • Link text that doesn't differ enough from surrounding body text
Common Mistake Styling placeholder text in #999 on white. That's 2.85:1 — fails Level AA. Either darken it to at least #767676 (4.54:1) or move the label above the input and remove the placeholder.

7 A 2.1.1 Keyboard

All functionality must be operable from the keyboard. No mouse-only interactions. If you can do it with a mouse, you must be able to do it with Tab, Shift+Tab, Enter, Space, and arrow keys.

This is the most commonly violated Level A criterion. Examples of failures:

  • A dropdown menu that only opens on mouseover
  • A slider built with <div onmousedown> instead of <input type="range">
  • A modal dialog that doesn't trap focus — Tab escapes to the background
  • A custom calendar widget with no keyboard navigation
  • An onclick handler on a <div> (not keyboard-accessible)

✗ Mouse-only

<div class="menu-item"
     onmouseover="showSubmenu()"
     onclick="navigate()">
  Products
</div>

✓ Keyboard-accessible

<button aria-haspopup="true"
        aria-expanded="false"
        aria-controls="submenu"
        onfocus="showSubmenu()">
  Products
</button>
Real-World Use Case A university's course registration portal rebuilt their custom date picker (a complex <div> grid) with a native <input type="date">. Keyboard-only users went from "impossible to register" to fully independent. The cost: 2 hours of engineering. The benefit: 14% of students could now use the system without help.

8 AA 2.4.6 Headings and Labels

Headings and labels must be descriptive — not "Click Here" or "Read More". The text should make sense out of context (which is how screen reader users navigate via headings list).

✗ Vague

<a href="/blog/post-123">Read more</a>
<a href="/cart">Click here</a>
<h2>Section 1</h2>
<h2>More Information</h2>

✓ Descriptive

<a href="/blog/post-123">
  Read: Sourdough Hydration Guide
</a>
<a href="/cart">View cart (3 items)</a>
<h2>What Hydration Means</h2>
<h2>Bread Flour vs All-Purpose</h2>
Pro Tip When you have multiple "Read more" links on a page (common in blog indexes), use aria-label to make each unique: <a href="/blog/1" aria-label="Read more: Sourdough Hydration Guide">Read more</a>. Screen readers announce the aria-label, sighted users see the short text.

9 A 4.1.2 Name, Role, Value

For every user interface component (links, buttons, form fields, custom widgets), the name, role, and state must be programmatically determinable. Native HTML provides this automatically; custom widgets need ARIA.

What this means in practice

PropertyNative HTMLCustom widget
NameText content or <label>Use aria-label or aria-labelledby
RoleImplicit (button, link, checkbox)Use role="button", role="checkbox", etc.
StateAttributes like checked, disabled, expanded on <details>Use aria-checked, aria-disabled, aria-expanded
Valuevalue on inputsUpdate via JS, expose with aria-valuenow

✗ Div with click handler

<div class="btn" onclick="toggle()">
  ☰ Menu
</div>

No role, no name, no state. Screen reader: nothing.

✓ Native button (best)

<button type="button"
        aria-expanded="false"
        aria-controls="menu"
        onclick="toggle()">
  Menu
</button>

Or, if div is required, add role and tabindex.

10 Common Mistakes

Using <div> for interactive elements

Loses all the built-in keyboard, role, and state semantics. Use <button>, <a>, <input> instead.

Empty or missing alt attributes

An <img> without alt at all is worse than alt="" — screen readers read the filename.

Placeholder-only form labels

Placeholders disappear on focus and have low contrast. Use real <label> elements.

Color contrast "looks fine"

Human perception is unreliable. Always test with a contrast checker — there's one in every browser's DevTools.

Heading levels for styling

Using <h4> because it's the right size breaks the page outline. Use CSS, not heading choice, for sizing.

"Click here" link text

Out of context, it means nothing. Make every link text describe the destination.

11 Exercise

Exercise: Audit a Login Form

Below is a login form. Identify each WCAG failure by criterion number, and rewrite the markup to pass.

<div class="login">
  <h3>Login</h3>
  <div class="field">
    <span class="placeholder-text">Email</span>
    <input type="text" id="email">
  </div>
  <div class="field">
    <span class="placeholder-text">Password</span>
    <input type="password" id="pwd">
  </div>
  <div class="btn" onclick="submit()">
    Submit
  </div>
  <div class="error" style="color:#999">
    Invalid email or password.
  </div>
</div>

Identify failures:

  • <h3> with no <h1>/<h2> above it (1.3.1)
  • No <label> elements (1.3.1, 3.3.2)
  • Placeholder-as-label — disappears on focus (3.3.2)
  • <div onclick> instead of <button> (4.1.2, 2.1.1)
  • Gray #999 error text on white (1.4.3 — 2.85:1 ratio)
  • Error not associated with the input (3.3.1, 4.1.3)

Rewrite the form to pass Level AA.

12 Support & Testing

WCAG 2.0: adopted as ISO/IEC 40500:2012 WCAG 2.1: referenced by ADA, Section 508, EN 301 549 WCAG 2.2: current W3C recommendation (since Oct 2023) All modern browsers: render and expose semantics per WCAG

Testing tools

  • axe DevTools — browser extension, automated WCAG audits (Chrome, Firefox)
  • WAVE — WebAIM's visual audit at wave.webaim.org
  • Lighthouse Accessibility audit — built into Chrome DevTools
  • WebAIM Contrast Checker — hex codes to ratios with pass/fail
  • NVDA / VoiceOver / JAWS — actual screen reader testing (see Screen Readers file)
  • Keyboard-only testing — unplug your mouse, try to use the site
Real-World Use Case A US-based e-commerce company faced an ADA lawsuit in 2022 over an inaccessible checkout. After a 6-month remediation to WCAG 2.1 AA, they not only settled the suit but saw a 17% increase in completed checkouts across all users — accessibility improvements benefit everyone, especially mobile and situational users.
