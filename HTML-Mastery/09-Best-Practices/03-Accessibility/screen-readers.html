Screen Reader Testing

NVDA, JAWS, VoiceOver, TalkBack, and Orca turn HTML into spoken words. Knowing how each announces your markup — and how to test without a screen reader — closes the gap between "passes axe" and "actually usable".

1 Why Test with Screen Readers?

Automated tools (axe, Lighthouse, WAVE) catch maybe 30% of accessibility issues. The rest — incorrect reading order, confusing announcements, broken live regions, missing context — only surface when you actually use the page with a screen reader.

Screen readers are not browsers. They're separate applications that sit on top of the browser's accessibility API and re-speak the DOM. Different screen readers interpret the same HTML differently. A page that works in NVDA may break in VoiceOver.

Pro Tip You don't need every screen reader. Pick one primary (NVDA on Windows is free and represents ~40% of users) and one secondary (VoiceOver on macOS for Mac users). Test on those two, then do spot-checks on JAWS before major releases.

2 NVDA (Windows, Free)

NVDA (NonVisual Desktop Access) is the most widely used screen reader among accessibility professionals — and it's free, open-source, and developed by NV Access. Runs on Windows.

Install and start

  1. Download from nvaccess.org
  2. Run the installer — you can use it as a portable app or install it
  3. Press Ctrl + Alt + N to launch (or use the desktop shortcut)
  4. NVDA will start speaking immediately

Essential shortcuts

Insert + QQuit NVDA
Insert + SStop speech
Insert + TRead window title

Pro Tip In browse mode, NVDA reads the page like a document (arrow keys navigate, single-letter shortcuts work). In focus mode, NVDA passes keys to the application (needed for complex widgets). Press Insert + Space to toggle. NVDA usually beeps when switching automatically.

3 JAWS (Windows, Paid)

JAWS (Job Access With Speech) by Freedom Scientific is the dominant screen reader in corporate and government environments. It's expensive (~$95/year subscription or ~$1,200 perpetual), but the most-used screen reader in employment contexts.

Why test in JAWS?

  • Government contracts and enterprise clients often mandate JAWS compatibility
  • JAWS has some unique behaviors not matched by NVDA (e.g. virtual PC cursor mode, custom scripts)
  • JAWS users have specific expectations for app-like behavior

Essential shortcuts overlap with NVDA: H for next heading, Tab for next control, Insert+F7 for elements list. JAWS uses the Insert key as the "JAWS key" (also called the "virtual buffer modifier").

Real-World Use Case A B2B SaaS company ignored JAWS testing because their internal users used NVDA. A Fortune 100 prospect evaluated the product with their corporate-standard JAWS 2024 and found a focus-trap failure in the date picker — costing a $180k contract. JAWS testing is now part of their QA gate.

4 VoiceOver (macOS/iOS, Free)

VoiceOver is built into every Mac, iPhone, and iPad. It's the only major screen reader for macOS, and the dominant one on mobile (after TalkBack). Free, no install needed.

On macOS

  1. Press Cmd + F5 to toggle VoiceOver on/off
  2. Use the VoiceOver modifier: Control + Option (or Caps Lock)
  3. Press VO + Right Arrow to move to the next item
  4. Press VO + Left Arrow to move backward
  5. Press VO + Shift + Down Arrow to enter a "VO cursor group" (like a list)

On iOS

  1. Settings → Accessibility → VoiceOver → On
  2. Tap once to focus an item (VoiceOver speaks it)
  3. Double-tap anywhere to activate the focused item
  4. Swipe right/left to move to next/previous element
  5. Two-finger flick up to read from top of screen
Pro Tip VoiceOver on iOS is the easiest way to do quick mobile screen reader testing. Turn it on, navigate your site, find the issues. Many users with motor disabilities also use VoiceOver on iOS — testing here catches real-world issues that desktop testing misses.

5 TalkBack (Android)

TalkBack is Android's built-in screen reader. Free, included with all Android devices. Behavior is similar to iOS VoiceOver — tap to focus, double-tap to activate, swipe to navigate.

Enable

  1. Settings → Accessibility → TalkBack → On
  2. Or: hold both volume keys for 3 seconds (on Android 12+)

Gestures

6 Orca (Linux)

Orca is the screen reader for Linux desktops (GNOME, Mate). Free and open-source, maintained by the GNOME project. Less common in enterprise but relevant for users on Linux.

Install via your distro's package manager (e.g. sudo apt install gnome-orca on Ubuntu). Launch with Super + Alt + S. Keyboard shortcuts use the Insert or Caps Lock modifier — similar to NVDA.

Orca is most useful if you're testing accessibility for an audience that includes Linux users (e.g. developer tools, open-source projects).

7 What Screen Readers Announce

Screen readers translate the accessibility tree (a cleaned-up version of the DOM) into speech. Here's what they say for common HTML patterns:

HTMLNVDA announcement
<h1>Welcome</h1>"Welcome, heading level 1"
<a href="/">Home</a>"Home, link"
<button>Submit</button>"Submit, button"
<img src="logo.png" alt="Acme">"Acme, graphic"
<img src="x.png" alt="">(silence — decorative)
<img src="x.png">"x dot png, graphic" (filename — bad)
<input type="text" id="e"><label for="e">Email</label>"Email, edit, blank"
<input type="checkbox">"checkbox, not checked"
<nav aria-label="Main">...</nav>"Main, navigation, landmark"
<ul><li>A</li><li>B</li></ul>"List, 2 items. Bullet 1: A. Bullet 2: B."
<select><option>A</option></select>"Combo box, A, collapsed"
<table> with proper <th scope>"Table with 3 rows and 2 columns. Row 1, column 1, [th text], ..."
Common Mistake Building custom UI without testing what the screen reader announces. A <div onclick> with no role announces as "Click here" with no element type — totally useless. Always test what NVDA/JAWS/VoiceOver actually say.

8 Live Regions

Dynamic content updates (toasts, sports scores, chat messages, form errors) need to be announced without focus moving. Use aria-live for this:

<!-- Toast: announced when it appears -->
<div role="status" aria-live="polite">
  <!-- JS injects: "Item added to cart" -->
</div>

<!-- Critical alert: interrupts current speech -->
<div role="alert" aria-live="assertive">
  <!-- JS injects: "Connection lost" -->
</div>
ValueBehaviorUse case
aria-live="polite"Announces when screen reader is idleToasts, status updates, non-critical errors
aria-live="assertive"Interrupts current speech immediatelyCritical alerts, validation errors blocking action
aria-live="off"Doesn't announce (default)Static content

Shortcut roles:

  • role="status" = polite live region
  • role="alert" = assertive live region
  • role="log" = chat log, polite, new entries announced
  • role="timer" = assertive, for countdowns
Pro Tip The live region element must exist in the DOM before its content changes — otherwise screen readers don't pick it up. Pre-render an empty <div role="status">, then update its textContent later.

9 Testing Without a Screen Reader

You can't always boot NVDA or borrow a Mac. These browser extensions simulate (imperfectly) what screen readers experience:

Chrome screen reader

ChromeOS includes "ChromeVox" — installable as an extension on Chrome desktop for free. Limited but useful for quick checks.

Accessibility Insights for Web

Microsoft's browser extension. Visualizes the accessibility tree, tab order, and automated issues. Free.

axe DevTools

Deque's automated audit. Doesn't simulate screen reader, but catches the missing alts, roles, and contrast issues that break screen reader UX.

Chrome DevTools → Accessibility tree

Built into Chrome. View → Developer Tools → More tools → Accessibility. Shows the tree the screen reader actually reads.

Safari Accessibility Inspector

Built into macOS Safari. Develop → Show Accessibility Inspector. See VoiceOver's view of your DOM.

WebAIM WAVE

Browser extension + web service. Visual overlay of accessibility issues. Not a screen reader but quick sanity check.

Common Mistake Treating these as substitutes for screen reader testing. They're complements — they help find issues, but they don't tell you how the page actually sounds. Real screen reader testing is irreplaceable.

10 Testing Workflow

  1. Run automated checks first — axe, Lighthouse, WAVE. Fix all reported issues.
  2. Keyboard test — Tab through the whole page. See the keyboard-nav file in this section.
  3. Screen reader test with NVDA (or VoiceOver if on Mac):
    • Read from top of page — verify the order makes sense
    • Use the headings list (Insert + F7) — verify every section is there and labeled
    • Use the landmarks list — verify main, nav, footer are present
    • Tab through interactive elements — verify each announces a name and role
    • Submit a form with errors — verify errors are announced (live region)
    • Open a modal — verify focus traps and the dialog is announced
  4. Mobile test — VoiceOver on iOS, TalkBack on Android
  5. JAWS spot-check — before major releases, run through key flows on JAWS
  6. Test with real users — at least quarterly, with users who rely on screen readers daily
Pro Tip Test on the screen reader your users actually use. If your audience is government employees, that's JAWS. If it's general public, that's NVDA + VoiceOver. Survey platforms like WebAIM's annual Screen Reader Survey tell you what to prioritize.

11 Common Mistakes

Assuming "passes axe" = accessible

Automated checks catch ~30% of issues. Live regions, reading order, and confusing announcements require manual screen reader testing.

Skipping mobile screen readers

NVDA-only testing misses VoiceOver/TalkBack quirks. Mobile users are a growing majority.

Adding aria-live without pre-rendering the container

Live region must exist in DOM before content updates. Dynamically inserting it doesn't work.

Over-announcing

Marking everything as aria-live="assertive" interrupts every action. Use polite for almost everything.

Testing only with mouse

Most screen reader users don't use a mouse. Test purely via keyboard commands.

Forgetting headings list

Screen reader users navigate via the headings list (Insert+F7). If your headings are wrong, they can't find anything.

12 Exercise

Exercise: Test a Real Page with NVDA

If you're on Windows, install NVDA and perform a complete screen reader test on any news article (e.g. one from a major news site). Otherwise, use VoiceOver on Mac or your platform's equivalent.

Steps:

  1. Open the article in your browser
  2. Launch the screen reader
  3. From the top of the page, navigate using arrow keys — note the reading order
  4. Use the headings list (Insert+F7) — list every heading and its level
  5. Use the landmarks list — note which landmarks are present
  6. Tab through interactive elements (links, buttons) — verify each announces a meaningful name and role
  7. Submit the comments form with empty fields — verify the error is announced via live region

Deliverable: A short report listing what worked, what didn't, and which WCAG criteria each failure violated.

Browser Support

Real-World Use Case A travel booking site ran their first full screen reader audit (NVDA + VoiceOver) and found that their date picker announced as "clickable, clickable, clickable" with no dates or context. After rebuilding with a native <input type="date"> and ARIA labels, booking completion by screen reader users went from 6% to 71% — making the site usable for a population that had previously been excluded.
