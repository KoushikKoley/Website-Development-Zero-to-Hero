The <label> Element

The single most important element for form accessibility. A <label> gives every input a readable name, makes the click target larger, and unlocks screen-reader announcements. Skip labels and your form is unusable for keyboard, mobile, and assistive-tech users.

1 Why labels matter

Without a label, an input is anonymous. A screen reader announces "edit text" with no context. Mobile users see a small target. Click-targets shrink. The form becomes harder to use for everyone — and impossible for assistive-tech users.

A <label> element fixes all of this:

  • Accessible name: Screen readers announce the label text when the input is focused.
  • Larger click target: Clicking the label focuses the input — better for users with motor difficulties.
  • Visual clarity: Users see what each field is for.
  • Browser autofill: Password managers and autofill engines rely on labels to map fields to data.
Common mistake Using placeholder in place of a label. The placeholder disappears on input, has poor contrast by default, and may not be announced by screen readers. Always include a real <label>.

2 Explicit association (for="id")

The most common pattern: a separate <label> element with a for attribute matching the input's id:

<label for="email">Email address</label>
<input type="email" id="email" name="email" required>

Best for:

  • Labels that need to appear above (or beside) the input
  • Forms with consistent layout (CSS grid / flex)
  • Situations where the label text includes other elements (icons, links)
Explicit label demo — click "Email address" to focus the input

3 Implicit association (wrapping)

Wrap the input inside the <label>. The association is automatic — no for / id needed:

<label>
  Email address
  <input type="email" name="email" required>
</label>

<!-- Or with the label text after the input (checkboxes/radios) -->
<label><input type="checkbox" name="agree" required> I accept</label>

Best for:

  • Checkboxes and radios (text appears right of the control naturally)
  • Layouts where label and input are tightly coupled
  • Avoiding the overhead of id management for many fields

Pro tip Many teams prefer explicit labels for consistency: every input has an id anyway (useful for anchors, JS hooks), and the for/id pattern is visually clear in source.

5 Clicking label focuses input

When a label is properly associated, clicking anywhere on the label text focuses (or toggles) the input. This makes the click target much larger — a huge UX win, especially on mobile.

Click target demo — click the text, not the input
Pro tip For checkboxes and radios, this is especially valuable — the visual checkbox is only ~16px, but the label might be 200px+ of clickable text. Use implicit labels for these to maximize the click area.

6 Multiple labels (anti-pattern)

Technically, multiple <label> elements can reference the same input via for. The spec allows it; the result is unpredictable — screen readers may pick only the first, or read them out of order.

<!-- AVOID: multiple labels per input -->
<label for="email">Email</label>
<input type="email" id="email" name="email">
<label for="email">(required for account creation)</label>

<!-- BETTER: single label with helper text via aria-describedby -->
<label for="email">Email</label>
<input type="email" id="email" name="email"
       aria-describedby="email-hint">
<small id="email-hint">Required for account creation</small>
Common mistake Multiple labels per input cause inconsistent screen-reader behavior. Use one label per input, plus aria-describedby for additional context, hints, or error messages.

7 Styling labels

Labels are normal block elements — style them freely. Common patterns:

/* Label above input */
label { display: block; font-weight: 500; margin-bottom: 4px; }

/* Label beside input (form-row pattern) */
.form-row { display: grid; grid-template-columns: 150px 1fr; gap: 12px; align-items: center; }
.form-row label { text-align: right; }

/* Inline label for checkboxes */
label.inline { display: inline-flex; align-items: center; gap: 6px; }

/* Required indicator */
label .required::after { content: " *"; color: var(--warn); }

8 Required indicator patterns

Marking required fields visually is good UX, but the indicator itself must be accessible. Patterns:

<!-- Pattern 1: asterisk with sr-only explanation -->
<label for="email">Email <span aria-hidden="true">*</span></label>
<input type="email" id="email" name="email" required>
<span class="sr-only">required</span>

<!-- Pattern 2: word "(required)" -->
<label for="email">Email (required)</label>
<input type="email" id="email" name="email" required>

<!-- Pattern 3: required as part of label text (clearest) -->
<label for="email">Email address (required)</label>
<input type="email" id="email" name="email" required>
Required indicator demo
Common mistake Asterisk alone with no screen-reader text. Screen readers may skip the visual * entirely. Either hide it from AT (aria-hidden="true") and add a sr-only "(required)" text, or include the word "(required)" in the label itself.

9 aria-label vs <label>

Sometimes there's no visible label (icon-only buttons, search inputs in a toolbar). In these cases, use aria-label to provide an accessible name. But prefer a visible <label> whenever possible:

Aspect<label>aria-label
Visible to sighted usersYesNo
Screen-reader supportUniversalUniversal (modern AT)
Click target expansionYes (label click focuses input)No
Best use caseStandard form fieldsIcon-only buttons, search inputs in compact toolbars
TranslationInherits page translationNeeds manual translation if hardcoded
 
<!-- Visible label (preferred) -->
<label for="q">Search</label>
<input type="search" id="q" name="q">

<!-- No visible label (toolbar pattern) -->
<input type="search" name="q"
       aria-label="Search articles"
       placeholder="Search...">
Common mistake Replacing visible labels with aria-label because "it looks cleaner." Visible labels help everyone — sighted users, low-vision users, and users who don't notice the placeholder. Reserve aria-label for genuinely label-free contexts (icon buttons, tight toolbars).

11 Try it yourself

Exercise 1 — Convert placeholder labels Take any form you've built that uses placeholders as labels. Add proper <label> elements (explicit association). Test that clicking the label text focuses the input.
Exercise 2 — Checkbox group Build a "Which topics interest you?" form with 5 checkboxes. Use implicit labels (wrapping) for each. Wrap them in a <fieldset> + <legend> for group labeling.
Exercise 3 — Required indicators Build a registration form with required email, password, and optional phone. Mark required fields with both a visible asterisk (hidden from AT) and an sr-only "(required)" text. Verify with a screen reader that it announces "required."

12 Browser support

13 Real-world use cases

Standard form fields

Explicit for/id labels above inputs — most common pattern.

Checkbox groups

Implicit labels wrapping each checkbox; fieldset for the group.

Search toolbars

Icon-only inputs use aria-label; no visible label.

Settings panels

Labels beside inputs in a grid — common in dashboards.

Multi-language forms

Visible labels translate naturally; aria-label needs manual translation.

Error states

Pair label with aria-describedby pointing at error message element.
