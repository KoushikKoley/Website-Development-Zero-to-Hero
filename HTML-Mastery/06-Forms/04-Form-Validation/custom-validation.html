Custom Validation Patterns

HTML5 covers most validation needs. But real apps need more: async checks (username taken?), debounced input, custom error UI that screen readers announce, and the discipline to never trust the client. Here's the production-grade playbook.

1 Combining HTML5 + JS

Start with HTML5 attributes for everything they can do — required, type="email", pattern, min/max. Then add JavaScript for what HTML5 can't do: async checks, conditional requirements, cross-field comparisons.

<!-- HTML5 handles the basics -->
<label for="username">Username</label>
<input type="text" id="username" name="username"
       pattern="[a-zA-Z0-9_]{3,20}"
       title="3-20 alphanumeric characters or underscores"
       autocomplete="username"
       required>
<div id="username-error" class="error-msg" role="alert"></div>

<script>
  // JS adds: async availability check + custom error UI
  const username = document.getElementById('username');
  const errorEl = document.getElementById('username-error');

  username.addEventListener('input', debounce(checkUsername, 300));

  async function checkUsername() {
    const value = username.value.trim();
    if (!value || !username.checkValidity()) {
      errorEl.textContent = '';
      username.setCustomValidity('');
      return;
    }
    const available = await fetch(`/api/check-username?u=${encodeURIComponent(value)}`)
      .then(r => r.json())
      .then(data => data.available);
    if (available) {
      username.setCustomValidity('');
      errorEl.textContent = '✓ Available';
      errorEl.style.color = 'green';
    } else {
      username.setCustomValidity('That username is taken');
      errorEl.textContent = '✗ Already taken';
      errorEl.style.color = 'red';
    }
  }
</script>

2 When to validate

Validation timing affects UX. Too eager and users see errors while typing; too late and they don't get feedback.

EventWhen it firesBest for
inputEvery keystroke / changeLive character counter, instant visual feedback
changeAfter blur (for text) or selection (for checkboxes)Saving drafts, debounced async checks
blurWhen focus leaves the fieldFinal per-field validation before user moves on
submitForm submission attemptLast-chance full validation
Pro tip Best UX pattern: validate on blur first (gentle), then on input only after the field has been touched. This avoids errors while typing but gives immediate feedback once the user knows there's a problem.

3 Debounced validation

For async checks (network calls), debouncing prevents firing a request per keystroke. Wait until the user pauses typing:

function debounce(fn, delay = 300) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  };
}

username.addEventListener('input', debounce(async (e) => {
  await checkUsernameAvailability(e.target.value);
}, 400));

4 Async validation (server-side checks)

Some checks require server roundtrip: username availability, coupon code validity, address verification. Pattern:

async function checkUsernameAvailability(value) {
  if (!value || value.length < 3) return;  // skip if too short

  // Show checking state
  showStatus('checking');

  try {
    const response = await fetch(`/api/check-username?u=${encodeURIComponent(value)}`);
    const data = await response.json();

    if (data.available) {
      usernameInput.setCustomValidity('');
      showStatus('available');
    } else {
      usernameInput.setCustomValidity('That username is already taken');
      showStatus('taken', 'Already taken');
    }
  } catch (err) {
    // Network error — don't block, just hide status
    console.warn('Username check failed:', err);
    showStatus('unknown');
  }
}
Common mistake Blocking form submission while waiting for async checks. If the network is slow, users can't submit. Better: allow submit, re-validate on server, show errors after submit if needed.

5 Accessible error display

For screen reader users, errors must be both visible and programmatically associated with their fields:

<label for="email">Email</label>
<input type="email" id="email" name="email"
       aria-describedby="email-error"
       aria-invalid="false">
<div id="email-error" role="alert"></div>

<script>
  function showError(input, message) {
    const errorEl = document.getElementById(input.id + '-error');
    errorEl.textContent = message;
    input.setAttribute('aria-invalid', 'true');
  }

  function clearError(input) {
    const errorEl = document.getElementById(input.id + '-error');
    errorEl.textContent = '';
    input.removeAttribute('aria-invalid');
  }
</script>

Three accessibility techniques in play:

  • aria-describedby="email-error" on the input: tells screen readers to read the error element when the input is focused.
  • role="alert" on the error element: tells screen readers to announce the content immediately when it changes (live region).
  • aria-invalid="true" on the input: marks the field programmatically as invalid.
Pro tip Use role="alert" only for errors that appear after user interaction (where you want an immediate announcement). For static instructions that don't change, plain text linked via aria-describedby is enough.

6 Preventing submission

When validation fails, block the form submission:

form.addEventListener('submit', (e) => {
  // Run any pending async checks first
  if (!form.checkValidity()) {
    e.preventDefault();

    // Focus the first invalid field
    const firstInvalid = form.querySelector(':invalid');
    if (firstInvalid) firstInvalid.focus();

    // Show errors for all invalid fields
    form.querySelectorAll(':invalid').forEach(field => {
      showError(field, field.validationMessage);
    });
  }
});

7 Real-world: username availability checker

Putting it all together — a complete username checker with HTML5 validation + debounced async check + accessible error UI:

<label for="username">Username</label>
<input type="text" id="username" name="username"
       pattern="[a-zA-Z0-9_]{3,20}"
       title="3-20 alphanumeric characters or underscores"
       autocomplete="username"
       aria-describedby="username-error username-hint"
       required>
<small id="username-hint">3-20 letters, numbers, or underscores</small>
<div id="username-error" role="alert"></div>

<script>
  const input = document.getElementById('username');
  const errorEl = document.getElementById('username-error');
  let timer;

  input.addEventListener('input', () => {
    errorEl.textContent = '';
    errorEl.style.color = '';
    input.setCustomValidity('');
    input.removeAttribute('aria-invalid');

    clearTimeout(timer);
    const value = input.value.trim();

    // Don't check async if HTML5 validation already fails
    if (!value || !input.checkValidity()) return;

    timer = setTimeout(() => checkAvailability(value), 400);
  });

  async function checkAvailability(value) {
    errorEl.textContent = 'Checking...';
    errorEl.style.color = 'var(--ink-soft)';

    try {
      const res = await fetch(`/api/check-username?u=${encodeURIComponent(value)}`);
      const { available } = await res.json();

      if (available) {
        errorEl.textContent = '✓ Available';
        errorEl.style.color = 'var(--success)';
      } else {
        input.setCustomValidity('That username is taken');
        input.setAttribute('aria-invalid', 'true');
        errorEl.textContent = '✗ Already taken';
        errorEl.style.color = 'var(--warn)';
      }
    } catch (err) {
      errorEl.textContent = '';
    }
  }
</script>

8 The golden rule: always re-validate on server

Client-side validation is for UX only. Users can disable JavaScript, edit HTML via dev tools, or send crafted requests directly to your API. The server must validate every field, every time.

Common mistake Trusting client validation for security. If your server skips validation because "the form already validated client-side," attackers can submit invalid data directly via curl or fetch. Always validate on the server.

9 Common mistakes

MistakeConsequenceFix
Async check on every keystrokeSpams the server, slow UXDebounce with 300-500ms delay
Blocking submit while async check pendingUsers can't submit on slow networksAllow submit; re-validate server-side
Error div without role="alert"Screen readers don't announceAdd role="alert" + aria-describedby
Not clearing errors on inputStale errors persistClear error in input handler
Skipping server-side validationSecurity holesAlways re-validate on server
Setting custom error and forgetting to clearField stuck invalidAlways pair set + clear in input handler
Validating too eagerly while typingFrustrating UX — errors before user is doneValidate on blur first, then on input after touched

10 Try it yourself

Exercise 1 — Debounced email validator Build an email field that, after a 400ms pause in typing, makes a simulated fetch call (use setTimeout) to check if the email is already registered. Show "✓ Available" or "✗ Already registered" with proper aria attributes.
Exercise 2 — Cross-field validation Build a password + confirm-password pair. Use JS to check they match on input; set setCustomValidity("Passwords don't match") on the confirm field if they differ. Clear when they match.
Exercise 3 — Full registration form Combine everything: username (with async availability), email (with async taken-check), password (with strength meter), confirm password. Validate on blur, show errors accessibly, prevent submit if invalid. Test with a screen reader.
