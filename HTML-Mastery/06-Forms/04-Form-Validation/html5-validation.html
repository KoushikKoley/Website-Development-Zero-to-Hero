HTML5 Built-in Validation

HTML5 ships with a complete validation system: required, type="email", pattern, min/max, minlength/maxlength — all enforced by the browser before form submission, plus CSS pseudo-classes for styling valid and invalid fields.

1 How native validation works

When the user submits a form (clicks submit or presses Enter), the browser runs built-in validation before firing the submit event. If any field fails, submission is cancelled and the browser focuses the first invalid field with an error tooltip.

Validation is driven by attributes:

AttributeValidates
requiredField must have a value
type="email"Value matches RFC email format
type="url"Value is an absolute URL
pattern="regex"Value matches the regex (anchored)
min / maxNumeric/date values in range
stepNumeric value is a valid step from min
minlength / maxlengthText length within bounds
Key insight Native validation runs before the submit event — meaning your JS submit handler won't even fire if validation fails. To intercept and customize validation, use the Constraint Validation API (covered in the next lesson).

2 required

Boolean attribute. Field must have a non-empty value. Browser shows "Please fill out this field" on submit attempt with empty value.

<label for="email">Email</label>
<input type="email" id="email" name="email" required>

<!-- Required radio group: at least one must be selected -->
<fieldset>
  <legend>Plan</legend>
  <label><input type="radio" name="plan" value="free" required> Free</label>
  <label><input type="radio" name="plan" value="pro"> Pro</label>
</fieldset>

<!-- Required checkbox (e.g., "accept terms") -->
<label><input type="checkbox" name="agree" required>
  I accept the terms</label>

3 type-based validation

Setting type to email, url, or number triggers automatic format validation:

<!-- Validates against RFC 5322 email format -->
<input type="email" name="email">

<!-- Must be absolute URL (with scheme) -->
<input type="url" name="website">

<!-- Must parse as a number -->
<input type="number" name="qty">
type validation demos — try invalid values then submit
Pro tip The native email validation is intentionally lenient (allows user@localhost). For stricter rules, add pattern. Always re-validate on the server — client validation is for UX, not security.

4 pattern (regex)

JavaScript regular expression the value must match. The regex is auto-anchored (wrapped in ^(?: ... )$) — you don't need ^ and $. Pair with title for a helpful hint in the error tooltip:

<!-- US ZIP code -->
<input type="text" name="zip"
       pattern="[0-9]{5}(-[0-9]{4})?"
       title="5-digit ZIP, optionally with -4 extension">

<!-- Hex color -->
<input type="text" name="hex"
       pattern="#?[0-9a-fA-F]{6}"
       title="Hex color like #ff0080">

<!-- Username (3-20 alphanumeric) -->
<input type="text" name="username"
       pattern="[a-zA-Z0-9_]{3,20}"
       title="3-20 letters, numbers, or underscores">

<!-- Strong password -->
<input type="password" name="password"
       pattern="(?=.*[a-z])(?=.*[A-Z])(?=.*[0-9]).{8,}"
       title="Min 8 chars, with uppercase, lowercase, and number">
pattern demo — try entering invalid patterns

5 min / max / step

For numeric (number, range) and temporal (date, time, etc.) inputs:

<!-- Quantity 1-100, integers only -->
<input type="number" name="qty" min="1" max="100" step="1">

<!-- Price 0+, to nearest cent -->
<input type="number" name="price" min="0" step="0.01">

<!-- Date in 2024 -->
<input type="date" name="when" min="2024-01-01" max="2024-12-31">

<!-- Time, 15-min intervals, 9am-5pm -->
<input type="time" name="appt" min="09:00" max="17:00" step="900">
min / max / step demo — try entering out-of-range values

6 minlength / maxlength

Length constraints on text inputs and textareas. maxlength hard-blocks typing beyond the limit; minlength triggers validation error on submit if too short.

<!-- Username 3-20 chars -->
<input type="text" name="username"
       minlength="3" maxlength="20" required>

<!-- Bio up to 280 chars (Twitter-style) -->
<textarea name="bio" maxlength="280"></textarea>

<!-- Password min 8 chars -->
<input type="password" name="password"
       minlength="8" required>

7 CSS pseudo-classes

Seven pseudo-classes let you style fields based on validation state:

Pseudo-classMatches when
:validField passes validation
:invalidField fails validation
:requiredField has required attribute
:optionalField does not have required
:placeholder-shownField is empty (placeholder visible)
:in-rangeNumeric/date value within min/max
:out-of-rangeNumeric/date value outside min/max
 
input:invalid { border-color: var(--warn); background: #fef2f2; }
input:valid   { border-color: var(--success); }

/* Only show invalid state after user has interacted */
input:not(:placeholder-shown):invalid { border-color: var(--warn); }
input:not(:placeholder-shown):valid   { border-color: var(--success); }

/* Mark required fields visually */
input:required { border-left: 3px solid var(--accent); }

/* Style in-range and out-of-range differently */
input[type="number"]:out-of-range { background: #fef2f2; }
input[type="number"]:in-range     { background: #f0fdf4; }
Pseudo-class demo — required fields get an amber left border; valid/invalid get colored
Common mistake Styling :invalid from page load. Empty required fields are "invalid" immediately, showing red borders before the user has touched anything. Use :not(:placeholder-shown) to only style invalid after typing, or check :focus/:blur states.

8 Browser error UI

Each browser renders validation errors differently:

  • Chrome / Edge: Small tooltip below the field with the error message; focuses the first invalid field.
  • Firefox: Similar tooltip, with a red "drop shadow" around the field.
  • Safari: Focuses the invalid field; shows a tooltip — though Safari historically had weaker error UI.
  • Mobile: On-screen message above the keyboard; focuses the field.

The default error messages are browser-generated and localized to the user's language. You can customize them via the Constraint Validation API (setCustomValidity()) — covered in the next lesson.

Pro tip The title attribute is included in pattern-mismatch tooltips. Set it to a human-readable hint about the expected format: title="5-digit ZIP code".

9 Disabling: novalidate

Two ways to skip native validation:

<!-- Form-level: skip validation for entire form -->
<form action="/save" method="post" novalidate>...</form>

<!-- Button-level: skip validation when this button is clicked -->
<button type="submit" formnovalidate>Save draft</button>

Common use cases:

  • "Save draft" button that saves progress without requiring all fields filled
  • Forms handled entirely via JavaScript with custom validation
  • Multi-step wizards that validate per step, not all at once

11 Try it yourself

Exercise 1 — Registration form Build a signup form: username (3-20 alphanumeric), email, password (8+ with upper/lower/number), and a required "accept terms" checkbox. Use pattern, minlength, and required.
Exercise 2 — Style validation states Use CSS :valid / :invalid to color-code field borders green/red. Use :not(:placeholder-shown) to delay invalid styling until the user types. Add a green checkmark via ::after on valid fields.
Exercise 3 — Save draft button Add two submit buttons to a form. One ("Publish") requires validation; the other ("Save Draft") uses formnovalidate to skip it. Test that the draft button submits even with empty required fields.

13 Real-world use cases

Signup forms

required + pattern on username, type=email, strong password pattern.

Checkout flows

Required fields, ZIP pattern per country, credit card pattern.

Booking systems

min/max on date pickers (no past dates); step on time (15-min slots).

Settings panels

Range sliders with min/max/step for numeric preferences.

Save Draft / Publish

Two submit buttons; one uses formnovalidate.

Survey forms

Required radios grouped in fieldsets; pattern for text answers.
