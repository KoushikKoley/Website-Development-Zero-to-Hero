Numeric & Temporal Inputs

Numbers, dates, and times deserve dedicated input types. The browser provides native pickers, keyboard hints, and validation — but UI differs widely across browsers. Learn when to trust native pickers and when to reach for a custom widget.

1 Numeric & temporal types overview

TypeWhat it collectsFormat submittedNative picker
numberNumeric valuePlain number string ("42" or "3.14")Spinner arrows
rangeNumber within rangePlain number stringSlider
dateCalendar date (no time)YYYY-MM-DDCalendar widget
timeTime of dayHH:MM (24-hour)Time picker

Key insight All temporal types submit fixed-format strings (ISO 8601 variants), not localized text. The browser handles localization in the UI but always sends a parseable, locale-independent string to the server. This is one of HTML5's most underappreciated wins.

2 type="number"

For genuine numeric quantities: quantity, age, price, score. Browser shows spinner arrows (up/down) and validates that the value parses as a number. Mobile shows a numeric keyboard.

<label for="qty">Quantity</label>
<input type="number" id="qty" name="qty"
       min="1" max="100" step="1" value="1">

<label for="price">Price (USD)</label>
<input type="number" id="price" name="price"
       min="0" step="0.01" value="9.99">
type="number" demo — try the arrows
Common mistake Using type="number" for things that look numeric but aren't quantities: ZIP codes (leading zeros stripped), phone numbers (formats vary), credit card numbers (16 digits risk precision loss). Use type="text" with inputmode="numeric" instead.

3 type="range" (sliders)

Renders a horizontal slider. Ideal for imprecise numeric input where the exact value matters less than the rough feel: volume, opacity, brightness, "rate from 1-10."

<label for="volume">Volume: <output for="volume" id="vol-out">50</output>%</label>
<input type="range" id="volume" name="volume"
       min="0" max="100" step="1" value="50"
       oninput="document.getElementById('vol-out').value = this.value">
type="range" demo — drag the slider
Common mistake Sliders show no value by default. Users have no idea what they're picking. Always pair with an <output> element (or visible text) that updates via oninput.

4 type="date"

Calendar date picker. The browser renders a native calendar widget. The submitted value is always YYYY-MM-DD regardless of how it's displayed to the user.

<label for="birthday">Birthday</label>
<input type="date" id="birthday" name="birthday"
       min="1900-01-01" max="2024-12-31">

<!-- Restrict to weekdays only (with JS fallback) -->
<label for="appointment">Appointment (Mon-Fri)</label>
<input type="date" id="appointment" name="appointment"
       min="2024-01-01" max="2024-12-31">
type="date" demo — click the field to open calendar

5 type="time"

Time-of-day picker. Value submitted as 24-hour HH:MM (or HH:MM:SS if step includes seconds). The browser may display it in the user's locale (12-hour with AM/PM) but always submits canonical 24-hour format.

<label for="wake">Wake-up time</label>
<input type="time" id="wake" name="wake" value="07:00">

<!-- Allow second precision -->
<label for="lap-time">Lap time</label>
<input type="time" id="lap-time" name="lap-time" step="1">
type="time" demo

6 type="datetime-local"

Combined date + time picker, without timezone. The submitted value is YYYY-MM-DDTHH:MM (an ISO 8601 "local" datetime string). The browser interprets this as the user's local time — you must decide on the server whether to treat it as UTC or local.

<label for="meeting">Meeting time</label>
<input type="datetime-local" id="meeting" name="meeting"
       min="2024-01-01T00:00" max="2024-12-31T23:59">
type="datetime-local" demo
Common mistake Using type="datetime-local" when you need timezone awareness. The value has no timezone info — if a user in Tokyo and a user in New York both submit "2024-06-15T14:00", they mean different absolute moments. For timezone-aware datetimes, capture the timezone separately (e.g., a separate <select>) or use a custom widget.

7 type="month" and type="week"

Two less-common temporal types:

  • type="month" — collects year + month. Value submitted as YYYY-MM (e.g., 2024-06). Useful for credit card expiration.
  • type="week" — collects ISO week. Value submitted as YYYY-Www (e.g., 2024-W23). Useful for shift scheduling, payroll.
<label for="cc-exp">Card expiration</label>
<input type="month" id="cc-exp" name="cc-exp"
       autocomplete="cc-exp"
       min="2024-01" max="2034-12" required>

<label for="pay-week">Pay week</label>
<input type="week" id="pay-week" name="pay-week" required>
type="month" demo

8 min, max, step

Three attributes constrain numeric and temporal values:

AttributePurposeApplies toEffect
minMinimum allowed valuenumber, range, date/time typesValidation error if below; slider/number can't go lower
maxMaximum allowed valuenumber, range, date/time typesValidation error if above; slider/number can't go higher
stepGranularitynumber, range, date/time typesSpinner increments by step; slider snaps; validation fails on mismatched values
 
<!-- Quantity in dozens -->
<input type="number" name="qty" min="12" max="120" step="12" value="12">

<!-- Price to nearest cent -->
<input type="number" name="price" min="0" step="0.01">

<!-- Time in 15-minute intervals -->
<input type="time" name="slot" min="09:00" max="17:00" step="900">  <!-- 900 sec = 15 min -->

<!-- Slider 0-10 in 0.5 steps -->
<input type="range" name="rating" min="0" max="10" step="0.5">
Pro tip step="any" disables step validation while keeping min/max. Useful for floating-point values where any precision is fine (e.g., scientific measurements).

The submitted value format is identical across browsers — only the UI differs. This is by design: respect the user's platform conventions unless you have a compelling reason not to.

10 Native pickers vs custom widgets

When to use native HTML5 pickers vs a JS library (Flatpickr, react-day-picker, Pikaday, etc.):

Use native whenUse custom when
Basic date/time selection is enoughYou need range selection (start + end on one calendar)
Performance and bundle size matter (no JS)You need blocked-out dates (holidays, blackout)
Mobile UX is critical (native pickers beat custom on touch)You need date+time+timezone all together
Progressive enhancement (works without JS)You need consistent cross-browser UI for branding
Browser autofill integration mattersYou need to restrict to weekdays / custom calendar rules
Pro tip Hybrid approach: use type="date" as the base, then progressively enhance with a JS library if it loaded successfully. Users without JS still get a working native picker. Many libraries detect and respect the input type.

11 Common mistakes

MistakeWhy it's wrongFix
type="number" for ZIP / phone / credit cardLeading zeros stripped, scientific notation for long numbers, spinner UX is oddUse type="text" inputmode="numeric"
Slider with no value displayUsers can't see what they pickedPair with <output> updated via oninput
type="datetime-local" for events across timezonesNo timezone info; ambiguityCapture timezone separately or use custom widget
Skipping min/max on slidersDefault min=0, max=100 may not match intentAlways set explicit min/max/step
Trusting client-side numeric validationUsers can bypass via dev toolsAlways re-validate on the server
Using step="1" for currencyRejects decimal values like 9.99Use step="0.01" (or step="any")

12 Try it yourself

Exercise 1 — Booking form Build a booking form: appointment date (no past dates), time (15-min intervals, 9am-5pm only), and number of guests (1-10). Add proper min, max, step.
Exercise 2 — Live slider Create a slider 0-100 in steps of 5. Use an <output> element that updates as the slider moves. Add a checkbox that toggles between "steps of 5" and "steps of 1" (changing the step attribute dynamically).
Exercise 3 — Date range restriction Create a "start date" and "end date" pair. When the user picks a start date, dynamically set the end date's min attribute to that date (preventing end-before-start).

13 Browser support

type="number" — universal type="range" — universal type="date" — all modern browsers (IE11 partial) type="time" — Chrome, Firefox, Edge, Safari 14.1+ type="datetime-local" — all modern browsers type="month" — Chrome, Edge, Safari desktop; partial elsewhere type="week" — Chrome, Edge, Opera; not Safari/Firefox min / max / step — universal on supported types

type="week" and type="month" have the weakest support; gracefully degrade to type="text" in unsupported browsers (server-side validation must always be present anyway).

14 Real-world use cases

Quantity pickers

E-commerce cart: number input with min=1, max=stock.

Range sliders

Audio volume, image opacity, price filters on search.

Booking systems

Date + time pickers for hotels, flights, appointments.

Credit card forms

type="month" for expiration with autocomplete="cc-exp".

Shift scheduling

type="week" for payroll periods.

Surveys / ratings

Slider 1-10 for satisfaction; step=1 for whole numbers.
