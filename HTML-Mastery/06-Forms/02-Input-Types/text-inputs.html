Text Inputs

HTML has six text-based input types — text, password, email, tel, url, and search — each tuned for a different purpose. Choose correctly and mobile users get the right keyboard, browsers apply built-in validation, and password managers know how to help.

1 Text input types overview

TypePurposeMobile keyboardBuilt-in validation
textGeneric single-line textStandardNone
passwordHidden text (obscured)Standard (often with @/#)None; browser offers to save
emailEmail addressEmail layout (@ key prominent)Validates RFC email format
telPhone numberNumeric dial padNone (use pattern)
urlAbsolute URLURL layout (/, .com keys)Must be absolute URL
searchSearch queryStandard with search icon on EnterNone
Key insight On mobile, picking the right type triggers the right keyboard automatically. Picking the wrong one means users fight with autocorrect, missing keys, and frustration. The type attribute is a UX feature, not just a validation feature.

2 type="text"

The fallback when no specific type applies: name, address line, free text. The default when the type attribute is omitted.

<label for="full-name">Full name</label>
<input type="text" id="full-name" name="full-name"
       autocomplete="name" required>
type="text" demo

3 type="password"

Obscures each character with a dot (•) as the user types. Modern browsers add a "reveal password" eye icon natively. Always pair with the right autocomplete token:

<!-- Login form: existing password -->
<label for="pw-login">Password</label>
<input type="password" id="pw-login" name="password"
       autocomplete="current-password" required>

<!-- Registration form: new password -->
<label for="pw-new">Create password</label>
<input type="password" id="pw-new" name="new-password"
       autocomplete="new-password"
       minlength="8" required>
Common mistake Setting autocomplete="off" on password fields to "prevent saving." Modern browsers ignore it because users have the right to use their password manager. Use proper tokens (current-password vs new-password) to give password managers context.
type="password" demo

4 type="email"

Triggers the email keyboard on mobile (the @ and . keys are prominent). Browser validates the value matches RFC email format on submit — but only when the field has a value (empty passes unless required).

<label for="u-email">Email address</label>
<input type="email" id="u-email" name="email"
       autocomplete="email" required
       placeholder="you@example.com">

<!-- Multiple emails (comma-separated, validated per entry) -->
<label for="invite-emails">Invite emails</label>
<input type="email" id="invite-emails" name="emails" multiple>
type="email" demo — try invalid email then submit
Pro tip The native email validation is intentionally lenient (allows user@localhost and other edge cases). For stricter rules, use pattern. Always re-validate on the server — client validation is for UX, not security.

5 type="tel"

Triggers the numeric dial pad on mobile. Browser does not validate format (phone formats vary globally), so add a pattern for stricter checks:

<label for="phone">US phone</label>
<input type="tel" id="phone" name="phone"
       autocomplete="tel"
       pattern="[0-9]{3}-[0-9]{3}-[0-9]{4}"
       placeholder="555-123-4567"
       required>
type="tel" demo — open on mobile to see dial pad
Key insight Phone numbers are wildly variable internationally. For global apps, use type="tel" with no pattern and let the server validate. For region-specific apps, a strict pattern catches typos.

6 type="url"

Validates that the value is an absolute URL (with scheme like http: or https:). Mobile shows a URL-friendly keyboard. Empty values pass unless required.

<label for="website">Website</label>
<input type="url" id="website" name="website"
       autocomplete="url"
       placeholder="https://example.com">
type="url" demo — "example.com" alone fails validation; needs scheme

7 type="search"

Semantically marks the input as a search field. Some browsers add a "clear" (×) button when text is present, and the Enter key on mobile may show a "Search" label. Behavior is otherwise similar to type="text".

<form action="/search" method="get" role="search">
  <label for="q" class="visually-hidden">Search</label>
  <input type="search" id="q" name="q"
         placeholder="Search docs..."
         enterkeyhint="search">
  <button type="submit">Go</button>
</form>
type="search" demo — note the clear (×) button when typing

8 inputmode

Forces a specific mobile keyboard without changing the input's type or validation. Useful when you want a text input that accepts only digits (e.g., a 6-digit SMS code) but don't want numeric coercion from type="number".

inputmodeKeyboardTypical use
text (default)StandardDefault text
numericNumeric (no decimal)PINs, postal codes, ages
decimalNumeric with .Prices, quantities
telDial pad (*#)Phone-like text
emailEmail (@ and . prominent)Text that should look like email
urlURL layout (/ and .com)Text that should look like URL
searchStandard with search hintSearch-like text
noneSuppress virtual keyboardCustom on-screen keyboards
 
<!-- 6-digit SMS code: numeric keyboard, but stays a text input -->
<label for="otp">Verification code</label>
<input type="text" id="otp" name="otp"
       inputmode="numeric"
       pattern="[0-9]{6}"
       maxlength="6"
       autocomplete="one-time-code"
       required>

Customizes the label of the Enter key on mobile virtual keyboards. Helps users understand what pressing Enter will do:

10 maxlength / minlength

Enforce length constraints on text inputs. maxlength prevents typing beyond the limit; minlength triggers validation error if the value is too short on submit.

<label for="username">Username (3-20 chars)</label>
<input type="text" id="username" name="username"
       minlength="3" maxlength="20" required>

<label for="bio">Bio (max 280 chars)</label>
<textarea id="bio" name="bio" maxlength="280"></textarea>
<small><span data-count>0</span>/280</small>
Common mistake Using maxlength to enforce "strong passwords." A long password is good, but maxlength="20" forces users into weaker passwords. Set a high maxlength="128" for sanity, never a strict low one for passwords.

11 pattern

JavaScript regex (anchored automatically) the value must match. The browser shows a validation error on submit if it doesn't. Pair with title for a hint message:

<label for="zip">US ZIP code</label>
<input type="text" id="zip" name="zip"
       pattern="\d{5}(-\d{4})?"
       title="5-digit ZIP, optionally with -4 extension"
       placeholder="12345 or 12345-6789">

<label for="hex">Hex color</label>
<input type="text" id="hex" name="hex"
       pattern="#?[0-9a-fA-F]{6}"
       title="Hex color like #ff0080">
Pro tip Patterns are anchored (wrapped in ^(?: ... )$) automatically — you don't need ^ and $ in your regex. Use title to explain the expected format; browsers include it in the validation tooltip.

12 placeholder (and why it's not a label)

Shows a hint inside the field when empty. Disappears on focus / input. Often abused as a label — but it is not a substitute for one:

Problem with placeholder-as-labelWhy it matters
Disappears when user starts typingUser can't recall what field they're in mid-form
Often low-contrast grayFails WCAG AA contrast in many designs
Screen readers may not announce itField has no accessible name
Confused with auto-filled valueUsers think placeholder is real data
Browser autofill hides itField becomes unlabeled once filled
 
<!-- BAD: placeholder as label -->
<input type="email" placeholder="Email address" name="email">

<!-- GOOD: visible label + helpful placeholder -->
<label for="email">Email address</label>
<input type="email" id="email" name="email"
       placeholder="you@example.com">
Common mistake Floating-label CSS patterns that show the placeholder text moving above the field on focus can work — but only if there's a real <label> for screen readers. Don't rely on the visual trick for accessibility.

16 Real-world use cases

Login forms

Email + password, autocomplete tokens, password manager integration.

Checkout flows

Email, phone, address — each with proper type + autocomplete.

SMS verification

OTP input with inputmode="numeric" + autocomplete="one-time-code" auto-fills from SMS on iOS/Android.

Site search

type="search" inside a form[role="search"], enterkeyhint="search".

Registration

Password fields with autocomplete="new-password" to disable auto-fill of existing.

Profile edit

Name (autocomplete="name"), website (type="url"), tel — all editable.
