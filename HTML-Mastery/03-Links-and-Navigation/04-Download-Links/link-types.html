Section 3.11 · <link rel>

Link Types — <link rel> in <head>

Most links live in <body>, but the <head> is full of invisible <link> tags that shape performance, SEO, and behavior: stylesheets, icons, canonical URLs, hreflang alternates, preconnect, preload, prefetch, manifest. They're the unsung heroes of the document.

1 What <link rel> Does

The <link> element lives in the <head> and references external resources. The rel attribute (relationship) tells the browser what the resource is for — a stylesheet, an icon, a canonical URL, a performance hint, etc.

<head>
  <!-- Stylesheet -->
  <link rel="stylesheet" href="/css/main.css">

  <-- Favicon -->
  <link rel="icon" href="/favicon.ico">

  <-- Canonical URL for SEO -->
  <link rel="canonical" href="https://example.com/article">

  <-- Preconnect to a third-party origin -->
  <link rel="preconnect" href="https://fonts.googleapis.com">

  <-- Preload a critical font -->
  <link rel="preload" href="/fonts/inter.woff2" as="font" type="font/woff2" crossorigin>

  <-- PWA manifest -->
  <link rel="manifest" href="/manifest.json">
</head>
Pro Tip All <link rel> attributes use the same vocabulary as <a rel> on anchors. The difference: <link> is in the <head> and references document-level resources; <a> is in the <body> and creates visible hyperlinks.

The 20+ recognized rel tokens fall into three categories:

3 stylesheet

The most common rel value — loads a CSS file and applies it to the page.

<link rel="stylesheet" href="/css/main.css">

<-- With media query (loads only when matching) -->
<link rel="stylesheet" href="/css/print.css" media="print">
<link rel="stylesheet" href="/css/mobile.css" media="(max-width: 768px)">

<-- Print + screen combined -->
<link rel="stylesheet" href="/css/responsive.css" media="screen, print">
Pro Tip — Render-Blocking <link rel="stylesheet"> is render-blocking by default — the browser won't paint the page until the CSS loads. For non-critical CSS, use media="print" swap, or load via JS, or use rel="preload" as="style" onload="this.rel='stylesheet'". 
<!-- Lazy-load non-critical CSS without blocking render -->
<link rel="preload" href="/non-critical.css" as="style" onload="this.onload=null;this.rel='stylesheet'">
<noscript><link rel="stylesheet" href="/non-critical.css"></noscript>

4 icon (Favicon)

Specifies the favicon — the small icon shown in browser tabs, bookmarks, and home-screen shortcuts.

<!-- Modern SVG favicon (preferred for high-DPI) -->
<link rel="icon" href="/favicon.svg" type="image/svg+xml">

<-- PNG favicons for various sizes -->
<link rel="icon" type="image/png" sizes="32x32" href="/favicon-32.png">
<link rel="icon" type="image/png" sizes="16x16" href="/favicon-16.png">

<-- Apple touch icon (home screen on iOS) -->
<link rel="apple-touch-icon" sizes="180x180" href="/apple-touch-icon.png">

<-- Web app manifest icon (Android/Chrome home screen) -->
<link rel="manifest" href="/manifest.json">

<-- Legacy .ico fallback -->
<link rel="shortcut icon" href="/favicon.ico">

<-- Theme color for mobile browser chrome -->
<meta name="theme-color" content="#2563eb">
Pro Tip For best cross-device support, provide: SVG (high-DPI), 32×32 PNG (standard), 180×180 PNG (Apple touch), 192×192 + 512×512 PNG (in manifest.json for Android), and a .ico fallback. Tools like realfavicongenerator.net generate them all.

5 canonical

Tells search engines: "this URL is the master version of this page". Prevents duplicate-content penalties when the same content is accessible at multiple URLs (e.g., with/without trailing slash, with/without query params, www vs non-www).

<!-- Always use an absolute URL -->
<link rel="canonical" href="https://example.com/blog/css-grid">

<-- On paginated lists, canonicalize each page to itself -->
<link rel="canonical" href="https://example.com/blog?page=2">

<-- On print/mobile variants, point to the desktop version -->
<link rel="canonical" href="https://example.com/blog/css-grid">
<!-- (don't point every variant to the first page — that hides subsequent content from Google) -->
Common Mistake — Self-Canonicalization Done Wrong Every page should canonicalize to itself (or its master version), not to the homepage. Don't use rel="canonical" to consolidate distinct content pages — Google will just ignore the directive. Use 301 redirects for true duplicates.

6 alternate & hreflang

Tells search engines about alternative versions of the page: translations, mobile/desktop, RSS feeds.

Translations (hreflang)

<!-- English (canonical) -->
<link rel="alternate" hreflang="en" href="https://example.com/en/about">

<-- French -->
<link rel="alternate" hreflang="fr" href="https://example.com/fr/a-propos">

<-- Spanish -->
<link rel="alternate" hreflang="es" href="https://example.com/es/acerca">

<-- Simplified Chinese -->
<link rel="alternate" hreflang="zh-Hans" href="https://example.com/zh-Hans/about">

<-- x-default: the default for users whose locale doesn't match -->
<link rel="alternate" hreflang="x-default" href="https://example.com/en/about">

Google uses these to serve the right language version in search results.

RSS / Atom Feeds

<link rel="alternate" type="application/rss+xml"
      title="Example Blog RSS Feed"
      href="/feed.xml">

<link rel="alternate" type="application/atom+xml"
      title="Example Blog Atom Feed"
      href="/atom.xml">

Browsers display an RSS icon in the address bar when they find these.

Mobile / Desktop Variants

<!-- On desktop page, link to mobile -->
<link rel="alternate" media="only screen and (max-width: 768px)"
      href="https://m.example.com/page">

<-- On mobile page, link back to desktop -->
<link rel="canonical" href="https://www.example.com/page">
Common Mistake — Incomplete hreflang If you list French and Spanish alternates but no English, Google can't pair them. Always include the canonical version itself + an hreflang="x-default" fallback. Test with Google Search Console's International Targeting report.

7 preload

High-priority fetch for resources needed on the current page. Use it to start downloading critical assets earlier than the browser would otherwise discover them.

<!-- Preload a critical font -->
<link rel="preload" href="/fonts/inter.woff2" as="font" type="font/woff2" crossorigin>

<-- Preload a critical CSS file (loaded but not yet applied) -->
<link rel="preload" href="/css/critical.css" as="style">

<-- Preload a hero image -->
<link rel="preload" href="/img/hero.webp" as="image">

<-- Preload a JS module -->
<link rel="modulepreload" href="/js/app.js">

<-- Preload a video -->
<link rel="preload" href="/video/intro.mp4" as="video">

The as attribute is required — it tells the browser the resource type so it can set proper headers and use the right cache.

as valueResource Type
audioAudio files
documentIframes
embedPlugin embeds
fetchfetch() or XHR
fontWeb fonts
imageImages
objectPlugin objects
scriptJS files
styleCSS files
trackWebVTT files
videoVideo files
workerWeb workers
Common Mistake — Preload Everything Preloading too many resources can backfire: it competes for bandwidth with render-critical requests. Reserve preload for things the page actually needs ASAP — the LCP image, the main font, critical CSS. Measure with Lighthouse or WebPageTest first.

8 prefetch

Low-priority fetch for resources likely needed on the next navigation. The browser fetches the resource in idle time and caches it.

<!-- Prefetch the next likely page -->
<link rel="prefetch" href="/next-article.html">

<-- Prefetch an image likely to appear next -->
<link rel="prefetch" href="/img/next-hero.webp" as="image">

<-- Prefetch a JS bundle for the next page -->
<link rel="prefetch" href="/js/checkout.js" as="script">

Speculation Rules (Modern Alternative)

Chrome now supports <script type="speculationrules"> for smarter prefetching and even prerendering of likely-next pages:

<script type="speculationrules">
{
  "prefetch": [
    {"urls": ["/next-article.html", "/pricing.html"]}
  ]
}
</script>

<-- Or prerender (full page render in background) -->
<script type="speculationrules">
{
  "prerender": [
    {"where": {"href_matches": "/next-article.html"}}
  ]
}
</script>
Pro Tip Use prefetch for likely-next pages (links visible in the viewport, "next" pagination). It can give near-instant page loads. But be mindful of mobile data costs — some users pay per MB. Consider Save-Data header detection.

9 preconnect & dns-prefetch

Warm up the connection to a third-party origin before you actually fetch from it. Saves DNS lookup + TCP handshake + TLS negotiation — can save 100-300ms.

<!-- Full preconnect (DNS + TCP + TLS) -->
<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>

<-- DNS-only prefetch (lighter; for low-priority origins) -->
<link rel="dns-prefetch" href="https://analytics.example.com">
<link rel="dns-prefetch" href="https://cdn.example.com">
TokenWhat It DoesWhen to Use
preconnectDNS + TCP + TLS handshakeOrigins you'll fetch from soon (fonts, CDN, API).
dns-prefetchDNS lookup onlyOrigins you might fetch from (analytics, tracking pixels).
Common Mistake — Too Many preconnects Each open connection costs browser resources. Limit to 3-4 critical origins. Beyond that, you're wasting memory and may slow down other fetches.

10 manifest (PWA)

Links to a Web App Manifest JSON file — enables "Add to Home Screen" and PWA installation.

<link rel="manifest" href="/manifest.json">

The manifest itself:

{
  "name": "Acme App",
  "short_name": "Acme",
  "description": "Manage your Acme widgets.",
  "start_url": "/",
  "display": "standalone",
  "background_color": "#ffffff",
  "theme_color": "#2563eb",
  "icons": [
    { "src": "/icons/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png" },
    { "src": "/icons/icon-maskable.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
  ]
}
Pro Tip For full PWA installability, also serve a Service Worker (registered via JS). The manifest alone enables "Add to Home Screen", but a service worker enables offline functionality — both are required for the install prompt.

11 search (OpenSearch)

Tells browsers your site has a search engine they can add to the browser's search bar.

<link rel="search"
      type="application/opensearchdescription+xml"
      title="Example Search"
      href="/opensearch.xml">

The OpenSearch description XML:

<?xml version="1.0" encoding="UTF-8"?>
<OpenSearchDescription xmlns="http://a9.com/-/spec/opensearch/1.1/">
  <ShortName>Example Search</ShortName>
  <Description>Search example.com</Description>
  <Url type="text/html"
       template="https://example.com/search?q={searchTerms}"/>
</OpenSearchDescription>

13 Try It Yourself

Exercise 1 — Complete <head> Build a page with a complete <head>: charset, viewport, title, description, favicon (multiple sizes), stylesheet, canonical, theme-color, and Open Graph tags. Verify with a HTML validator and Lighthouse SEO audit.
Exercise 2 — hreflang Setup Build a multilingual page with three translations (English, French, Spanish). Add rel="alternate" hreflang="..." for each (including x-default). Validate with Google Search Console's International Targeting.
Exercise 3 — Performance Hints Add preconnect for two origins (e.g., fonts.googleapis.com and a CDN). Add preload for a hero image and a critical font. Measure with Lighthouse — your "Reduce preconnect" score should improve.
Exercise 4 — PWA Manifest Create a manifest.json with name, icons, theme color, and display mode. Link it via <link rel="manifest">. Test in Chrome DevTools → Application → Manifest.
Exercise 5 — RSS Auto-Discovery Add an RSS feed link to your page using <link rel="alternate" type="application/rss+xml">. Visit in Firefox — the RSS icon should appear in the address bar.
Exercise 6 — Lazy-Load Non-Critical CSS Take a render-blocking stylesheet and convert it to a non-blocking preload pattern (using the onload="this.rel='stylesheet'" trick). Measure First Contentful Paint improvement.

15 Real-World Use Cases

SEO-Optimized Pages

Canonical + hreflang alternates + Open Graph + Twitter Card. Standard for any content site.

Performance-First Sites

preconnect to fonts/CDN/API origins + preload critical font/hero image. Standard for e-commerce and news.

Progressive Web Apps

manifest.json + service worker + theme-color + apple-touch-icon. Enables installable, offline-capable web apps.

Multi-Language Sites

hreflang alternates for every supported language. Critical for international SEO (Wikipedia, Booking, Airbnb).

Blogs with RSS

rel="alternate" type="application/rss+xml" for feed discovery. Standard for any content site.

Favicon Optimization

Multiple favicon sizes + Apple touch icon + maskable PWA icon. Generated with realfavicongenerator.net.

WordPress

Auto-generates: canonical, shortlink, prev/next, pingback, alternate (RSS), wlwmanifest.

Speculation Rules

Modern sites use <script type="speculationrules"> to prerender the most-likely next page for instant navigation.

16 Summary

  • <link rel> in <head> references document-level resources without visible hyperlinks.
  • Resources: stylesheet, icon, manifest, preload, prefetch, preconnect, dns-prefetch, modulepreload.
  • SEO: canonical (always absolute), alternate + hreflang for translations, amphtml for AMP.
  • Meta: author, help, license, next/prev, search, pingback.
  • preload = high-priority for current page; prefetch = low-priority for next page.
  • preconnect warms full connection; dns-prefetch is DNS-only.
  • Always include crossorigin when preloading fonts.
  • Provide multiple favicon sizes for cross-device support.
  • PWA install requires manifest + service worker.
  • Modern alternative to prefetch: speculation rules in Chrome.
