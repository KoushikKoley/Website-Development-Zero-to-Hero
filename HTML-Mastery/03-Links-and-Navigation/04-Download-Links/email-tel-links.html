What Are Special URL Schemes?

Beyond http: and https:, browsers recognize several "special" URL schemes that hand off the action to another application instead of loading a web page. The two most useful for content authors are mailto: (opens the visitor's default email client with a pre-filled message) and tel: (initiates a phone call on devices with calling capability). Used well, these schemes remove friction from contact flows: a single tap on a phone number dials it; a single tap on an email address opens a draft already addressed and titled.

Mobile devices derive the most value from these schemes — desktop users without a configured mail client will see a less graceful fallback — so always provide visible text alternatives ("email us at hello@example.com") alongside the link. The schemes themselves are simple, but the syntax has enough rules and edge cases to warrant careful study.

The Basic mailto: Link

The simplest mailto: link contains only the recipient's email address. When clicked, the browser opens the user's default mail client with that address pre-filled in the "To" field. No subject, no body — just the address.

<a href="mailto:hello@example.com">Email us</a>
Email us
ℹ️ No protocol-relative URL

Always write mailto: with the trailing colon — mailto: is the scheme; the email address is the path. Do not add // (e.g. mailto://hello@example.com is invalid).

mailto: Parameters

You can pre-fill many fields of the email by adding query-string-style parameters after the address. The supported parameters are subject, body, cc (carbon copy), and bcc (blind carbon copy). Separate the first parameter from the address with ?, additional parameters with &.

<a href="mailto:hello@example.com?subject=Hello%20there&body=I%20wanted%20to%20say%20hi.">
  Send a greeting
</a>
Send a greeting

Full parameter reference

ParameterPurposeExample
subjectSets the email subject linesubject=Support%20Request
bodySets the email body (use %0A for line breaks)body=Hello%0A%0AMy%20question%20is...
ccAdds one or more CC recipientscc=boss@example.com
bccAdds one or more BCC recipientsbcc=archive@example.com
⚠️ Length limits vary

Browsers and email clients impose different (and often short) length limits on mailto: URLs. Avoid stuffing long pre-filled body content; anything beyond ~2,000 characters may be truncated or rejected. For long content, prefer a contact form.

Multiple Recipients

Send to multiple recipients by separating addresses with commas inside the main mailto: section (before the ?), or repeat the cc/bcc parameters. The first form is more widely supported.

<!-- Multiple addresses in the "to" field -->
<a href="mailto:sales@example.com,support@example.com?subject=Joint%20Inquiry">
  Email sales and support
</a>

<!-- Or split between to, cc, and bcc -->
<a href="mailto:sales@example.com?cc=billing@example.com&bcc=audit@example.com">
  Email with CC and BCC
</a>
Email sales and support

URL Encoding (Percent-Encoding)

Mailto URLs live inside an HTML attribute, so they must obey URL encoding rules. Spaces become %20 (or + in some contexts), commas are usually safe, but characters like &, ?, =, #, and non-ASCII letters must be percent-encoded. Line breaks in the body use %0D%0A (CRLF) or %0A (LF) — most clients accept either.

<!-- Multi-line body -->
<a href="mailto:hi@example.com?subject=Bug%20Report&body=Description:%0A%0ASteps%20to%20reproduce:%0A1.%20%0A2.%20%0A3.%20">
  Report a bug
</a>
✅ Pro Tip

If you're generating mailto links dynamically with JavaScript, use encodeURIComponent() on each piece — it handles every reserved character correctly. In a build step, use your templating language's URL-encoding filter (e.g. |urlencode in Jinja/Django, urlencode in Liquid).

The Basic tel: Link

The tel: URL scheme triggers a phone call. On mobile devices this opens the dialer pre-filled with the number; on desktops with calling apps (Skype, FaceTime, etc.) it may launch those instead.

<a href="tel:+18005551234">Call us: (800) 555-1234</a>
Call us: (800) 555-1234
ℹ️ Visible text should NOT be just digits

Always present a human-readable phone number as the link text — (800) 555-1234 is friendlier than +18005551234. The href should contain the E.164 format (with the + and country code) for maximum portability.

Phone Number Format (E.164)

The most reliable tel: format follows the ITU-T E.164 standard: a leading +, then the country code, then the subscriber number, with no spaces, dashes, or parentheses inside the URL. While browsers are tolerant of separators, E.164 is what carriers and PBX systems expect, so it survives the trip through more apps.

<!-- E.164 (recommended) -->
<a href="tel:+14155550123">+1 (415) 555-0123</a>

<!-- With separators (works in browsers, but discouraged) -->
<a href="tel:+1-415-555-0123">+1 (415) 555-0123</a>

<!-- Local format (region-dependent, may fail abroad) -->
<a href="tel:5550123">555-0123</a>

International Numbers and Pauses

For international audiences, always use E.164. If you need to dial an extension or insert a pause, use , (one-second pause) or ; (wait for user input). Note that ; is part of the RFC 3966 spec but support is spotty — test on real devices.

<!-- With extension -->
<a href="tel:+18005551234,1234">Call (800) 555-1234 ext. 1234</a>

<!-- With wait (RFC 3966) -->
<a href="tel:+18005551234;ext=1234">Call (800) 555-1234 ext. 1234</a>

sms: Links

The sms: scheme opens the SMS app pre-filled with a recipient and (optionally) a body. Support is best on mobile; desktop browsers usually do nothing. Use ? for the body on iOS and & on Android — to satisfy both, provide two links or accept that one platform may not see the body.

<!-- iOS syntax -->
<a href="sms:+18005551234?body=Hello%20there">Text us</a>

<!-- Android syntax -->
<a href="sms:+18005551234?body=Hello%20there">Text us</a>

<!-- Cross-platform safer (no body) -->
<a href="sms:+18005551234">Text us</a>
⚠️ Body support is inconsistent

Safari on iOS expects ?body=; Chrome on Android historically wanted ?body= too but the spec evolved. Test on real devices before relying on pre-filled SMS bodies in production.

FaceTime, Skype, and Other App Schemes

Apple exposes facetime: and facetime-audio: for video and audio calls on supported devices. Skype recognizes skype: with a ?call or ?chat action. WhatsApp accepts https://wa.me/<number>?text=<encoded>. None of these are universal — always include a visible phone number or username as fallback text.

<a href="facetime:john@example.com">FaceTime John</a>
<a href="facetime-audio:+18005551234">FaceTime Audio (800) 555-1234</a>
<a href="skype:john.doe?call">Call John on Skype</a>
<a href="https://wa.me/18005551234?text=Hi%20there">WhatsApp us</a>

Styling Action Links

mailto: and tel: links are still <a> elements, so they inherit the same color, hover, and focus styles as ordinary links. It's good UX to make them visually distinct so users understand the link will leave the page (launch an external app). Icons help — a small envelope SVG next to mailto, a phone glyph next to tel.

<style>
  .action-link {
    display: inline-flex;
    align-items: center;
    gap: 0.4rem;
    background: #6366f1;
    color: #fff;
    padding: 0.6rem 1.1rem;
    border-radius: 8px;
    text-decoration: none;
    font-weight: 600;
    transition: background 0.15s ease;
  }
  .action-link:hover { background: #4f46e5; }
  .action-link:focus-visible {
    outline: 3px solid #fbbf24;
    outline-offset: 2px;
  }
</style>

<a class="action-link" href="mailto:hello@example.com">
  ✉️ Email us
</a>
<a class="action-link" href="tel:+18005551234">
  📞 Call us
</a>

Security and Privacy Concerns

mailto: links expose email addresses to anyone reading the source — including spam harvesters. To reduce spam, consider obfuscating the address (e.g. hello [at] example [dot] com as visible text, while the href uses real encoding), or replace the link with a contact form protected by CAPTCHA. The same applies to phone numbers: a public tel: link makes your number crawlable.

Never accept user input and concatenate it directly into a mailto: URL without validation — an attacker could craft a link that runs JavaScript in older browsers via javascript: scheme or smuggles extra parameters into the body. Sanitize and URL-encode all dynamic values.

⚠️ Never use javascript: scheme

The legacy javascript: URL scheme (e.g. href="javascript:sendMail()") is deprecated, a security risk, and breaks in browsers with JavaScript disabled. Always use mailto: for email triggers, and reserve javascript: for nothing.

UX Best Practices

  • Make numbers tappable: on mobile, wrap every visible phone number in a tel: link. The minimum target size for thumb taps is 44×44px (Apple HIG) or 48×48dp (Material).
  • Show the address: the visible text should always include the email address or phone number itself, not just "Click here" — screen-reader users benefit from the explicit info.
  • Provide a contact form too: mailto: fails for users on shared/public machines without a configured mail client. A form is more reliable.
  • Use aria-label for icon-only links: if your link text is just an envelope emoji, add aria-label="Email us at hello@example.com".
  • Add rel="noopener" when combining with target="_blank": though mailto: rarely opens a new tab, if you do, prevent reverse-tabnabbing.
✏️ Try It Yourself

Build a small "Contact card" component that includes: a styled mailto link with pre-filled subject "Question from website" and a 3-line body template, a tel: link in E.164 format, a WhatsApp link, and visible text fallback for each. Test by clicking each link on both desktop and a mobile device.

Summary

The mailto: and tel: URL schemes are tiny but mighty — they turn any link into a one-tap action that opens the visitor's preferred email client or dialer. Master the parameter syntax (subject, body, cc, bcc), always URL-encode dynamic values, prefer E.164 phone numbers, and remember that these schemes are most powerful on mobile while desktop users may need a contact form fallback. Style your action links to set expectations, keep accessibility in mind with descriptive text and ARIA labels, and you'll have contact flows that delight users on every device.

Browser Support mailto: universal since IE3; tel: supported in all modern mobile browsers and most desktop browsers since 2015. sms: body support varies — always test on real devices before shipping.
