Section 3.9 · A11y Links

Accessible Links

Accessibility isn't a feature — it's a baseline. Links are the most common interactive element on the web, and they're where most accessibility failures happen: vague "click here" text, missing focus styles, color-only differentiation. Get links right, and you've solved 80% of common a11y issues.

1 Why Link Accessibility Matters

Links are how users move through your site. If they're inaccessible, certain users can't navigate at all — they can't buy your product, read your content, or contact you. The legal and moral case is clear; the practical case is even simpler: accessible links benefit everyone.

  • Screen reader users navigate by tabbing through links and hearing only the link text — not surrounding context.
  • Keyboard users need visible focus indicators to know where they are.
  • Low-vision users need sufficient color contrast.
  • Voice-control users say the visible link text to click it.
  • Cognitive-load-sensitive users benefit from clear, descriptive labels.
Pro Tip WCAG 2.1 AA is the legal standard in many jurisdictions (ADA in the US, EAA in the EU, AODA in Ontario). It's also the baseline Google Lighthouse audits against. Aim higher (AAA where reasonable) — but never below AA.

2 Link Text Best Practices

The single most common accessibility mistake: vague link text. Screen reader users often pull up a "links list" — every link on the page, out of context. If your link text is "click here" or "read more", that list is useless.

❌ Don't

<!-- Vague, context-dependent -->
<a href="/blog/post-1">Click here</a>
<a href="/blog/post-2">Read more</a>
<a href="/blog/post-3">Learn more</a>
<a href="#">here</a>
<a href="#">link</a>

✅ Do

<!-- Descriptive, self-contained -->
<a href="/blog/css-grid">Understanding CSS Grid Layout</a>
<a href="/blog/flexbox">Mastering Flexbox Patterns</a>
<a href="/pricing">View pricing plans</a>
<a href="/api/docs">Read the API documentation</a>
Common Mistake The "Read more" pattern is everywhere — and accessibility tools universally flag it. The fix: include context in the link, or use aria-labelledby / aria-label to extend it: 
<article>
  <h3 id="post-1-title">Understanding CSS Grid</h3>
  <p>A deep dive into two-dimensional layout...</p>
  <a href="/blog/css-grid" aria-labelledby="post-1-title">Read more</a>
</article>
Now screen readers announce: "Understanding CSS Grid, link".

Other Link-Text Rules

  • Don't include the URL as the link text (e.g., "Click https://example.com/page" — say "Visit Example's page").
  • Avoid "http://" / "www." prefixes in visible text — they're noise.
  • Don't make the entire sentence a link. Link only the action/object.
  • Avoid ALL CAPS — many screen readers spell them out letter by letter.
  • Keep link text concise — under ~100 characters when possible.
Pro Tip — Voice Control Voice-control users (Dragon, Voice Control on Mac/iOS) say the visible link text to click. "Click Read more" fails when there are 5 "Read more" links on the page. "Click Understanding CSS Grid" works perfectly.

3 aria-current

When the link points to the page the user is currently on, mark it with aria-current="page". Screen readers announce "current page"; you can also use it as a CSS hook for styling.

<nav aria-label="Primary">
  <ul>
    <li><a href="/" aria-current="page">Home</a></li>
    <li><a href="/products">Products</a></li>
    <li><a href="/about">About</a></li>
  </ul>
</nav>

<style>
  nav a[aria-current="page"] {
    background: var(--brand);
    color: white;
    font-weight: 600;
  }
</style>

The full deep dive is in 03-Page-Navigation/site-nav.html.

4 Focus Styles & :focus-visible

Keyboard users navigate with Tab. They need to see which element is currently focused — the focus ring is how. Removing the default outline is one of the worst accessibility crimes on the web.

❌ Don't

/* Removes focus indicator entirely */
a { outline: none; }

/* Applies to mouse clicks too — ugly and unnecessary */
a:focus { outline: none; }

✅ Do

/* Applies only when keyboard-navigating */
a:focus-visible {
  outline: 3px solid var(--brand);
  outline-offset: 3px;
  border-radius: 2px;
}

/* Mouse clicks don't show ring — but keyboard does */

Pro Tip — :focus-visible vs :focus :focus applies whenever the element has focus — including after a mouse click. :focus-visible applies only when the browser heuristically decides the user is keyboard-navigating. Always prefer :focus-visible for custom styles — mouse users won't see an ugly ring after clicking, but keyboard users still get one.

Make the Ring Visible

The focus ring must have a contrast ratio of at least 3:1 against adjacent colors (WCAG 2.4.11 — Focus Appearance, in WCAG 2.2). Avoid thin outlines — 3px is the minimum recommended width.

5 Skip Links

A skip link is the first focusable element on the page. Hidden until focused, it lets keyboard users jump directly to main content — bypassing long navigation menus.

<!-- First element in <body> -->
<a href="#main" class="skip-link">Skip to main content</a>

<nav>...long navigation...</nav>

<main id="main">
  <h1>Main content</h1>
</main>

<style>
  .skip-link {
    position: absolute;
    top: -100px;
    left: 8px;
    z-index: 1000;
    background: var(--brand);
    color: white;
    padding: 12px 18px;
    border-radius: 0 0 8px 8px;
    text-decoration: none;
    transition: top 0.2s;
  }
  .skip-link:focus {
    top: 0;
  }
</style>
Common Mistake — display: none Using display: none or visibility: hidden makes the link unfocusable. Always use off-screen positioning (top: -100px) and reveal on :focus.

WCAG 2.4.1 (Bypass Blocks) requires a way to skip repetitive navigation. Skip links are the simplest, most reliable solution.

6 Distinguishing Links from Buttons

Both can be styled to look identical — but they have different semantics. Getting this wrong confuses screen reader users and breaks keyboard behavior.

AspectLink <a>Button <button>
ActivationEnter (also Ctrl/Cmd+Click, middle-click)Enter or Spacebar
CursorPointerPointer (if you style it)
Address bar URLUpdates with hrefNo URL change
Right-click → "Open in new tab"YesNo
BookmarkableYesNo
Use caseNavigationAction (toggle, submit, modal)

Decision Rule

  • If clicking changes the URL → use <a href>.
  • If clicking does an action (open modal, toggle, submit, fetch) → use <button>.
  • If you're not sure → it's almost always a button.
<!-- ✅ Link: navigation -->
<a href="/products/123">View product</a>

<-- ✅ Button: action -->
<button type="button" onclick="openModal()">Quick view</button>

<-- ✅ Button: form submit -->
<button type="submit">Place order</button>

<-- ❌ Wrong: link pretending to be a button -->
<a href="#" onclick="openModal()">Quick view</a>
Common Mistake Many "link-styled-as-button" patterns use href="#" — which scrolls to top on click. Even with preventDefault(), screen readers announce "link" instead of "button". Use the right element.

7 Color Contrast (WCAG AA & AAA)

Link color must contrast with its background. WCAG defines two conformance levels:

LevelContrast Ratio (normal text)Contrast Ratio (large text, 18pt+)
AA (minimum)4.5:13:1
AAA (enhanced)7:14.5:1
AA pass: #2563eb on white Ratio: 4.6:1 ✓
AAA pass: #1e40af on white Ratio: 8.6:1 ✓
Fail: #93c5fd on white Ratio: 1.9:1 ✗

Don't Rely on Color Alone

Links must be distinguishable from non-link text — but not by color alone. Add underline, bold, or an icon. Colorblind users can't see "blue" as different from "black".

/* ✅ Always underline links */
a { text-decoration: underline; }

/* ✅ Or use underline on hover at minimum */
a { text-decoration: none; }
a:hover { text-decoration: underline; }

/* ✅ Differentiate visited */
a:visited { color: #6b21a8; }
Common Mistake — Removing Underline Many design systems remove underlines for aesthetic reasons. This is a known accessibility failure (WCAG 1.4.1). If you must remove underlines, ensure the link is still distinguishable by:
  • Strong color contrast vs body text AND background.
  • Bold weight.
  • Icon (e.g., ↗ for external links).
  • Background pill / button-like styling.
And always restore underline on hover and focus.

8 Screen Reader Announcements

Screen readers announce links based on their accessible name — which comes from the link text, or from aria-label/aria-labelledby if provided. The word "link" is added automatically.

Icon-Only Links

Icon-only links (e.g., social media icons in a footer) have no visible text — you must provide an accessible name:

<!-- ❌ Screen reader says just "link" -->
<a href="/cart"><svg>...cart icon...</svg></a>

<-- ✅ Option 1: aria-label -->
<a href="/cart" aria-label="View shopping cart (3 items)">
  <svg aria-hidden="true">...cart icon...</svg>
</a>

<-- ✅ Option 2: visually-hidden text -->
<a href="/cart">
  <svg aria-hidden="true">...cart icon...</svg>
  <span class="sr-only">View shopping cart (3 items)</span>
</a>

<-- CSS for sr-only -->
<style>
  .sr-only {
    position: absolute;
    width: 1px; height: 1px;
    padding: 0; margin: -1px;
    overflow: hidden;
    clip: rect(0, 0, 0, 0);
    white-space: nowrap;
    border: 0;
  }
</style>
Pro Tip Always mark decorative icons aria-hidden="true" — otherwise screen readers may announce "image" alongside the link. Pair aria-hidden on the icon with aria-label (or visible text) on the link.

Avoid Redundant Announcements

<!-- ❌ Redundant: announces "Cart link, link" -->
<a href="/cart" aria-label="Cart link">...</a>

<-- ✅ Clean: announces "Cart, link" -->
<a href="/cart" aria-label="Cart">...</a>

9 External & New-Tab Links

When a link opens in a new tab (target="_blank"), screen reader users benefit from knowing in advance. Add this info to the accessible name:

<!-- ✅ Visible text informs the user -->
<a href="https://example.com" target="_blank" rel="noopener noreferrer">
  Visit Example.com (opens in new tab)
</a>

<-- ✅ Or visually-hidden text + visible icon -->
<a href="https://example.com" target="_blank" rel="noopener noreferrer">
  Visit Example.com
  <svg aria-hidden="true" width="14" height="14">
    <path d="M7 17L17 7M17 7H7M17 7v10" />
  </svg>
  <span class="sr-only">(opens in new tab)</span>
</a>

<-- ✅ Or aria-label -->
<a href="https://example.com" target="_blank" rel="noopener noreferrer"
   aria-label="Visit Example.com (opens in new tab)">
  Visit Example.com ↗
</a>
Common Mistake Don't surprise users with new tabs without warning. Some users (especially those with cognitive disabilities or screen reader users) find unexpected tab switches disorienting. Either:
  • Open in the same tab (default), or
  • Clearly indicate "opens in new tab" in text/icon.

10 Try It Yourself

Exercise 1 — Fix Vague Link Text Rewrite these links with descriptive text: "Click here to read about our pricing", "Read more about the new feature", "Link to the documentation". Each link should make sense out of context.
Exercise 2 — aria-labelledby Pattern Build a blog post card with a heading, excerpt, and "Read more" link. Use aria-labelledby to associate the "Read more" link with the heading — so screen readers announce the title.
Exercise 3 — Focus Ring Style :focus-visible with a 3px outline that has 3px offset. Tab through your page — verify the ring is visible on every focusable element. Test that mouse clicks don't show the ring.
Exercise 4 — Icon-Only Link Build a "Share to Twitter" icon link. The icon (SVG Twitter bird) is the only visible content. Add aria-label="Share to Twitter" and mark the SVG aria-hidden="true".
Exercise 5 — Contrast Audit Use a contrast checker (WebAIM, Chrome DevTools "Inspect → Accessibility") to verify your link colors meet WCAG AA. If any fail, adjust the color until they pass.
Exercise 6 — Link vs Button Audit Audit your existing project. Find every <a href="#"> and decide: should it be a button? Convert any that don't change the URL.
Exercise 7 — Skip Link Add a skip link as the first focusable element on a page. Make it visually hidden until focused. Test by tabbing from the address bar — the link should slide into view.

12 Real-World Use Cases

Nav Menus

Every nav item needs descriptive text + aria-current="page" + visible focus state.

Blog Cards

Block-link pattern with "Read more" + aria-labelledby pointing to the post title.

Social Media Footer

Icon-only links to Twitter, LinkedIn, etc. Each needs aria-label="Follow us on X".

PDF Downloads

Indicate PDF + file size in link text: "Annual Report 2024 (PDF, 2.4 MB)".

External Links

Visual ↗ icon + rel="noopener noreferrer external" + aria-label indicating new tab.

Shopping Cart

Icon + "Cart (3)" text + aria-label="View shopping cart, 3 items".

Legal Documents

Skip links to skip to: Definitions, Your Rights, Contact, etc. Critical for ToS/Privacy pages.

Help / Support

Inline links in help articles should have full context — not just "click here".

13 Summary

  • Link text must be descriptive and self-contained — never "click here" or "read more".
  • Use aria-current="page" on the link to the current page.
  • Always style :focus-visible — never remove focus outlines.
  • Skip links (first focusable element) let keyboard users bypass repetitive nav.
  • Use <a href> for navigation; <button> for actions. Don't mix them up.
  • Color contrast: ≥4.5:1 for normal text (WCAG AA); ≥7:1 for AAA.
  • Don't rely on color alone to distinguish links — keep underlines.
  • Icon-only links need aria-label; mark icons aria-hidden="true".
  • Indicate new-tab links in text or aria-label.
  • WCAG 2.1 AA is the legal baseline; aim higher where reasonable.
