Responsive Tables

Tables are inherently wide — and screens are inherently narrow. Five battle-tested patterns to make tables usable on mobile: horizontal scroll, card transformation, data-attribute labels, CSS Grid rebuilds, and the hybrid "best of both" approach.

1 The problem

Tables are designed for wide horizontal layout — many columns side by side. Mobile screens are 320-414px wide. A 6-column table with 100px columns needs 600px minimum. The content overflows, the user pinch-zooms, and the experience falls apart.

Unlike flex/grid layouts, tables don't naturally reflow: their semantic structure is rows-and-columns, and you can't just flex-wrap a <tr> to put some cells on a second line.

Key insight There is no "one right way" to make tables responsive. The best pattern depends on your data: how many columns, how much text per cell, whether users need to compare rows side-by-side, and whether the table is the primary content or supplementary.

3 Pattern 1: Horizontal scroll

The simplest, fastest, most accessible solution. Wrap the table in a div with overflow-x: auto. The browser shows a horizontal scrollbar; on touch devices, the user swipes.

<div class="table-scroll">
  <table>
    <caption>Q1 Sales by Region</caption>
    <thead>
      <tr><th scope="col">Region</th><th scope="col">Jan</th>...</tr>
    </thead>
    <tbody>
      <tr><th scope="row">North</th><td>$1.2M</td>...</tr>
    </tbody>
  </table>
</div>

<style>
  .table-scroll {
    overflow-x: auto;
    -webkit-overflow-scrolling: touch;  /* momentum on iOS */
  }
  .table-scroll table { min-width: 600px; }
</style>

Pro Tip Set min-width on the table so it doesn't try to compress — it forces the scrollbar to appear when the viewport is too narrow. Use -webkit-overflow-scrolling: touch for smooth momentum scroll on older iOS.
Common Mistake Don't hide the horizontal scrollbar — users on desktop may not realize the table scrolls. Style it subtly with ::-webkit-scrollbar rather than removing it.

4 Pattern 2: Card transform

On mobile, completely change the visual layout: each row becomes a stacked card, with each cell becoming a labeled key-value pair. The table semantics are preserved in the markup — only CSS changes the look.

/* Desktop: normal table */
table { width: 100%; border-collapse: collapse; }
th, td { border: 1px solid #cbd5e1; padding: 8px 12px; }

/* Mobile: transform to cards */
@media (max-width: 600px) {
  table thead { display: none; }

  table, table tbody, table tr, table td {
    display: block;
    width: 100%;
    border: none;
  }

  table tr {
    margin-bottom: 12px;
    border: 1px solid #cbd5e1;
    border-radius: 8px;
    padding: 8px 12px;
    background: white;
  }

  table td {
    padding: 6px 0;
    border: none;
  }

  /* Label each cell with the data-label attribute */
  table td::before {
    content: attr(data-label);
    font-weight: 600;
    color: #475569;
    display: inline-block;
    width: 100px;
    margin-right: 8px;
  }
}

5 Pattern 3: Data-attribute labels

This is the cleanest "one source, two layouts" approach. Each <td> carries a data-label attribute echoing the column header text. CSS reveals the labels only on mobile.

<table>
  <thead>
    <tr>
      <th scope="col">Product</th>
      <th scope="col">Price</th>
      <th scope="col">Stock</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td data-label="Product">Apple</td>
      <td data-label="Price">$1.20</td>
      <td data-label="Stock">128</td>
    </tr>
  </tbody>
</table>
Pro Tip The data-label approach combines with the card-transform CSS (Pattern 2). Keep header text and data-label text identical — automate via server templates to prevent drift.
Drawback The header text is duplicated in two places. If headers change, you must update both. Use a build step or template variable to keep them in sync.

6 Pattern 4: CSS Grid rebuild

For highly bespoke layouts, abandon <table> on mobile and switch to CSS Grid. You lose table semantics unless you add ARIA roles:

<!-- Mobile markup with ARIA roles mimicking table -->
<div role="table" aria-label="Q1 Sales by Region">
  <div role="row">
    <span role="columnheader">Region</span>
    <span role="columnheader">Jan</span>
    <span role="columnheader">Feb</span>
  </div>
  <div role="row">
    <span role="rowheader">North</span>
    <span role="cell">$1.2M</span>
    <span role="cell">$1.4M</span>
  </div>
</div>

<style>
  [role="table"] {
    display: grid;
    grid-template-columns: 1fr 1fr 1fr;
    gap: 4px;
  }
  [role="row"] {
    display: contents;  /* children become grid items */
  }
</style>
Cost vs benefit This is significant effort. Only choose this when the visual layout genuinely can't be expressed as a table. For 95% of responsive tables, Patterns 1-3 work better and preserve semantics for free.

7 Pattern 5: Hybrid (progressive disclosure)

Show only the most important columns on mobile. Hide secondary columns. Provide a "Show more" button per row to expand the rest. Used by Gmail's mobile web (subject + sender visible; details on tap).

<style>
  /* Hide non-essential columns on mobile */
  @media (max-width: 600px) {
    .table td.secondary, .table th.secondary {
      display: none;
    }
    .table tr.expanded td.secondary {
      display: block;
      width: 100%;
    }
  }
</style>

<script>
  document.querySelectorAll('.table tr').forEach(row => {
    row.addEventListener('click', () => {
      row.classList.toggle('expanded');
    });
  });
</script>
Pro Tip Combine Pattern 5 with Pattern 1 (scroll) for the best UX: show 2-3 key columns visible, then allow horizontal scroll for the rest, with tap-to-expand for full details. This is the gold-standard pattern used by Stripe Dashboard, Linear, and modern admin tools.

8 Viewport-based font sizing

For tables that must fit on small screens without scrolling, shrink the font as the viewport narrows:

table {
  /* fluid font size — scales with viewport */
  font-size: clamp(0.75rem, 2.5vw, 0.95rem);
}

/* Or use container queries (modern browsers) */
@container table-cards (max-width: 480px) {
  .table-card { font-size: 0.8rem; }
}

clamp() sets a minimum, preferred, and maximum size. On a 320px phone, the font shrinks to ~12px; on a 1200px desktop, it caps at ~15px. Pair with reduced cell padding on mobile.

Accessibility check Never go below 12px for table text — WCAG recommends minimum 12-14px for readability. If your table won't fit at that size, switch to a different pattern (scroll or cards) rather than shrinking further.

10 Common mistakes

MistakeImpactFix
Removing <caption> on mobileScreen reader users lose the table's accessible name.Keep the caption; just style it.
Setting display: block on table without restructuringCells stack but lose row association; screen readers confused.Use card transform CSS or rebuild with ARIA.
Hiding columns with display: none on mobileScreen reader users lose the hidden data permanently.Use visibility: collapse on <col> or progressive disclosure.
Font sizes below 12px on mobileFails WCAG readability; squinting users.Use clamp() with min 0.75rem.
Removing hover states on touch devicesHover-only actions become inaccessible.Add tap-to-toggle; never rely on hover alone.
Forgetting sticky first column in scroll patternRow context lost when scrolling right.Apply position: sticky; left: 0; to first column cells.
Not testing on real devices"Works in DevTools mobile mode" isn't enough — touch interactions differ.Test on actual phones or BrowserStack.

11 Try it yourself

Exercise 1 — Scroll wrap Take a 6-column table. Wrap it in a <div style="overflow-x:auto">. Set min-width: 600px on the table. Resize your browser to 400px wide and verify you can scroll horizontally.
Exercise 2 — Card transform Apply the card-transform CSS from Pattern 2 to a 3-column table inside a @media (max-width: 600px) query. Add data-label attributes to each <td>. Test on a phone-width viewport.
Exercise 3 — Sticky first column Combine Pattern 1 (scroll) with a sticky first column. Apply position: sticky; left: 0; to the first column's cells. Verify you can scroll horizontally while the row labels stay visible.
Exercise 4 — Fluid font size Apply font-size: clamp(0.75rem, 2.5vw, 0.95rem); to a table. Verify the font shrinks gracefully as you narrow the viewport, with a floor of 12px.
Exercise 5 — Hybrid pattern Build a 5-column table. On mobile, show only 2 columns by default. Add a "Details" button per row that toggles a class revealing the other columns. Test the UX on a phone-width viewport.

12 Browser support

overflow-x: auto — universal @media queries — universal display: block on table — universal position: sticky — modern browsers clamp() — modern browsers (90%+) data-* attributes — universal CSS Grid — modern browsers ARIA table roles — universal in modern screen readers

Every pattern in this lesson works in browsers your users actually have. Container queries are newer (2023+) but have graceful fallback — the table simply doesn't shrink as aggressively without them.

13 Real-world use cases

Admin dashboards

Hybrid pattern with sticky first column + horizontal scroll. Stripe, Linear, Notion.

Contact lists

Card transform on mobile — each contact becomes a tappable card.

Financial reports

Horizontal scroll with sticky row-header column. Preserve digit alignment.

Sports standings

Hide low-priority columns (shots, possession); show rank + team + points.

E-commerce carts

Card transform — each cart item becomes a stacked card with quantity controls.

Booking systems

Scrollable day-by-day schedule with sticky time column on the left.
