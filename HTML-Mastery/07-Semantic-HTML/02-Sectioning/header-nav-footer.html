<header>, <nav> & <footer>

Three elements that frame every section of every page. <header> holds introductory content. <nav> holds major navigation. <footer> holds closing information. They aren't restricted to the top and bottom of the page — they can appear inside any sectioning element, which means a single page often has many of them.

1 The <header> element

<header> represents introductory content for its nearest sectioning ancestor (the page's <body>, or an <article>, <section>, <aside>, or <nav>). It typically contains:

  • A heading (<h1>–<h6>)
  • A logo or wordmark
  • Search form, primary navigation
  • Author byline, publish date, social links
  • Introductory paragraph or tagline
<!-- Page-level header -->
<header>
  <a href="/" class="logo">Acme Corp</a>
  <nav aria-label="Primary">
    <ul>
      <li><a href="/">Home</a></li>
      <li><a href="/products">Products</a></li>
      <li><a href="/about">About</a></li>
    </ul>
  </nav>
  <form role="search">
    <input type="search" placeholder="Search…" aria-label="Search">
  </form>
</header>

A page-level header is announced by screen readers as a "banner" landmark — the top-of-page region users can jump to with a single key.

Pro Tip The HTML5 spec says a <header> that is a direct child of <body> gets the implicit ARIA role banner. A <header> inside an <article> or <section> does not get banner — it's just an introductory chunk within that section.

2 Multiple headers per page

A common misconception: "you can only have one <header> per page". Wrong. The spec allows one <header> per sectioning element. So a page with a main article and two sidebars can legitimately have four headers:

<body>

  <!-- 1. Page header (becomes the "banner" landmark) -->
  <header>
    <nav>…</nav>
  </header>

  <main>
    <article>
      <!-- 2. Article header (just intro content, NOT a banner) -->
      <header>
        <h1>How to Brew Coffee</h1>
        <p>By Ada on <time datetime="2024-03-12">March 12</time></p>
      </header>

      <p>Body…</p>
    </article>

    <aside>
      <!-- 3. Sidebar header -->
      <header>
        <h2>Related Posts</h2>
      </header>
      <ul>…</ul>
    </aside>
  </main>

  <!-- 4. Page footer -->
  <footer>…</footer>

</body>

Only the top-level <header> (the one that's a direct child of <body>) becomes the banner landmark. The others are simply introductory content within their respective sections.

Common Mistake Wrapping every "top of section" content in a <header>. If the section has just a heading and no other introductory content, the heading alone is enough — you don't need a header wrapper. <section><h2>…</h2><p>…</p></section> is perfectly fine.

3 The <nav> element

<nav> is for major navigation blocks: collections of links that let users navigate the site or page. It is not for every group of links — only for the ones that are themselves navigation.

Appropriate uses

  • Primary site navigation (top menu, main nav bar)
  • Secondary navigation (sidebar menus, section sub-nav)
  • Footer link lists (about, contact, legal — if grouped as navigation)
  • Table of contents within a long article
  • Breadcrumb trails
  • Pagination controls
<!-- Primary nav -->
<nav aria-label="Primary">
  <ul>
    <li><a href="/">Home</a></li>
    <li><a href="/products">Products</a></li>
    <li><a href="/about">About</a></li>
    <li><a href="/contact">Contact</a></li>
  </ul>
</nav>

<!-- Breadcrumbs -->
<nav aria-label="Breadcrumb">
  <ol>
    <li><a href="/">Home</a></li>
    <li><a href="/blog">Blog</a></li>
    <li aria-current="page">This Post</li>
  </ol>
</nav>

<!-- Pagination -->
<nav aria-label="Pagination">
  <ul>
    <li><a href="?page=1" rel="prev">← Previous</a></li>
    <li><a href="?page=3" rel="next">Next →</a></li>
  </ul>
</nav>
Pro Tip Always add an aria-label to <nav> when there's more than one on the page. Without it, screen readers announce all of them simply as "navigation" — users can't tell which is which. With labels, they hear "primary", "breadcrumb", "pagination" — instantly distinguishable.

4 When NOT to use <nav>

The HTML spec is explicit: "Not all groups of links on a page need to be in a <nav> element — the element is intended only for major navigation blocks."

Use <nav>Don't use <nav>
Primary site nav, footer nav, breadcrumbs, pagination, table of contents A list of "related articles" inside a blog post body
Tab navigation that switches view inside a section A list of social-media links in an author bio
Sidebar category filter for an e-commerce section A list of links inside a paragraph of body text
Category navigation in product listings Tag clouds (they're links, but not navigation in the user's mental model)

For non-navigation link groups, use a plain <ul> inside whatever sectioning element makes sense — usually <aside> for related links, or just <ul> directly inside the article body.

Common Mistake Wrapping every list of links in <nav>. The result is screen reader users navigating past dozens of "navigation" landmarks. Save <nav> for the navigations that users would actually want to jump to.

5 The <footer> element

<footer> represents closing content for its nearest sectioning ancestor. Like <header>, it can appear multiple times per page — once per sectioning element that needs one.

Appropriate contents

  • Copyright notices and legal links
  • Author info, contact details, social media
  • Related links, "see also" sections
  • Sitemap links, "back to top" anchor
  • Citation list, references, appendix
  • Post meta: tags, categories, share buttons
<!-- Page-level footer (becomes "contentinfo" landmark) -->
<footer>
  <p>© 2024 Acme Corp. All rights reserved.</p>
  <nav aria-label="Footer">
    <ul>
      <li><a href="/privacy">Privacy</a></li>
      <li><a href="/terms">Terms</a></li>
      <li><a href="/contact">Contact</a></li>
    </ul>
  </nav>
</footer>
<!-- Article-level footer (just closing info, NOT contentinfo) -->
<article>
  <h1>Post Title</h1>
  <p>Body…</p>

  <footer>
    <p>Tags:
      <a href="/tag/html">html</a>,
      <a href="/tag/a11y">a11y</a>
    </p>
    <p>By <a href="/author/ada">Ada</a> ·
       Published <time datetime="2024-03-12">March 12</time>
    </p>
  </footer>
</article>

6 Footer contents

Content typeElementExample
Copyright<p><p>© 2024 Acme</p>
Legal links<nav> + <ul>Privacy, Terms, Cookies
Contact info<address>Email, postal address (use only for actual contact info)
Social media<ul> (or <nav> if you consider it navigation)Twitter, GitHub, LinkedIn icons
Newsletter signup<form>Email input + subscribe button
Sitemap<nav> + nested <ul>Multi-level nav tree
Author bio<div> or <aside>Avatar + name + short bio
Back to top<a href="#top">Single link, no wrapper needed
Pro Tip Use <address> inside a footer for actual contact information (email, phone, postal). The element doesn't italicize for styling — it's semantic: "this is contact info for the author/owner of the article or page". Don't use it for arbitrary postal addresses in body content; only for the contact info of the page/article owner.

7 Browser default styling

<header>, <nav>, and <footer> all have no default styling. They are block-level elements (display: block) but browsers apply zero padding, margin, color, or typography to them. They're a completely blank canvas — which is exactly the point.

ElementDefault displayDefault marginDefault role
<header> (child of body)block0banner
<header> (inside article/section)block0none (just generic)
<nav>block0navigation
<footer> (child of body)block0contentinfo
<footer> (inside article/section)block0none (just generic)

Compare with <h1> which has default font-size: 2em; margin: 0.67em 0;, or <p> which has margin: 1em 0. The structural elements are intentionally unstyled so you can build any visual treatment on top.

Pro Tip Because these elements have no default styles, your CSS reset doesn't need to touch them. But your design system does need to define what they look like. Many starter stylesheets add header, nav, footer { display: block; } purely for ancient Internet Explorer — modern browsers don't need this.

8 Real-world patterns

Pattern A: Classic three-region page

<body>
  <header>
    <a href="/" class="logo">…</a>
    <nav aria-label="Primary">…</nav>
    <form role="search">…</form>
  </header>

  <main>
    <article>…</article>
  </main>

  <footer>
    <p>© 2024 Acme</p>
    <nav aria-label="Footer">…</nav>
  </footer>
</body>

Pattern B: Article with full chrome

<article>
  <header>
    <h1>Why Semantic HTML Matters</h1>
    <p class="byline">
      By <a rel="author" href="/authors/ada">Ada Lovelace</a> ·
      <time datetime="2024-03-12">March 12, 2024</time> ·
      8 min read
    </p>
  </header>

  <p>Body…</p>

  <footer>
    <p>Tags: <a href="/tag/html">html</a>,
              <a href="/tag/a11y">a11y</a></p>
    <address>
      Contact: <a href="mailto:ada@acme.com">ada@acme.com</a>
    </address>
  </footer>
</article>

Pattern C: Sidebar with sub-nav

<aside aria-label="Sidebar">
  <header>
    <h2>Documentation</h2>
  </header>
  <nav aria-label="Documentation sections">
    <ul>
      <li><a href="/docs/intro">Introduction</a></li>
      <li><a href="/docs/install">Installation</a></li>
      <li><a href="/docs/api">API Reference</a></li>
    </ul>
  </nav>
</aside>

9 Common mistakes

MistakeWhy it's wrongFix
Wrapping every section's heading in <header> Unnecessary; the heading alone is enough Use <header> only when there's other intro content (byline, date, logo)
Multiple <nav>s without aria-label SR users can't tell them apart Add aria-label="Primary", "Footer", "Breadcrumb" etc.
Putting all body content in <nav> "to make it accessible" Wrong element; <main> is the right one Use <main> for primary content
Using <footer> for any content at the bottom of a div <footer> only makes sense inside a sectioning element Wrap your bottom content in <section> or use it inside <article>/<main>
Skipping <address> for contact info Loses the "this is contact info" semantic Use <address> for author/owner contact details
Putting primary nav inside <main> Nav belongs outside main; main is for unique content Place <nav> in <header> or sibling to <main>
Using <nav> for a list of tags or social-media icons in body Not "major navigation" Use plain <ul>

10 Try it yourself

Exercise 1 — Landmark scan Open a website you use daily. Using VoiceOver's rotor (VO+U) or NVDA's landmark key (D), count how many "banner", "navigation", and "contentinfo" landmarks it has. If the count is wrong (zero or way too many), diagnose why and write down the fix.
Exercise 2 — Label your navs Take any page you've built with multiple <nav> elements (primary, footer, breadcrumb). Add aria-label to each one with a distinguishing name. Test in a screen reader — verify each is announced distinctly.
Exercise 3 — Article chrome Build a full blog post with <header> (h1, byline, date), body, and <footer> (tags, author contact via <address>). Validate that the article footer is NOT announced as "contentinfo" — only the page-level footer should be.
Exercise 4 — Naked HTML Disable CSS on a page you've built. Does the header still look like a header (logo + nav links)? Does the footer still read like a footer? If not, your structure is relying on CSS to convey meaning — fix the markup.

11 Browser support

Chrome Firefox Safari Edge All modern mobile browsers

All three elements are universally supported in every modern browser. The implicit ARIA roles — banner for page-level header, navigation for nav, contentinfo for page-level footer — are exposed correctly to all screen readers (NVDA, JAWS, VoiceOver, TalkBack).

The only historical quirk: in Internet Explorer 8 and earlier, these elements weren't recognized as block-level by default. You needed the "HTML5 shiv" — a tiny JS snippet that called document.createElement('header') etc. IE8 has been end-of-life since 2016; you don't need this.

12 Real-world use cases

Marketing sites

Every marketing page: one <header> with logo + nav, one <footer> with legal links, one <main> in between.

Blog themes

WordPress, Ghost, Hugo themes — header with site nav, footer with categories, post header with byline.

E-commerce

Header: logo + search + cart. Footer: customer service, returns, payment methods, social.

Documentation sites

Header: product name + version selector. Sidebar: table of contents in <nav>. Footer: edit on GitHub link.

SaaS dashboards

Header: app name + user menu. Sidebar: app navigation in <nav>. Footer: usually omitted (admin screens).

News articles

Article <header> with headline + byline + dateline; article <footer> with related coverage and tags.

Reader apps

Pocket, Instapaper, Safari Reader all key off <header> + <footer> to strip chrome when extracting article text.

Government sites

WCAG 2.1 AA mandates "bypass blocks" — a skip link OR proper landmark structure. Header/nav/main/footer satisfies the requirement for free.

SPA route changes

In React/Vue SPAs, keep <header> and <footer> stable across routes; only swap content inside <main>. SR users retain their place in the document.
