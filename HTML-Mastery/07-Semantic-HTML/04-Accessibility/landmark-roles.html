HTML5 Landmark Elements & ARIA Roles

The biggest accessibility win in HTML5 wasn't a new attribute — it was new elements. <header>, <nav>, <main>, <aside>, <footer>, and friends map automatically to ARIA landmark roles, letting screen-reader users jump straight to the part of the page they need without listening to every line.

1 What Are Landmarks?

Landmarks are ARIA roles that identify the major structural regions of a page — the header, navigation, main content, sidebar, footer, and so on. Once a region is marked as a landmark, screen-reader users can:

  • Jump directly to it via keyboard shortcut (e.g., D in NVDA cycles landmarks, VO+U in VoiceOver opens a landmark rotor).
  • Get a list of all landmarks on the page to navigate by structure.
  • Skip repetitive content like site-wide headers and nav menus to reach the main content.

Before HTML5, developers had to manually add role="banner", role="main", etc. to <div> elements. Today, native HTML5 elements expose these roles automatically — you get them for free.

Key principle If you use the right HTML5 element, you don't need to add the corresponding role attribute. In fact, the W3C HTML5 spec explicitly tells authors NOT to add redundant ARIA roles — the browser already does the mapping.

2 Element → Role Mapping

The HTML Accessibility API Mappings (HTML-AAM) specification defines which ARIA role each HTML element exposes. Here's the complete landmark mapping:

HTML elementImplicit ARIA roleConditionLandmark type
<header>bannerOnly when not nested in <article>/<aside>/<nav>/<section>Page-level header
<nav>navigationAlwaysNavigation region
<main>mainAlways (one per page)Main content
<article>articleAlwaysSelf-contained composition
<aside>complementaryAlwaysSide content
<footer>contentinfoOnly when not nested (same as header)Page-level footer
<section>regionOnly when it has an accessible name (via aria-label or aria-labelledby)Named region
<form>formOnly when it has an accessible name (otherwise generic in newer specs)Named form region
<search>searchAlwaysSearch region (new in 2023)
Common Mistake Adding role="main" to a <main> element (or role="navigation" to a <nav>). It's redundant, makes your markup noisier, and some screen readers may double-announce the region. Trust the implicit mapping.

3 How Screen Readers Use Landmarks

Here's the workflow a screen-reader user follows on a well-landmarked page:

NVDA (free, Windows)

D — jump to next landmark
Shift+D — jump to previous landmark
Insert+F7 — open elements list, filter by landmarks

JAWS (Windows, commercial)

R — jump to next landmark region
Insert+R — cycle landmark regions
Insert+Ctrl+R — list landmarks

VoiceOver (macOS / iOS)

VO+U — open rotor, swipe to "Landmarks"
On iOS: two-finger swipe up/down jumps to next/prev landmark

TalkBack (Android)

Swipe up then right (or down then left) → "Landmarks" menu → tap a landmark to jump to it.

Without landmarks, users have only two ways to navigate: tab through every focusable element (exhausting) or read linearly from the top (painful on long pages). Landmarks give them a third option — structural navigation — that approaches the experience of a sighted user glancing at the page layout.

4 banner — The Page Header

Only one <header> per page should be the page-level header. When it's a direct child of <body> (not nested in <article>, <aside>, <nav>, or <section>), it exposes the banner role.

<body>
  <header>              <!-- ← exposes banner -->
    <h1>Acme Corp</h1>
    <nav>...</nav>
  </header>
  <main>...</main>
</body>

The "one banner per page" rule

The ARIA spec says: "In a document, the author MUST mark no more than one element with the banner role." If you nest <header> inside an <article>, it does not expose banner — it becomes a generic group. This is exactly what you want: each article can have its own header without creating extra banners.

<article>
  <header>             <!-- ← exposes "group", NOT "banner" -->
    <h2>Article title</h2>
    <p>By Jane Doe</p>
  </header>
  ...
</article>

5 navigation — The <nav> Element

Every <nav> element exposes the navigation landmark. Multiple <nav> elements per page are fine — but each should have a distinguishing accessible name so users can pick the one they want.

<nav aria-label="Primary">
  <ul>...</ul>
</nav>

<nav aria-label="Footer">
  <ul>...</ul>
</nav>

<nav aria-label="Breadcrumb">
  <ol>...</ol>
</nav>
Pro Tip When the visible text already names the navigation clearly (e.g. a visible "Site Sections" heading above the <nav>), use aria-labelledby pointing to that heading's id instead of aria-label. This avoids duplicating the text and keeps the label in sync automatically.
Common Mistake Wrapping every list of links in <nav>. The spec is clear: <nav> is for major navigation blocks. A list of social-media icons in the footer, or links inside a paragraph, should be a plain <ul> with anchors — not a <nav>.

6 main — The Main Content

The <main> element exposes the main landmark. Per spec, exactly one <main> per page. Its content should be unique to that page (not repeated across the site).

<body>
  <header>...</header>
  <nav aria-label="Primary">...</nav>
  <main>
    <h1>Page title</h1>
    <article>...</article>
  </main>
  <footer>...</footer>
</body>

"Skip to main content" link

Even with landmarks, sighted keyboard users benefit from a visible "skip link" as the first focusable element on the page. It's a redundant affordance — landmarks cover screen-reader users, but keyboard-only sighted users without a screen reader still need it.

<body>
  <a href="#main" class="skip-link">Skip to main content</a>
  <header>...</header>
  <main id="main" tabindex="-1">...</main>
</body>

The tabindex="-1" on <main> lets it receive focus programmatically when the skip link is activated — without it, focus moves but the browser may not scroll to it on all browsers.

7 contentinfo — The Page Footer

Like the header, the page-level <footer> exposes the contentinfo landmark only when it's not nested in a sectioning element. Nested footers (e.g. inside an <article>) become group instead.

<body>
  ...
  <footer>              <!-- ← exposes contentinfo -->
    <address>...</address>
    <p>© 2024 Acme Corp.</p>
    <nav aria-label="Footer">...</nav>
  </footer>
</body>

The contentinfo landmark typically contains: copyright, privacy/terms links, contact information (via <address>), social media links, language switcher.

8 complementary — The <aside> Element

Each <aside> exposes the complementary landmark — content that's related to the main content but not strictly part of it. Sidebars, pull quotes, related-content boxes, ads.

<main>
  <article>
    <h1>Main article</h1>
    ...
    <aside>            <!-- ← complementary landmark -->
      <h2>About the author</h2>
      ...
    </aside>
  </article>
</main>
Pro Tip If you have multiple <aside> elements on a page (e.g. a sidebar AND a pull quote AND a "related posts" widget), add an aria-label to each so users can distinguish them in the landmark rotor: aria-label="Author bio", aria-label="Pull quote", aria-label="Related posts".

9 region & form — The Conditional Landmarks

section → region (only when named)

A bare <section> does not expose the region landmark — it becomes a generic group. The reason: there are usually many <section>s per page, and exposing all of them as landmarks would clutter the rotor.

<!-- ❌ NOT a region — just a styled group -->
<section class="card">
  <h2>Title</h2>
  ...
</section>

<!-- ✅ A region — has an accessible name -->
<section aria-labelledby="weather-heading">
  <h2 id="weather-heading">Weather forecast</h2>
  ...
</section>

Use this when you have a section that warrants landmark status (e.g. a "Latest news" widget that users may want to jump to directly).

form → form (only when named)

Same rule. A <form> with an accessible name (via aria-label or aria-labelledby) exposes the form landmark. A bare form becomes a generic group.

<form aria-label="Newsletter signup" action="..." method="post">
  <label>Email: <input type="email" name="email"></label>
  <button>Subscribe</button>
</form>
Common Mistake Wrapping every form in role="form". Don't. Use aria-label on a real <form> element, and the browser will expose the landmark automatically. Adding role="form" on a <div> is the older pattern; with HTML5 it's unnecessary.

10 search — The New Landmark (2023)

The <search> element is the newest HTML5 landmark. It exposes the search role (which itself was added to ARIA 1.3 in 2023). Wrap any search interface in it — site-wide search, filter forms, search-as-you-type widgets.

<search>
  <form role="search" action="/search" method="get">
    <label for="q">Search this site</label>
    <input type="search" id="q" name="q">
    <button type="submit">Search</button>
  </form>
</search>

Before <search> existed, authors had to apply role="search" to a <form> or <div>. Now it's a native element, and you can drop the role attribute (the implicit mapping handles it).

Note on the role attribute Some screen readers still want role="search" on the inner form for older AT compatibility. The current best practice is: use <search>, and also add role="search" on the inner form if you want maximum backwards compatibility. Once AT support catches up (within ~2 years of the element shipping widely in 2023), the role attribute becomes redundant.

11 Practical Tips

One main per page

If you find yourself with two <main> elements, you have a layout problem. Reorganize so there's exactly one.

Name your duplicate landmarks

Multiple <nav>, <aside>, or named <section> per page is fine — just give each a distinct aria-label so users can tell them apart.

Don't nest landmarks pointlessly

A <nav> inside another <nav> rarely makes sense. Flatten if possible.

Keep the visible label aligned

If you have a visible heading "Section Menu" above a <nav>, point aria-labelledby at the heading instead of inventing a separate aria-label like "Section nav". They should match.

Test with the rotor

Open your page in VoiceOver (VO+U) or NVDA (Ins+F7) and look at the landmark list. It should look like a sensible table of contents for the page — no junk entries.

Use the W3C validator

Run your page through validator.w3.org/nu. It will flag duplicate mains, redundant roles, and other landmark issues.

12 Browser Support

<header> banner — Chrome/Firefox/Safari/Edge <nav> navigation — all <main> main — all (IE 11 with role fallback) <aside> complementary — all <footer> contentinfo — all <section> region when named — all <form> form when named — all <search> — Chrome 118+, Firefox 118+, Safari 17+

All landmark mappings except <search> have been stable since ~2014. <search> shipped in browsers in late 2023; for older browsers it gracefully degrades to a generic container (just add role="search" as a fallback if you support pre-2023 browsers).

13 Try It Yourself

Exercise 1 — Audit a page Open any popular website (a news site, an e-commerce front page). View source and count how many landmark elements (<header>, <nav>, <main>, <aside>, <footer>) appear. Identify any missing landmarks (e.g., no <main>, or multiple unnamed <nav>s).
Exercise 2 — Build the canonical page skeleton Create an HTML5 page with exactly one <header> (banner), one primary <nav>, one <main> containing an <article> and an <aside> (complementary), one <search>, and one <footer> (contentinfo). Verify with the W3C validator that all roles are exposed correctly (no need to add explicit role attributes).
Exercise 3 — Name your landmarks Take your exercise 2 page and add a second <nav> in the footer. Add appropriate aria-label values to both navs so screen-reader users can tell them apart.
Exercise 4 — Test with a screen reader Install NVDA (Windows, free) or enable VoiceOver (macOS). Open your page. Use the landmark rotor (NVDA: Ins+F7 → Landmarks; VoiceOver: VO+U → Landmarks). Confirm that every region appears with a meaningful name.

14 Real-World Use Cases

News sites

Header (masthead), primary nav, main (article), aside (related stories), search (site search), footer.

E-commerce

Header (logo + cart), nav (categories), main (product list or product detail), aside (filters), search (catalog), footer (legal links).

SaaS dashboards

Header (account), nav (sidebar menu), main (current view), aside (help panel), search (cmd-K palette), footer (status bar).

Blogs

Header (masthead), nav (categories), main (post), aside (sidebar with about + recent), search (site search), footer (contact via <address>).

Documentation sites

Header (product name), nav (sidebar TOC), main (current page), aside (right-side TOC or related), search (full-text search), footer (version switcher).

Web apps

Single-page apps should still expose landmarks — they're especially valuable for users navigating dynamic UIs.
