The Document Outline

Every HTML page has an invisible skeleton: its heading hierarchy. Get it right and screen readers, search engines, and reader modes all parse your content effortlessly. Get it wrong and the same tools see chaos. Here's how the document outline works — and the parts of the HTML5 outline algorithm you should ignore.

1 Heading hierarchy (h1–h6)

HTML gives you six heading levels: <h1> (most important) down to <h6> (least). These are not styling — they're structural. A heading opens a new implicit section that lasts until the next heading of equal or higher rank.

<h1>Cooking for Beginners</h1>
  <p>Intro paragraph…</p>

  <h2>Pasta</h2>
    <p>About pasta…</p>

    <h3>Spaghetti Carbonara</h3>
      <p>Recipe…</p>

    <h3>Penne Arrabbiata</h3>
      <p>Recipe…</p>

  <h2>Desserts</h2>
    <p>About desserts…</p>

Notice how <h3> appears between two <h2> sections — it's automatically a subsection of Pasta, not of Desserts. This is the "implicit section" rule.

Pro Tip Don't skip levels. Going from h2 straight to h4 is technically valid but breaks screen reader navigation (which expects each level to nest inside the previous one). Always go h2 → h3 → h4.

2 Implicit sections

A heading element implicitly opens a section that ends when:

  • A heading of equal rank appears, or
  • A heading of higher rank (lower number) appears, or
  • The containing element ends

So the structure of headings alone determines the outline — even without any <section> elements.

Implicit outline of the cooking example
1. Cooking for Beginners
1.1 Pasta
1.1.1 Spaghetti Carbonara
1.1.2 Penne Arrabbiata
1.2 Desserts

The numbered version above is roughly what screen readers and search engines reconstruct from the heading tags alone. No <section> required — though wrapping them makes the source code clearer for humans.

3 The HTML5 outline algorithm (deprecated but useful)

When HTML5 was first drafted, the spec proposed a clever idea: each <section> would reset the heading counter. So you could write:

<h1>Site Title</h1>
<section>
  <h1>Blog Post Title</h1>
  <section>
    <h1>Subsection</h1>
  </section>
</section>

…and the outline would be:

1. Site Title
1.1 Blog Post Title
1.1.1 Subsection

This "outline algorithm" was meant to free authors from memorizing h1–h6 levels. But it was never implemented by any browser. Screen readers and search engines fall back to the heading numbers themselves. The WHATWG removed the outline algorithm from the spec in 2022.

Common Mistake Using multiple <h1> tags inside nested <section>s expecting the browser to auto-rank them. It does not. Screen readers see three <h1>s and announce "heading level 1, heading level 1, heading level 1" — confusing.

What to do instead

Use <h1>–<h6> by number, matching the visual depth of your content. Use <section> to group related content visually and semantically, but don't expect it to change heading levels.

<h1>Site Title</h1>
<section>
  <h2>Blog Post Title</h2>
  <section>
    <h3>Subsection</h3>
  </section>
</section>

4 Using <section> to scope headings

<section> is the thematic grouping element. It's appropriate when the content inside has a unifying theme and (ideally) a heading. Use it to make the implicit section explicit.

When section helps

  • You have a long article and want to break it into thematic chunks
  • You want each chunk to be addressable via fragment links
  • You're building a tabbed interface where each tab is a section of related content
  • You're documenting API methods and each method is its own section
<article>
  <h1>Getting Started with Fetch API</h1>
  <p>Intro…</p>

  <section aria-labelledby="basic-heading">
    <h2 id="basic-heading">Basic Usage</h2>
    <p>…</p>
    <pre><code>fetch('/api')…</code></pre>
  </section>

  <section aria-labelledby="error-heading">
    <h2 id="error-heading">Error Handling</h2>
    <p>…</p>
    <pre><code>try { fetch... } catch(e) { ... }</code></pre>
  </section>

  <section aria-labelledby="adv-heading">
    <h2 id="adv-heading">Advanced: Streaming</h2>
    <p>…</p>
  </section>
</article>
Pro Tip Use aria-labelledby on <section> to give it an accessible name derived from its heading. Screen readers then announce the section name as a landmark — but only if there's a heading. A <section> without a heading is no more meaningful than a <div>.

5 The "one h1 per page" rule

The classic rule of thumb: exactly one <h1> per page. It represents the page's primary topic. Subtopics use <h2>; sub-subtopics use <h3>; and so on.

This isn't a hard spec rule — HTML technically allows multiple <h1>s. But every major consumer of your HTML — Google, screen readers, reader modes — assumes one <h1>. Don't fight them.

Page typeRecommended structure
Homepage One <h1> = site tagline; <h2> per major section ("Features", "Pricing", "Testimonials")
Blog post One <h1> = post title; <h2> per section; <h3> for sub-sections
Product page One <h1> = product name; <h2> for "Description", "Specs", "Reviews"
Documentation page One <h1> = page topic; <h2> per major concept; <h3> for sub-concepts
App dashboard One <h1> = view name; <h2> per panel/widget

Special case: article cards on a listing page

If your page is a blog index showing many post previews, each preview is an <article>. Each article's title is technically a heading. What level? <h2> — because the page already has an <h1> like "Blog".

<main>
  <h1>Blog</h1>

  <article>
    <h2><a href="/posts/semantic">Why Semantic HTML Matters</a></h2>
    <p>Excerpt…</p>
  </article>

  <article>
    <h2><a href="/posts/aria">ARIA in 2024</a></h2>
    <p>Excerpt…</p>
  </article>
</main>
Common Mistake Marking each article preview title as <h1> thinking "it's the title of this article". Screen reader users navigating by 1 would hear ten <h1>s in a row and lose track of where they are. Use <h2> for previews; the actual article page itself uses <h1>.

6 Accessibility tree vs DOM tree

These are two different trees built from the same HTML. Understanding the difference is the key to understanding how screen readers actually "see" your page.

DOM treeAccessibility tree
Built from every HTML element Built from elements that have semantic meaning
Includes <div>, <span>, presentational wrappers Skips elements with no semantic role (unless they have ARIA)
Used by CSS, JavaScript, and DevTools Used by screen readers, voice control, and other AT
Includes every node — visible or not Excludes display: none and visibility: hidden content
A <div class="button" onclick> is a node A <div class="button" onclick> is invisible (no role) — until you add role="button"

The practical implication: writing more DOM nodes doesn't help screen readers. Writing the right semantic elements does. One <button> in the DOM produces one node in the accessibility tree, fully wired. A div button requires three ARIA attributes and a JS event handler to even appear in the tree — and even then it's often buggy.

<!-- DOM: 1 node. A11y tree: 1 node, role=button, focusable -->
<button>Save</button>

<!-- DOM: 1 node. A11y tree: 0 nodes by default. -->
<!-- To appear: needs role=button + tabindex=0 + JS keyboard -->
<div class="btn" onclick="save()">Save</div>
Pro Tip You can inspect the accessibility tree directly in Chrome DevTools: Elements panel → Accessibility tab. Compare it side-by-side with the DOM tree. Anything in the DOM but not in the a11y tree is invisible to screen reader users.

7 Outline patterns

Pattern A: Classic article outline

HTML 
<article>
  <h1>GraphQL Schema Design</h1>
  <p>Intro…</p>

  <h2>Types</h2>
  <p>…</p>

  <h3>Object Types</h3>
  <p>…</p>

  <h3>Input Types</h3>
  <p>…</p>

  <h2>Queries</h2>
  <p>…</p>

  <h2>Mutations</h2>
  <p>…</p>
</article>
Outline
1. GraphQL Schema Design
1.1 Types
1.1.1 Object Types
1.1.2 Input Types
1.2 Queries
1.3 Mutations

Pattern B: Nested article (comment on a post)

<article>
  <h1>Why I Switched to Vim</h1>
  <p>Body of the post…</p>

  <section>
    <h2>Comments</h2>

    <article>
      <h3>Great post!</h3>
      <p>I agree with everything.</p>
    </article>

    <article>
      <h3>Disagree</h3>
      <p>Emacs is better.</p>
    </article>
  </section>
</article>
Pro Tip Comments are themselves <article> elements — they're self-contained, distributable content. Nested them inside the post article and use <h3> because they're a sub-heading inside the "Comments" <h2> section.

8 Common mistakes

MistakeWhy it's wrongFix
Skipping heading levels (h2 → h4) Screen reader users navigating by level get lost Always go h2 → h3 → h4
Multiple <h1>s in nested sections (relying on outline algorithm) The outline algorithm was never implemented; SR sees multiple level-1 headings One h1 per page; use h2-h6 inside
Using headings for visual styling ("I want big text") Pollutes the outline; SR users see junk headings Use CSS for styling; reserve headings for actual section titles
Marking every preview card title as <h1> Ten level-1 headings on one page Page gets one <h1>; previews are <h2> or <h3>
<section> without any heading No semantic value over a div; doesn't appear in the a11y tree as a landmark Either add a heading or use a div
Using <h2> in the footer for "Copyright" Adds noise to the outline; copyright isn't a section Use <p> for copyright text

9 Try it yourself

Exercise 1 — Outline audit Take any blog post you've written. Strip the CSS. Read just the headings top-to-bottom. Do they form a coherent summary of the post? If not, your outline is broken — fix the heading levels.
Exercise 2 — DevTools accessibility tree Open Chrome DevTools on any web page. Elements panel → Accessibility tab. Find the heading tree. Compare it to what's in the DOM. Are there "phantom" headings from divs? Are there missing headings where they should be?
Exercise 3 — Rebuild with one h1 Find a page that uses multiple <h1>s (often a homepage with multiple "feature" sections). Rewrite with one <h1> and proper <h2>/<h3> nesting. Test with a screen reader — does heading navigation now make sense?
Exercise 4 — Section labeling Build a docs page with three sections. Add aria-labelledby to each <section> pointing at its heading's id. Use VoiceOver's rotor (VO+U) to verify that each section now appears as a named landmark.

10 Browser support

Chrome Firefox Safari Edge NVDA JAWS VoiceOver

Headings and the implicit-section behavior they create are part of HTML itself — universal support across every browser ever made. The HTML5 outline algorithm (section-scoped heading ranks) is the only feature that was removed: no current browser implements it. Treat it as historical and use explicit <h1>–<h6> by number.

Accessibility tree inspection is available in Chrome DevTools (Elements → Accessibility), Firefox DevTools (Accessibility tab), and Safari Web Inspector (Nodes → Accessibility). All three let you see exactly what screen readers will announce.

11 Real-world use cases

Blog posts

One h1 for the title, h2 per section, h3 for sub-sections. Standard pattern across WordPress, Ghost, Medium.

Documentation sites

MDN, React docs, Vue docs — heavy use of section + aria-labelledby to make each topic a navigable landmark.

News articles

h1 = headline, h2 = subhead/deck, h3 = section breaks within long-form pieces.

Legal documents

Terms of Service, privacy policies — numbered sections, each with its own h2 for navigation.

Product detail pages

h1 = product name, h2 = "Description", "Specifications", "Reviews".

Comment threads

Each comment is an <article> with an <h3> (or h4 for replies to replies).

Documentation readers

Reader Mode, Pocket, Instapaper all extract the heading outline to show as a table of contents.

Search results

Google uses your heading outline for "Jump to section" links in SERPs.

Print PDFs

Print-to-PDF engines generate bookmarks from headings. Skip a level and you get a broken bookmark tree.
