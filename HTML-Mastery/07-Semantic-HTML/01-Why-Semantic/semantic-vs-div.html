Semantic HTML vs Div Soup

If your markup reads like <div class="header"><div class="title">…</div></div>, you have div soup. Semantic HTML replaces those divs with elements that convey meaning — to browsers, to assistive tech, to search engines, and to the next developer who opens your file.

1 What "semantic" means

A semantic element describes what its content means, not how it should look. The element name itself carries meaning:

ElementWhat it tells youWhat it does NOT tell you
<h1>"This is the most important heading on the page"What font size to use
<nav>"This is a major navigation block"Whether it should be horizontal or vertical
<article>"This is a self-contained, distributable piece of content"Whether it has a border
<button>"This is a clickable control that triggers an action"What color it is
<time>"This is a date or duration"How to format it

Presentation is the job of CSS. Meaning is the job of HTML. When you mix them — by choosing <div class="big-text"> instead of <h2> — you've made a div soup. The browser sees a div. The screen reader sees a div. Google sees a div. Everyone loses.

Pro Tip A semantic element is one whose tag name alone, with no class or role attributes, tells you why it exists. <div class="hero"> doesn't qualify. <header> does.

2 Why <div> and <span> aren't semantic

<div> and <span> are the only two elements in HTML that have no inherent meaning. They exist for when you genuinely need a generic grouping element — usually as a CSS hook or for layout (flex/grid containers). They are not inherently evil. They become evil when used instead of a more meaningful element.

Div soup — no meaning
<div class="header">
  <div class="nav">
    <div class="nav-item">Home</div>
    <div class="nav-item">About</div>
  </div>
</div>
<div class="main">
  <div class="article">
    <div class="title">Hello</div>
    <div class="body">Welcome.</div>
  </div>
</div>
Semantic — meaning is explicit
<header>
  <nav>
    <ul>
      <li><a href="/">Home</a></li>
      <li><a href="/about">About</a></li>
    </ul>
  </nav>
</header>
<main>
  <article>
    <h1>Hello</h1>
    <p>Welcome.</p>
  </article>
</main>

When div and span ARE appropriate

Use a <div> when…Use a <span> when…
You need a layout wrapper (flex/grid container) with no semantic role You need a phrasing-level CSS hook or JS target inside text
No existing element describes your content (e.g. a card grid container) You want to apply lang, dir, or styling to a slice of inline text
You're wrapping multiple elements that need a common parent for styling or scripting You're isolating a fragment for JS without breaking phrasing flow
Common Mistake Wrapping every section in a div "just in case you need it for CSS later". You usually don't. The semantic element is itself a valid CSS target — header { ... } works perfectly fine.

3 The cost of div soup

1. Poor accessibility

Screen reader users navigate by landmarks (header, nav, main, footer) and by headings. A div has no landmark role and no heading level. The user has to read every div top to bottom — useless for a 5,000-word article.

2. Poor SEO

Search engines weight <h1> heavily and use semantic structure to understand what a page is about. A div with class="title" tells Google nothing.

3. Harder to maintain

When every section is a div, the only way to know which div is which is to read its class name and hope the original author was consistent. <nav> needs no such guessing.

4. Worse default behavior

A <button> is keyboard-focusable, submits forms, fires click on Enter/Space, and is announced as "button". A <div onclick> is none of those things unless you bolt on a dozen attributes.

5. No Reader Mode support

Browser "Reader" modes extract article, main, headings, and paragraphs. Div soup confuses them and your content won't be readable in reader mode.

6. Misses browser features

Features like :focus-visible, tabindex defaults, form reset, autofill, and printing behavior are wired to specific elements. Choosing divs opts you out of all of it.

4 Before / after comparison

Same rendered output. Radically different markup. The "before" version requires re-implementing semantics through ARIA, classes, and JS. The "after" version gets it for free.

Case A: A site header with navigation

Before — div soup
<div id="site-header" class="header">
  <div class="logo">Acme Corp</div>
  <div class="navigation" role="navigation">
    <div class="nav-link" role="link"
         tabindex="0"
         onclick="go('/')">Home</div>
    <div class="nav-link" role="link"
         tabindex="0"
         onclick="go('/about')">About</div>
  </div>
</div>
After — semantic
<header>
  <a href="/" class="logo">Acme Corp</a>
  <nav>
    <ul>
      <li><a href="/">Home</a></li>
      <li><a href="/about">About</a></li>
    </ul>
  </nav>
</header>

Case B: A blog post

Before — div soup
<div class="post">
  <div class="post-title">Why Semantic HTML</div>
  <div class="post-meta">
    By <span class="author">Ada</span>
    on <span class="date">2024-03-12</span>
  </div>
  <div class="post-content">
    <div class="paragraph">Semantic HTML matters.</div>
    <div class="paragraph">Here is why.</div>
  </div>
</div>
After — semantic
<article>
  <h2>Why Semantic HTML</h2>
  <p>By <span>Ada</span>
     on <time datetime="2024-03-12">
       March 12, 2024
     </time>.</p>
  <p>Semantic HTML matters.</p>
  <p>Here is why.</p>
</article>

Case C: A call-to-action button

Before — div button
<div class="btn btn-primary"
     role="button"
     tabindex="0"
     onclick="submit()">
  Submit
</div>

<!-- And you still need to handle: -->
<!-- - Enter key fires click         -->
<!-- - Space key fires click         -->
<!-- - Disabled state                -->
<!-- - Focus ring styling            -->
<!-- - Form submission on Enter      -->
After — real button
<button type="submit"
        class="btn btn-primary">
  Submit
</button>

<!-- That's it. Keyboard, focus, -->
<!-- disabled, form submission,  -->
<!-- and screen reader support   -->
<!-- are all built in.           -->

5 The "would a stranger understand this?" test

Strip every class and id from your HTML, then hand it to a stranger with no CSS. Can they answer these questions?

  1. What is the title of this page? (Should be an <h1>)
  2. Where is the main navigation? (Should be <nav>)
  3. Where does the main content start? (Should be <main>)
  4. Is this a clickable action? (Should be <button> or <a>)
  5. Is this a form? (Should be <form>)
  6. Is this content self-contained, like a blog post? (Should be <article>)
  7. Is this content tangentially related, like a sidebar? (Should be <aside>)
  8. What's the copyright info at the bottom? (Should be <footer>)

If the stranger can't tell, you've used divs where semantic elements belong.

Pro Tip Turn off CSS in your browser (DevTools → Rendering → Emulate CSS media print, or use a "disable styles" extension). The page should still be usable and its structure should be obvious. Headings should be bigger; lists should have bullets; links should be underlined and blue; buttons should look like gray buttons. This is "naked HTML", and it's the test of whether your semantics hold up.
A handy "div-to-semantic" replacement table
If you wrote…Use this instead
<div class="header"><header>
<div class="nav"><nav>
<div class="main"><main>
<div class="footer"><footer>
<div class="article"><article>
<div class="sidebar"><aside>
<div class="section"><section> (only if it has a heading)
<div class="title"><h1>–<h6>
<div class="button" onclick><button>
<div class="dialog"><dialog>
<div class="figure"><figure>
<div class="date"><time>

6 Common mistakes

MistakeWhy it's wrongFix
<div onclick="..."> Not keyboard-accessible, not announced as a control Use <button> for actions, <a> for navigation
<div class="h1">Title</div> No heading semantics; loses SEO + a11y Use <h1> through <h6>
<div role="navigation"> with no nav element You're adding semantics via ARIA when an element already does the job Use <nav> directly (it has role="navigation" by default)
Wrapping every section in <div class="container"> Often unnecessary; the semantic element can be styled directly Apply styles to the semantic element; only add divs when truly needed for layout
Using <div> for list items Loses list semantics, screen reader count announcements Use <ul>/<ol> + <li>
Replacing all divs with sections <section> requires a heading — without one it's no better than a div Use <section> only when there's a heading; otherwise <div> is fine

7 Try it yourself

Exercise 1 — Spot the soup Open any random web page in your browser. View source. Find three places where the author used a div instead of a semantic element. Write down what semantic element would have been better.
Exercise 2 — Naked HTML test Take a page you've built. Disable all CSS (DevTools → Cmd/Ctrl+Shift+P → "Disable CSS"). Does the page still make sense? Is the heading hierarchy visible? Are nav links clearly links? Fix any structure that breaks when CSS is off.
Exercise 3 — Div soup → semantic Rewrite this markup semantically: 
<div class="card">
  <div class="card-image"><img src="cat.jpg"></div>
  <div class="card-body">
    <div class="card-title">My Cat</div>
    <div class="card-text">A photo of my cat.</div>
    <div class="card-button" onclick="like()">Like</div>
  </div>
</div>
Hint: figure, figcaption, h3, p, button.
Exercise 4 — Screen reader pass Install a screen reader (NVDA on Windows, VoiceOver on Mac, or use the "Read aloud" feature). Navigate your page by landmark (in NVDA: press D to jump to next landmark). Did the screen reader find your header, nav, main, and footer? If not, replace the corresponding divs.

8 Browser support

Chrome Firefox Safari Edge All mobile browsers

Semantic HTML elements (header, nav, main, article, aside, section, footer, figure, time, mark, etc.) are supported in every browser made since roughly 2011. There is no browser-compatibility excuse for using divs instead.

The only legacy concern is Internet Explorer 8 and earlier, which didn't recognize these elements as block-level. For IE8 support you needed the "HTML5 shiv" — a tiny script that registered the new elements via document.createElement. IE8 reached end of life in 2016. You don't need this anymore.

9 Real-world use cases

Marketing site redesigns

The classic refactor: take a div-soup landing page and rebuild with header/nav/main/footer. SEO and a11y improve overnight.

Component libraries

Design systems that emit semantic elements (Card → article, Modal → dialog, List → ul) need less ARIA bolted on by consumers.

Reader Mode compatibility

News sites that use article + headings get reliably extracted by Safari Reader, Firefox Reader View, and Pocket.

Accessibility audits

WCAG audits flag "no main landmark", "no h1", "div with onclick" — all fixable by switching from divs to semantic elements.

Migrations to React/Vue/Svelte

When porting templates to components, semantic elements become obvious component boundaries: <Article>, <Nav>, <Footer>.

Email templates

Even email clients — limited though they are — increasingly support article, section, and semantic headings. Use them where supported, fall back to tables only where needed.
